## ⭐ ГОЛОВНА ТЕЗА РОБОТИ (проводити наскрізно — Вступ, розд. 1–4, Висновки, захист)

**«Всетут» — це не черговий список задач. Його новизна — міжмодульний зв'язок даних:** запис в
одному модулі **активно впливає** на інші, а не лежить мертвим вантажем. Планувальник працює як
**прискорювач менеджменту** повсякдення. Технічно це реалізовано трьома механізмами:

1. **Єдиний календар** — усі модулі (навчання, робота, здоров'я, перегляд, покупки, цикл) зливають
   свої події в один потік через сутність `TaskItem` з полями `SourceModule`/`SourceEntityId`.
2. **Спільний список покупок** — нестача запасів їжі, ліків чи засобів гігієни з різних модулів
   автоматично стікається в один список; а одна відмітка «куплено» розходиться **назад** у запаси,
   аптечку, фінанси (витрата) та історію покупок.
3. **Спільний словник правил/тегів (RuleEngine)** — хвороби користувача (модуль «Здоров'я»)
   перетворюються на обмеження, які фільтрують страви («Їжа») і підсвічують попередження у списку
   покупок; баланс («Фінанси») обмежує підбір страв і покупок у межах бюджету.

Ця теза закриває критерії **К1** (актуальність/новизна) і **К2** (повнота рішення). Усюди, де
описуємо модуль, додаємо речення: «як цей модуль обмінюється даними з рештою».

## §C. РОЗДІЛ 2. ОГЛЯД ТЕХНОЛОГІЙ ТА СПЕЦИФІКАЦІЯ ВИМОГ (14–16 с.)

### 2.1 Огляд стеку технологій (≈5–6 с.)

Структура: клієнт → сервер → БД → безпека → інструменти. Для кожного — **чому обрано** (з посиланнями
на джерела ≤5 р.). Дані — реальні версії нижче.

- **2.1.1 Клієнтська частина (2–3 абзаци).** React **19.2** + Vite **8.3** + react-router-dom **7.18**;

- **2.1.2 Серверна частина (2–3 абзаци).** ASP.NET Core **.NET 8**, C#; архітектура Web API (REST).

### 2.2 Специфікація вимог до ПЗ — SRS (≈8–9 с.) — ⚠️ ядро розділу

Повний шаблон (методичка + приклад банку), заповнений під «Всетут». Нижче — **каркас із реальними
даними**; на захисті й у тексті це головний формальний документ.

- **Абзац 2 — типи правил (3–4 реч.).** Дані (реальні): `RecurrenceRule.Type` ∈ {**WeekCycle** — цикл

### 4.1 Реалізація та тестування модуля автентифікації та акаунта (≈2.5 с.)

- **Абзац 2 — JWT і сесії (3–4 реч.).** Claims `sub`/`tver`; читання userId централізовано; відкликання

- **Абзац 3 — керування акаунтом (2–3 реч.).** Експорт у JSON; видалення контенту/акаунта в транзакції;
  фонове очищення неактивних (попередження за 30 днів, видалення після року).

### 4.2 Реалізація та тестування календаря й механізму повторюваних подій (≈4 с.) — ⭐ найцінніше

- **Абзац 2 — генерація входжень (3–4 реч.).** `GetEffectiveOccurrences`, кліпування `EndDate`,

- **Абзац 3 — злиття календаря (3–4 реч.).** ⭐ `GetTasksForRangeAsync` зливає одноразові + повторення
  **всіх модулів** (study/work/health/media/shopping…) в один потік; фільтр деактивованих змін;
  групування накладань.
- **Абзац 4 — режими та борги (2–3 реч.).** 5 режимів; «борги» — похідний стан (прострочені дедлайни
  навчання/роботи/книг) агрегуються й показуються, але закриваються у відповідному модулі.
- **Лістинг 4.2 (≤1 с.):** фрагмент `GetEffectiveOccurrences` (кліпування + Cancelled/Moved).
- **Таблиця 4.2 — тест-кейси:** щоденне (EveryNDays), щотижневе (WeekCycle), числа місяця (29–31
  природно пропускаються), виняток Cancelled, перенесення Moved, кліпування за EndDate, злиття подій
  з модуля «Навчання» у календар.

### 4.3 Реалізація та тестування списку покупок як вузла зв'язку (≈3 с.) — ⭐ демонструє тезу
- **Абзац 1 — надходження в список (3–4 реч.).** ⭐ Нестача з Їжі (`OutOfStock` авто / `RunningLow`
  через підтвердження), Аптечки (`RunningLow` → розділ «Аптека»), Циклу (гігієна авто). Авто-
  категоризація за назвою (`guessShoppingCategory`).
- **Абзац 2 — «один жест, кілька ефектів» (3–4 реч.).** ⭐ `CheckItemAsync`: відмітка «куплено» →
  поповнює запас/аптечку + фіксує ціну (`UserProductPrice`) + **створює витрату** `FinanceTransaction`
  (якщо задано ціну) + пише `PurchaseHistory`. Ідемпотентно.
- **Абзац 3 — підбір у межах бюджету (2–3 реч.).** Баланс із Фінансів обмежує підбір покупок/страв
  (солвер комбінацій) — демо є навіть на головній сторінці.
- **Лістинг 4.3 (≤1 с.):** фрагмент `CheckItemAsync` (розходження ефектів) або `handleStock`.
- **Таблиця 4.3 — тест-кейси:** продукт OutOfStock → у список (авто); ліки RunningLow → підтвердження →
  розділ «Аптека»; відмітка «куплено» з ціною → запас Available + витрата у фінансах + історія;
  без дублів; гігієна циклу → список.

### 4.4 Реалізація та тестування швидкого додавання (NLP) (≈2.5 с.)
- **Абзац 1 — принцип (2–3 реч.).** Rule-based парсер (без ШІ/зовнішніх сервісів); **ніколи не створює
  автоматично** — завжди екран підтвердження; укр./англ.
- **Абзац 2 — маршрутизація (3–4 реч.).** ⭐ Один рядок → потрібний модуль: finance→транзакція,
  note→нотатка, media→запис, health→візит, work→зустріч, food→страва, запаси/покупки, решта→задача;
  заперечення («не купувати») → проста задача.
- **Абзац 3 — платний гейт (2 реч.).** 3 безкоштовні використання → 100 ₴ (WayForPay/мок); серверний
  контроль (`BillingService.ConsumeAsync`).
- **Лістинг 4.4 (≤1 с.):** фрагмент класифікації/маршрутизації рядка.
- **Таблиця 4.4 — тест-кейси:** «купити молоко завтра о 17» → задача; «витратив 200 на каву» →
  витрата; «записатися до стоматолога» → візит; «прочитати [книга]» → медіа; неоднозначне число; укр.
  фраза з друкарськconsole-помилкою (авто-виправлення); перевищення ліміту → paywall.

### 4.5 Керівництво користувача (≈2 с. у тексті, повне — у Додаток)
- Покрокові сценарії з **послідовністю скриншотів**: реєстрація → увімкнення модулів у профілі →
  створення події (разова/повторювана) → перегляд календаря й боргів → робота з модулем (напр. запаси
  → список покупок → відмітка «куплено») → швидке додавання. Кожен крок — скриншот + 1–2 речення.
- **Міні-підсумок розділу 4.** Реалізовано й перевірено функціональність; тестування підтверджує
  відповідність вимогам SRS; розроблено керівництво користувача.
