## 2. Что ломается — топ по всему проекту

### 🔴 CRITICAL

1. **Подделка JWT → захват любого аккаунта.** Симметричный ключ HS256 = `CHANGE_ME_TO_A_LONG_RANDOM_SECRET_IN_PRODUCTION` лежит в git (`server/appsettings.json:12`). Любой может сгенерировать токен с произвольным `sub` (= userId, которому доверяют все контроллеры) → полный доступ к чужим данным + выгрузка через `/api/account/export`. PoC: `poc/security/01-jwt-forgery.ps1`, `poc/robustness/mint_token.mjs`.

2. **Обход paywall «Швидке додавання».** Два независимых пути: (A) `Billing:Mock=true` по умолчанию + `ConfirmAsync` с `Mock || …` → бесплатная самостоятельная разблокировка; (B) callback `[AllowAnonymous]` (`BillingController.cs:67`), в `HandleCallbackAsync` **подпись не проверяется** — подделанный POST `transactionStatus:"Approved"` разблокирует фичу даже при `Mock=false`. PoC: `poc/security/02-billing-paywall-bypass.ps1`.

3. **Отсутствие всех обязательных юр. документов** (для приложения с данными о здоровье и менструальном цикле): нет Политики конфиденциальности, нет согласия на обработку перс. данных при регистрации, **нет явного согласия на обработку данных особой категории** (здоровье/цикл) — прямое нарушение ст. 7 ЗУ №2297-VI «Про захист персональних даних». `Cycle` открывается автоматически при `gender==='female'` без какого-либо согласия.

### 🟠 HIGH

4. **Битое правило повторения кладёт весь календарь.** `RecurrenceRulesController.IsValidRule` проверяет только непустоту; `TaskService.cs:133/:57` разворачивает его через `int.Parse`. Правило с `monthDays:"abc"` сохраняется (200), после чего **каждый** `GET /api/tasks/day` и `/period` отдаёт **500** — Day/Period-вид сломаны при каждой загрузке, пока правило не удалят в обход UI. Самострел, но воспроизводимый дураком. PoC: `poc/robustness/server_poc.sh`.

5. **500 на плохом вводе вместо 400 — системно.** В `Program.cs` нет middleware обработки исключений → каждый баг ввода отдаёт 500 с полным .NET stack trace в теле ответа. Конкретно: `GET /api/finance/stats` при `year=0/99999`/без параметра (`FinanceService.cs:78`, `new DateTime(year,…)`); `SetLimitAsync` и `ApplyReceiptTotalAsync` без `ClampMoney` → переполнение `decimal(18,2)`; `tasks/free-days` без ограничения диапазона.

6. **Брутфорс кода подтверждения email → захват чужого (ещё не зарегистрированного) email.** 6-значный код (`AuthController.cs:53`), нет счётчика попыток (`EmailVerificationCode.cs`), нет rate-limit. PoC: `poc/security/03-email-code-bruteforce.ps1`.

7. **Нет отзыва токена; срок 90 дней; logout только на клиенте** (`JwtService.cs:34`). Утёкший токен живёт 3 месяца.

8. **NLP quick-add — O(n²).** Длинная вставка морозит вкладку: ~56 КБ текста = ~62 с заблокированного main-thread, нет лимита длины. PoC: `poc/robustness/nlp_scaling.mjs`.

9. **Нет публичной оферты / условий / идентификации продавца** для платной фичи (ЗУ №675-VII «Про електронну комерцію»), **нет условий возврата** (ЗУ «Про захист прав споживачів»), **1-летнее авто-удаление аккаунта не раскрыто** и без предупреждающего письма — пользователь молча теряет мед./фин. данные.

### 🟡 MEDIUM / 🟢 LOW (выборка)

- Коммит секретов в git (JWT-ключ, WayForPay `MerchantSecretKey`), слабый HMAC-MD5 с хардкод-fallback (`BillingService.cs:211-216`).
- Перечисление аккаунтов через `email_taken` + неаутентифицированный вызов send-code (`AuthController.cs:50-51,83-84`).
- Нет rate-limiting нигде; нет HTTPS/HSTS/security-заголовков.
- Данные о несовершеннолетних: регистрация явно нацелена на `pupil` (школяр), но нет проверки возраста / согласия родителей.
- Мок-форма оплаты собирает номер карты/CVV внутри приложения (PCI); медицинский дисклеймер частичный (есть для лекарств/цикла, нет для аптечки/визитов); нет атрибуции DDInter/USDA.
- Хранение `<script>`/control/RTL/emoji «как есть» — поверхность для stored-XSS при будущем рендере.

## 3. Единство стиля — вердикт

**«Согласованное ядро, несогласованные швы».** Ключевые дисциплины из `plans/coding-guide.md` соблюдены единообразно, но есть ~4 структурных расхождения, читающихся как «археология истории разработки» (старые модули vs новые):

**Сильные расхождения (структурные):**
- **3 параллельных HTTP-слоя на клиенте:** 12 модулей через общий `http.js`; `api/tasks.js:4-21` — свой дублирующий враппер с *другой сигнатурой*; `api/client.js` + `api/account.js:8` — голый `fetch`. (Комментарий в `http.js` сам признаёт, что он извлечён из `tasks.js`, который так и не мигрировали.)
- **Сервис vs прямой `_db` на сервере:** Finance/Cycle/Study — через сервис; Notes/Todo/HealthProfile — прямо в `_db`; Media/Account — гибрид.
- **CSS-на-компонент только у половины дерева:** весь `study/` (7), `work/` (6), `notes/Board.jsx`, `common/ComboList.jsx` — без своих `.css`.
- **Хардкод украинских строк в обход i18n:** `Food.jsx:647,728`, `MonthGrid.jsx:38,48`, `Sidebar.jsx:54` — остаются украинскими в английской локали (живой баг локализации).

**Косметика:** разнобой объявления маршрутов (`[controller]` vs литерал vs пустая база), имена параметров `request` vs `r`, expression- vs block-bodied actions, generic-English ошибки в `client.js:43,52`.

**Что сделано единообразно (честный плюс):** украинские комментарии / английские идентификаторы везде; сервисы возвращают DTO (нет утечки EF-сущностей); сигнатуры `userId`-first `…Async`; все actions `IActionResult`; **ключи i18n синхронизированы идеально — uk.json/en.json по 997 ключей, ноль пропусков**; только функциональные компоненты; единый no-semicolon JS. Баланс: ~6 плюсов против ~8 расхождений (4 структурных + 4 косметических).

## 4. Проверенные «честные негативы» (НЕ уязвимо)

Чтобы отчёт не вводил в заблуждение:
- **IDOR нет.** Каждый модуль (Tasks, Finance, Cycle, Medicine, HealthProfile, Study, Work, Notes, Shopping, Media, Todo, Checkup, Account) скоупит все операции по `userId`. Полная таблица-доказательство — в приложении секции 01.
- **SQL-инъекций нет** (нет raw/интерполированного SQL), **mass-assignment нет** (DTO-записи, а не EF-сущности), **загрузки файлов / path-traversal нет** (контроллер «Media» — это watchlist, не файлы).
- `LastActiveAt`-middleware выполняется **после** `UseAuthentication/UseAuthorization` — подмена `sub` там невозможна (гипотеза из брифа не подтвердилась).
- Auth-эндпоинты отдают 400 (не 500) на пустые поля — ASP.NET валидирует non-nullable record-строки; `AddTransaction`/`SetBalance` безопасно клампятся; разворот повторений ограничен 1 годом.
- Выгрузка/удаление данных технически реализованы (`AccountController` + Settings UI) — но пользователю о праве на это нигде не сообщают (нет политики).
