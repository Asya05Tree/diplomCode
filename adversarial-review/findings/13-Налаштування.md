## 1. Фронтенд — сторінка, вкладки, логіка

### 1.1 🔴 Зміна статі / статусу навчання стирає зріст/вагу/рік народження — CONFIRMED (reproduced)
**Evidence:** `client/src/api/healthProfile.js:8-9` builds `{ height, weight, birthYear, gender, studentType, isWorking }`; `App.jsx:110-112` calls `setHealthProfile({ gender })` (and `:101-106` `setHealthProfile({ studentType, isWorking })`) — omitted keys are `undefined` and `JSON.stringify` drops them. Server `HealthProfileController.cs:53-55` **unconditionally** writes `profile.Height = request.Height is double ? clamp : null` for Height/Weight/BirthYear (no protective `if`, unlike Gender/StudentType/IsWorking at :56-59). A missing field ⇒ `null` ⇒ overwrites stored value.
**Reproduction:** `poc/13-settings/01-profile-null-wipe.mjs`
```
After Health tab save: { Height:'170', Weight:'65', BirthYear:'1998', Gender:'female', ... }
Wire body the client actually sends on gender toggle: {"gender":"male"}
PUT (gender toggle) status=200 → { Height:'NULL', Weight:'NULL', BirthYear:'NULL', Gender:'male', ... }
Wire body on study-status toggle: {"studentType":"none","isWorking":false}
PUT (study toggle) status=200 → { Height:'NULL', Weight:'NULL', BirthYear:'NULL', ... }
Gender toggle nulls numeric fields: CONFIRMED (BROKEN)
Study  toggle nulls numeric fields: CONFIRMED (BROKEN)
```
**Impact:** 100%-reliable silent data loss. Every click on a gender/study-status button in Settings erases body metrics entered in the Health tab — those feed the food rules engine (BMI/age), so recommendations silently degrade. Expected: a PATCH-style merge or a protective `if` on the three numeric fields.

### 1.2 🟠 Оптимістичне оновлення без відкату й без обробки помилки — CONFIRMED (code)
**Evidence:** `App.jsx:101-107,110-113` — `handleSetStudyStatus`/`handleSetGender` call `setState` first, then `await setHealthProfile(...)` with no `try/catch`. On PUT failure the UI already flipped (sidebar entry appeared/disappeared) and the promise rejects unhandled. Combined with 1.1 every such PUT also nulls numeric fields; rapid toggling races (last-write-wins, no debounce/serialisation). See also §11.1.
**Impact:** UI/DB divergence until reload (`loadStudyStatus`); unhandled rejection.

### 1.3 🟡 Вкладки — локальний стан без збереження — CONFIRMED (code)
**Evidence:** `Settings.jsx:29` `useState('appearance')`; Layout remounts via `key={location.pathname}` (`App.jsx:40`). Navigating away and back always resets to "Appearance". Acceptable but non-obvious after account actions.

### 1.4 🟡 `accountNote` («Усі дані видалено») не скидається й відв'язаний від контексту — CONFIRMED (code)
**Evidence:** `Settings.jsx:83` sets `accountNote` on wipe; it renders at `:346` next to the **Export** button (outside the danger zone that triggered it) and is never cleared while mounted.

### 1.5 🔵 `settings.title` присутній у перекладах, ніде не використовується — CONFIRMED
**Evidence:** `grep settings.title *.jsx` → no hits; keys exist (`uk.json`/`en.json` = "Налаштування"/"Settings"). Dead key (see §4.2).

## 2. Стилі, CSS, адаптивність, теми, прев'ю

### 2.1 🟠 Немає видимого фокуса клавіатури — CONFIRMED (code)
**Evidence:** `Settings.css` has no `:focus`/`:focus-visible` rule for `.settings-option` or `.settings-tab`; the only `outline` is on `.settings-swatch--active` (Settings.css:213-225), i.e. tied to selected state, not focus. Tabbing through segmented buttons/swatches shows no indicator.
**Impact:** keyboard-only and a11y users (see §5) cannot see focus.

### 2.2 🟡 Прев'ю формату дати — різні роздільники між варіантами — CONFIRMED (code)
**Evidence:** `date.js` `formatDateFor`: dmy=`09.03.2026` (dots), mdy=`03/09/2026` (slashes), ymd=`2026-03-09` (hyphens), ydm=`2026.09.03` (dots); surfaced verbatim in `Settings.jsx:249`. Inconsistent separators confuse comparison.

### 2.3 🟡 Прев'ю палітри ігнорує тему / контраст пастелі — CONFIRMED (code)
**Evidence:** swatch gradient = `PALETTE_COLORS[name][paletteStyle]` only (`Settings.jsx:182`), theme-independent by design; but swatch label/border are theme-dependent — pale gradients (e.g. amber `#FFF1A8→#FFD59E`) need contrast verification on the light card.

### 2.4 🟡 `--color-success` fallback `#2e7d32` на темній темі — CONFIRMED (code)
**Evidence:** `Settings.css:311` `.settings-account-note { color: var(--color-success,#2e7d32); }` — dark-green fallback may be low-contrast on a dark background if the var is undefined.

### 2.5 🔵 Адаптив/анімація — CONFIRMED (code, acceptable)
`.settings-appearance-row`→1 col at 560px; palette grid `auto-fit minmax(110px,1fr)`; who-logged-in row `nowrap+ellipsis` (full email needs tooltip). Transition deliberately excludes `background` to avoid gradient flicker.

## 3. Валідація, стани (exporting/working/error)

### 3.1 🟠 Enter у полі пароля обходить `busy` → подвійна відправка wipe/delete — CONFIRMED (code)
**Evidence:** `Settings.jsx:381` `onKeyDown={(e)=>e.key==='Enter'&&submitConfirm()}`; `submitConfirm` (`:71-97`) has **no `if (busy) return`** guard — only the button is `disabled={busy}` (`:389`). Enter is not gated. The server has no idempotency key either, so N rapid Enters issue N `wipe`/`delete` POSTs. (The server is rate-limit-free, §4 below / §8 — all attempts accepted.)
**Impact:** duplicate destructive requests; wipe is idempotent-ish but delete's 2nd call hits the password gate inconsistently (see §5-05 / PoC 05 step 5).

### 3.2 🟡 `setState` на розмонтованому компоненті після delete — CONFIRMED (code)
**Evidence:** `Settings.jsx:85-86` success→`onLogout()` (remount), then `finally{ setBusy(false) }` (`:94`) runs post-unmount → React warning. Harmless.

### 3.3 🟡 `exporting` не блокує небезпечні дії й навпаки — CONFIRMED (code)
**Evidence:** `exporting` disables only the export button (`:342`); wipe/delete modal still openable; `busy` doesn't block export. No cross-locking.

### 3.4 🔵 Клієнтська валідація пароля = лише «непорожній» — CONFIRMED (acceptable)
**Evidence:** `Settings.jsx:72` `if(!password)`; real check is server-side BCrypt. Correct.

### 3.5 🔵 Очищення помилок — CONFIRMED (acceptable)
`accountError` cleared in open/close/submit; `exportError` only before next export.

## 7. Авторизація та власність

### 7.1 ⚪ Усі запити фільтровані за `CurrentUserId`; експорт self-scoped — VERIFIED (reproduced)
**Evidence:** `AccountService.ExportAsync:101-178` every table `.Where(UserId==userId)`; children via parent userId. PoC 03:
```
C) attacker own-token export contains victim's email: no (self-scoped)
```

### 7.2 ⚪ IDOR на профіль неможливий — REFUTED (by design)
**Evidence:** `HealthProfileController` GET/PUT take no id param; always `FindAsync(CurrentUserId)`. There is no path/body id to tamper with — no IDOR surface. (Cross-user action requires forging a token for another `sub`, which is the TAB-01 key issue, not a Settings-level IDOR.)

### 7.3 ⚪ Re-auth паролем справжній на сервері — VERIFIED (reproduced, PoC 04 — forged token + wrong pwd still 400)
```
B) delete victim via forged token + wrong pwd: status=400 error=invalid_credentials (password is the barrier)
```

### 7.4 🟠 Видалення акаунта не відкликає JWT — CONFIRMED (reproduced)
**Evidence:** `AccountService.DeleteAccountAsync:81-97` removes the User row; no token blacklist/version. PoC 05:
```
1) delete: status=200  Users row remaining=0
2) GET /health-profile with post-delete token: status=404  (NOT 401 → token still authenticates)
3) GET /account/export post-delete: status=404
4) PUT /health-profile post-delete: status=500  (orphan upsert attempted for dead account)
5) delete again: status=400 invalid_credentials (auth passes; password gate 400s on missing user)
```
**Impact:** a captured/stored token keeps passing `[Authorize]` until `exp`; `UpdateProfile` (`HealthProfileController.cs:44-49`) tries to upsert a `UserProfile` for a deleted `UserId` → FK 500 (dead-account request processed). No revocation.

### 7.5 🔵 `CurrentUserId` робить `int.Parse(...!)` — CONFIRMED (fragile)
**Evidence:** `AccountController.cs:31` / `HealthProfileController.cs:29` — missing/non-numeric `sub` → 500 not 401. (TAB-01 covers forged-`sub` cases.)

## 8. Безпека (НЕБЕЗПЕЧНА ЗОНА)

### 8.1 ⚪ Хеш пароля НЕ в JSON-експорті — VERIFIED-SAFE (reproduced)
**Evidence:** `AccountService.cs:109-113` projects only `Id,Nickname,Email,IsEmailConfirmed,CreatedAt,LastActiveAt`. PoC 03:
```
password hash present in export: no
```
Caveat: `profile` and module entities are exported **as full entities** (`AccountService.cs:114+`) — any future sensitive column added to those models auto-leaks. Recommend explicit DTOs.

### 8.2 🔴(chain) / 🟡(local) Export без re-auth + forgeable token = повний data-exfil — CONFIRMED (reproduced)
**Evidence:** export has no password gate (§6.3); the dev signing key is committed (`provision.mjs:21`) so a token for any `sub` can be minted. PoC 03:
```
B) GET /export FORGED token for victim userId=101: status=200 contains-victim-email=true bytes=1454
```
**Impact:** knowing only a victim's numeric userId, an attacker downloads their entire dataset (cycle/health/finance) with no password. Root cause of forgeability is TAB-01 (committed `CHANGE_ME...` key); the Settings-side aggravator is "export requires no re-auth". Hardening export with a password/fresh-token requirement would break this chain even if the key leaks.

### 8.3 ⚪ CSRF неексплуатований — VERIFIED-SAFE
**Evidence:** auth is a `Bearer` header, not a cookie (`http.js:14,24`, `account.js:9`). Browsers don't attach it cross-site; no ambient credentials ⇒ classic CSRF on wipe/delete/export fails. Export is GET but token is in the header, not the URL.

### 8.4 🟠 Delete неатомарний (дві транзакції) — CONFIRMED (code)
**Evidence:** `AccountService.cs:22,77` `WipeContentAsync` opens+commits its **own** tx; `DeleteAccountAsync:89-95` opens a **second** tx for modules/profile/codes/User. A crash between commits leaves all content wiped but the `User` row alive → "half-deleted" account. Should be one transaction.

### 8.5 🟠 Немає rate-limit/локауту на перевірку пароля — CONFIRMED (reproduced)
**Evidence:** no throttling in `VerifyPasswordAsync`. PoC 04:
```
C) 12 wrong-password wipe attempts statuses=[400×12]  (no 429, no lockout)
```
**Impact:** a session-holding attacker can brute-force the password via the destructive endpoints unthrottled.

### 8.6 🟡 Експорт — весь датасет у пам'ять — CONFIRMED (code)
**Evidence:** `AccountController.cs:47` `SerializeToUtf8Bytes(data,...)` after materialising every table into `List<>`; no streaming/paging. Memory spike for large accounts.

### 8.7 🟡 Delete може лишати дані, прив'язані не до `UserId` — PARTIAL (code)
**Evidence:** email-keyed codes cleaned (`AccountService.cs:93`) ✅, but any email-keyed payment/entitlement rows (quick-add paywall) are not visibly cleaned in `DeleteAccountAsync`. Worth auditing (entitlement table not referenced here).

### 8.8 🔵 Немає другого підтвердження (слово DELETE) — CONFIRMED (acceptable for thesis).
