# Findings — TAB 14: Спільне (оболонка, навігація, автентифікація, інтеграція)

Adversarial review of the cross-cutting / system layer of **Всетут**
(React/Vite client + ASP.NET Core / EF / MySQL server).

- **Environment:** backend live at `http://localhost:5080` (Development), MySQL docker `planner-mysql`.
- **PoCs:** `adversarial-review/poc/14-system/*.mjs` — runnable with `node <file>.mjs` against the live server.
- **Method:** every point is **CONFIRMED** (live reproduction + `file:line`), **REFUTED**, or **AUDIT/cross-ref** (owned per-module by tabs 03–13 or needs manual UI check).

Verdict legend: 🔴 critical confirmed · 🟠 major confirmed · 🟡 minor confirmed · 🔵 noted/audit (behavior as-designed or needs manual check) · ⚪ REFUTED.

> **Bottom line proven on the live server:** the committed JWT signing key lets anyone mint a
> valid token for *any* userId (PoC 01), tokens are never revoked and live 90 days (PoC 03), the
> client-only gating of study/work/cycle is bypassable at the API by any logged-in user (PoC 05),
> and the `[AllowAnonymous]` billing callback flips the paid feature to "unlocked" from an
> **unsigned** request (PoC 06). Signature/lifetime validation itself is correct (PoC 07) — the key,
> not the crypto, is the hole.

**6.3 — 🔴 (top risk #1).** The signing key `CHANGE_ME_TO_A_LONG_RANDOM_SECRET_IN_PRODUCTION` is committed (`appsettings.json:12`) and loaded verbatim (`Program.cs:49`, `JwtService.cs:21`). Anyone with the repo signs an HS256 token for any `sub`.
- Reproduction: **PoC `01-jwt-forgery.mjs`** — forge token for victim userId 138, no password:
```
/api/auth/me          -> 200  {"nickname":"Victim","email":"adv.t14.victim@gmail.com"}
/api/finance          -> 200  {"balance":0,"limits":[],"transactions":[],...}
/api/cycle            -> 200
VERDICT: CONFIRMED 🔴  -> Any account is fully impersonatable by userId alone.
```
(POST /api/notes returned 400 only because the probe body was intentionally empty — read/identity are fully granted.)

**6.2 — 🔴 (top risk #3).** `handleLogout` (`App.jsx:115-122`) only `localStorage.removeItem`. No blacklist / token-version / `SecurityStamp`; validation is stateless (`Program.cs:41-50`).
- Reproduction: **PoC `03-token-no-revocation.mjs`**:
```
[3] AFTER logout   /api/auth/me -> 200  {"nickname":"Logout",...}
[3] AFTER logout   /api/finance -> 200
[4] token exp = 2027-02-05T...  (~90 days from now)
VERDICT: CONFIRMED 🔴
```
Lifetime 90 days hardcoded (`JwtService.cs:34`, `expires: DateTime.UtcNow.AddDays(90)`). A captured token = ~3 months of access that "Вийти" cannot kill.

**6.1 — 🟠** Token stored in `localStorage['authToken']` (`http.js:6-10`, `App.jsx:32`). Combined with 6.2/6.3 and no CSP (§8), any XSS exfiltrates a 90-day bearer.

**6.4 — 🟠** `apiGet/apiSend` (`http.js:12-30`) throw via `throwApiError` (`client.js:13-16`) with no global 401→logout handling. A token expiring mid-session leaves the user stuck in a "logged-in" UI with every request failing generically. CONFIRMED by code (only `getMe` at startup handles it).

**6.5 — 🔵** Default `ClockSkew` (5 min) observed live: in an earlier run a token expired 10 s ago was still accepted; `07-token-negatives.mjs` with exp −1h → correctly 401. Behavior as-designed, noted.

**6.6 — 🟠** `Program.cs` has no rate-limiting middleware (none registered). `/api/auth/login` returns generic `invalid_credentials` (good, no user enumeration — `AuthController.cs:124-125`), **but** `/api/auth/send-code` and `/register` return `email_taken` (`AuthController.cs:50-51, 83-84`) → registered-email enumeration. Also 6-digit codes use `Random.Shared` (`AuthController.cs:53`, not crypto) with no attempt/throttle limit. CONFIRMED by code.

**6.7 — ⚪ REFUTED.** `Me` does `FindAsync` and returns 404 for a deleted user (`AuthController.cs:136-137`); the client `.catch` treats any `/me` failure as "clear token" (`App.jsx:87-89`), so a deleted account is logged out correctly. No defect.

**6.3 control — ⚪/⚪** `07-token-negatives.mjs`: alg:none → 401, wrong-key → 401, expired → 401. **Validation is correct**; this isolates the committed key as the sole cause of 6.3.

## 7. Авторизація системно (IDOR / scope)

**Systemic pattern — baseline CORRECT.** All 17 data controllers apply `[Authorize]` at class level and derive `private int CurrentUserId => int.Parse(User.FindFirst(Sub)!.Value)`; by-id operations filter `x.Id==id && x.UserId==CurrentUserId` → foreign ids yield `NotFound`. - Reproduction of the gate working: **PoC `02-authz-sweep.mjs`** — all 20 data endpoints return **401** without a token; only `/api/health` (200), `/api/billing/callback` (200), `/api/billing/return` (302), and swagger (dev) answer without auth.

**Caveat:** this baseline is only as strong as the token (§6.3 breaks it entirely) and does **not** cover conditional-module status (§2.1). Per-entity IDOR for each module (tasks, media, finance, study steps, work contacts, etc.) is owned by tabs 03–13 — not duplicated here. The one nested-resource risk worth re-checking (study `steps`→`project`, recurrence `exceptions`→`rule`) belongs to those tabs.

**7-HealthController — 🔵** `HealthController.cs:9-24` has no `[Authorize]`; it only runs `Database.CanConnectAsync()`. Publicly discloses DB reachability (`02-authz-sweep.mjs` → 200 `{"status":"ok","database":"connected"}`). Low impact; noted.

**AccountController — ⚪ safe.** `AccountController.cs:18-19` is `[Authorize]`; `export`/`wipe`/`delete` take **no id parameter** — they operate solely on `CurrentUserId` (confirmed by read). No cross-user account deletion path.

```
[3] status after forged callback -> unlocked=true
VERDICT: CONFIRMED 🔴
```

**8.9 — 🟠** `appsettings.Development.json:5-9` sets EF Core logging to `Information` → SQL with parameters (emails, verification codes) is logged. Must be suppressed in prod for auth/billing.

**8.11 / 8.12 — 🟠** See 6.6. `Random.Shared` for codes (`AuthController.cs:53`), no attempt/send throttling, `email_taken` enumeration (`AuthController.cs:50-51,83-84`).
