## Як читати цей план

# 🟥 P0 — Блокери (робити першими, згори вниз)

## P0-1. Прибрати секрети з git і перегенерувати JWT-ключ  _(S1 + S6)_

**Що зламано:** закоммічений плейсхолдер `Jwt:Key = "CHANGE_ME_TO_A_LONG_RANDOM_SECRET_IN_PRODUCTION"` дозволяє будь-кому підробити токен для **будь-якого** `userId` → повне перевтілення в чужий акаунт без пароля. Разом з ним у git лежать WayForPay `MerchantSecretKey` і пароль БД.
**Де підтверджено:** `poc/01-auth/*`, `poc/14-system/01-*` (forged JWT → `/api/auth/me` 200 за чужого юзера).
**Корінь:** `server/appsettings.json:12,24`, `server/appsettings.Development.json:3`, `Program.cs:49`, `JwtService.cs`.

**Як виправити (просто, без Vault):**
1. **Прибрати секрети з коду.** Винести `Jwt:Key`, `Billing:WayForPay:MerchantSecretKey`, рядок підключення з паролем БД у:
   - для розробки — **User Secrets** (`dotnet user-secrets set "Jwt:Key" "<64+ випадкових байтів>"`), це вбудований механізм ASP.NET, не вимагає пакетів;
   - для «прод»/захисту — змінні середовища (`Jwt__Key`, `ConnectionStrings__Default` тощо). ASP.NET читає їх автоматично поверх `appsettings.json`.
2. **Згенерувати справжній ключ** ≥ 64 випадкових байтів (base64), а не словникову фразу.
3. У `appsettings.json` лишити тільки **плейсхолдери-посилання** або порожні значення; жодного реального секрету.
4. Додати в `.gitignore`: `appsettings.Development.json`, `appsettings.*.local.json`, `*.secrets.json`. Файл `appsettings.json` без секретів може лишитись у репозиторії.
5. **Перегенерувати всі секрети**, бо вони вже в історії git (вони скомпрометовані назавжди): новий JWT-ключ (інвалідовує всі старі токени — це добре), новий пароль MySQL, нові WayForPay-ключі в кабінеті.
6. На старті додати перевірку: якщо `Jwt:Key` відсутній або коротший за 32 байти — **кидати виняток і не запускатись** (щоб плейсхолдер ніколи не доїхав до прод).

**Перевірка:** `poc/14-system/01-*` і `poc/01-auth/*` з підробкою ключа → очікувано **401** (підпис більше не сходиться). Старі видані токени теж 401.

## P0-2. Серверний гейтинг умовних модулів: Навчання / Робота / Цикл  _(S2)_

**Чому це проти спеки:** `planner-spec.md §2.4` — «Выключённый модуль не появляется нигде: ни в навигации, ни в фильтрах, ни в анкете». Приховування — частина контракту, а не косметика.
**Де підтверджено:** `poc/09-study/01`, `poc/10-work/01`, `poc/11-cycle/01`, `poc/14-system/05`.
**Корінь:** `server/Controllers/StudyController.cs:16`, `WorkController.cs`, `CycleController.cs:16` — жодної перевірки профілю.

**Як виправити (просто):**
- Додати **одну перевірку на вході кожного контролера** умовного модуля: прочитати профіль поточного юзера й повернути **403**, якщо модуль йому не належить:
  - `StudyController` → `profile.StudentType in ('pupil','student')`;
  - `WorkController` → `profile.IsWorking == true`;
  - `CycleController` → `profile.Gender == 'female'`.
- Реалізувати як маленький приватний метод-гард (`EnsureModuleEnabled()`), що викликається першим рядком у кожному екшені, або як атрибут-фільтр `[RequireModule("study")]`, якщо так чистіше. **Без узагальнених абстракцій** — рівно три прості перевірки (coding-guide §2).

**Перевірка:** ті самі PoC з акаунтом без модуля → очікувано **403** замість 200; дані не створюються.

> Примітка: за `planner-spec.md §3.1` модулі мали б жити в окремій таблиці `UserModule(UserId, ModuleCode, IsEnabled)`. Поточна реалізація виводить їх із полів профілю — цього достатньо для гейтингу; міграцію на `UserModule` можна зробити пізніше (не блокер безпеки).

## P0-3. Закрити обхід платного Quick Add  _(S3)_

**Що зламано:** три незалежні дірки, кожна окремо дає платну фічу безкоштовно:
1. `Billing:Mock=true` потрапляє у прод → будь-яка «оплата» одразу успішна (mock);
2. callback оплати `[AllowAnonymous]` і **не перевіряє `merchantSignature`** → хто завгодно POST-ить «оплату пройшла» і розблоковує акаунт;
3. generic-шлях створення не перевіряє entitlement → пейвол обходиться знизу (`findings/02`).
**Де підтверджено:** `poc/02-quickadd/billing_bypass`, `poc/14-system/06`.
**Корінь:** `server/appsettings.json:15` (`Mock=true`), `server/Services/BillingService.cs:109,117` (callback без перевірки підпису).

**Як виправити:**
1. `Billing:Mock` — **тільки з конфігу середовища**, за замовчуванням `false`. У проді ніколи не `true`. На старті: якщо середовище Production і `Mock=true` — відмовити в запуску.
2. **Перевіряти `merchantSignature`** у callback: обчислити HMAC-MD5 за полями транзакції тим самим `MerchantSecretKey` (вже є в налаштуваннях WayForPay), порівняти з присланим. Не збігається → **400**, нічого не розблоковувати.
3. Entitlement перевіряти **на сервері на шляху фактичного створення** (не лише в UI): якщо безкоштовний ліміт вичерпано і немає розблокування — **402/403**. Див. також P2-7 (TOCTOU у лічильнику).

**Перевірка:** `poc/02-quickadd/billing_bypass` → анонімний callback очікувано **400** (підпис не сходиться); акаунт лишається заблокованим; у Production `Mock` недоступний.

# 🟧 P1 — Self-DoS, цілісність і приватність даних

## P1-1. Безпечне читання `userId` з токена (прибрати 500)  _(S5)_

**Що зламано:** валідний підпис, але без `sub` / з нечисловим `sub` → `int.Parse(User...Sub!.Value)` кидає → **500** замість 401. Патерн повторюється в усіх контролерах.
**Де підтверджено:** `poc/01,03,06,07,08,11,12`.
**Як виправити:** один спільний helper (extension на `ControllerBase` або `ClaimsPrincipal`), напр. `TryGetUserId(out int id)`: `TryParse` замість `Parse`; якщо немає/не число → повернути `Unauthorized()`. Замінити всі `int.Parse(... Sub ...)` на нього. Проста заміна, 1 метод + sed по контролерах.
**Перевірка:** токен без `sub`/з текстовим `sub` → **401**, не 500.

## P1-2. Глобальний обробник помилок + вимкнути stack trace у проді  _(S7)_

**Що зламано:** `DeveloperExceptionPage` активний → будь-який необроблений виняток віддає повний stack trace (внутрішня структура, шляхи, типи EF). Десятки 500 нижче цим і зручні атакам.
**Корінь:** `server/Program.cs` (dev exception page глобально).
**Як виправити (просто):** додати `UseExceptionHandler` з віддачею `ProblemDetails` (`{ "error": "internal_error" }`, без деталей) для не-Development; `DeveloperExceptionPage` лишити **тільки** під `app.Environment.IsDevelopment()`. Це вбудований механізм, без пакетів. Лог деталей — на сервер, не в тіло відповіді.
**Перевірка:** будь-який з 500-PoC у режимі Production → тіло без stack trace.

> Це **страхувальна сітка**, а не заміна валідації. Конкретні 500 нижче (P1-3…P1-6) треба лагодити по суті — щоб повертався 400 з сенсом, а не 500 «щось пішло не так».

## P1-3. Календар: дубль винятку правила ламає весь календар  _(вкладка 03)_

**Що зламано:** два `RecurrenceException` на одну дату → `ToDictionary` кидає `ArgumentException` → **500 на `/tasks/day`, `/period`, `/preview`** одразу (весь календар мертвий). Плюс криві патерни (`"abc"`, overflow дат) → 500.
**Корінь:** `server/Services/TaskService.cs:187,211`.
**Як виправити:**
- Замість `ToDictionary` — групування з детермінованим вибором (останній/перший виняток на дату виграє), або унікальний індекс `(RecurrenceRuleId, Date)` в БД + валідація при створенні винятку (дубль → 400).
- Розгортання правил обгорнути валідацією вхідних полів (див. P1-4): криві `MonthDays`/патерни → 400, не 500.
**Перевірка:** `poc/03-calendar/01-duplicate-exception-500` → календар віддає дані (дубль відкинуто на вводі або злитий), не 500.

## P1-4. Валідація полів повторення (спільний `/api/tasks/period`)  _(вкладки 09, 11, 03)_

**Що зламано:** криві `MonthDays` (`"abc,99"`) і overflow дат (`9999-12-20` + `AddDays`) → **500 на спільних `/api/tasks/period` та `/day`** — ламає не лише свій модуль, а календар усіх.
**Корінь:** `TaskService` (парсинг `MonthDays`, `DateOnly.AddDays`), `CycleController`/`CycleService`.
**Як виправити (за спекою `planner-spec.md §3.3`):**
- `MonthDays` — парсити в список `int`, кожне значення **1–31**, інакше 400. Порожнє/сміття → 400.
- `CycleWeeks` 1–4; `IntervalDays` ≥ 1 і з розумною стелею; `MonthDayMode` — з allowlist.
- `EndDate` — **обмежити одним роком** від `StartDate` (спека: «Термін дії правила обмежений одним роком»). Це ж автоматично знімає overflow-арифметику дат.
- Усі дати валідувати в допустимому вікні (спека §3.3: назад 90 днів, вперед ≤ 1 рік) перед арифметикою.
**Перевірка:** `poc/09-study/*MonthDays*`, `poc/11-cycle/*overflow*` → **400** з поясненням, календар живий.

## P1-5. Обмежити розгортання повторень (ресурсне виснаження)  _(вкладки 10, 03)_

**Що зламано:** один 100-річний recurrence-запит розгортається в **73 052 входжень** in-memory; `/period` без ліміту діапазону віддає ~3 МБ.
**Чому це проти спеки:** `planner-spec.md §3.3` — «Завдання за правилами не зберігаються в базі, а розгортаються **під час показу обраного інтервалу**… не на роки вперед» (пор. coding-guide §8).
**Як виправити:**
- `EndDate ≤ StartDate + 1 рік` (той самий кап, що в P1-4) — усуває 100-річні правила в корені.
- `/period`: обмежити довжину запитуваного діапазону (напр., ≤ 366 днів) → інакше 400. Розгортати тільки запитаний інтервал, не весь період дії правила.
**Перевірка:** `poc/10-work/*recurrence*`, `poc/03-calendar/*period*` → діапазон за межею → 400; кількість входжень обмежена вікном.

## P1-6. Цикл: валідація періодів + GET не мутує  _(вкладка 11; частина S9)_

**Що зламано:** `end < start` і вкладені періоди приймаються; **GET `/api/cycle` пише в БД при читанні**; overflow дат → 500 на кожному GET.
**Корінь:** `CycleController.cs:16`, `CycleService`.
**Як виправити:**
- Валідація `CycleRecord`: `EndDate ≥ StartDate` (або `null`), заборонити перекриття/вкладеність періодів → 400.
- **Прибрати запис із GET** — читання не повинно мутувати (див. P2-3). Будь-яке авто-створення/міграцію винести в явний POST або в момент реєстрації.
- Overflow дат закрити валідацією вікна (P1-4).
**Перевірка:** `poc/11-cycle/*` → криві періоди 400; повторний GET не змінює рядки в БД.

## P1-7. Фінанси/Покупки: подвійний облік і «розмазування» чека  _(вкладка 05)_

**Що зламано:** позиції чека рахуються разом із загальним чеком → витрати подвоюються (400 замість 300); при позначці чек «розмазується» на всю історію раніше позначених позицій; `-500` як ціна → стає доходом; `1e16` → 500.
**Чому це проти спеки:** `planner-spec.md §4.8/§3.6` — відмітка позиції **один раз** закриває її, поповнює запаси й **один раз** списує гроші («один жест — кілька ефектів», але не подвійний облік).
**Корінь:** `server/Services/ShoppingService.cs:194`.
**Як виправити:**
- Один чіткий інваріант: сума транзакції формується **або** з позицій, **або** з загального поля — не обидва. Прибрати подвійне додавання.
- Прив'язати списання до **конкретної відмітки конкретної позиції** (idempotency: повторна відмітка не створює другу транзакцію; зняття відмітки — відкочує). Не чіпати історію раніше позначених.
- Валідація ціни: `EstimatedPrice ≥ 0`, розумна стеля; `decimal(18,2)` вже є — додати межі діапазону (інакше 400, не 500).
**Перевірка:** `poc/05-shopping/*double-count*`, `*price*` → підсумок = реальна сума один раз; негативна/величезна ціна → 400.

## P1-8. Їжа: IDOR на запаси та витік заборонених рецептів  _(вкладка 06)_

**Що зламано:** користувач B тягне приватний продукт користувача A (IDOR на запаси); **заборонені правилами рецепти «течуть» разом з інгредієнтами** — hard-hide лише клієнтський.
**Чому це критично для диплому:** п.9 спеки («що захищається») — RuleEngine на тегах і міжмодульні зв'язки через правила. Якщо заборона — лише клієнтська, уся теза про «одну точку перевірки» (spec §2.3) спростована.
**Корінь:** `server/Services/RecipeService.cs:124`.
**Як виправити:**
- Усі запити до `StockItem`/`Product` скоупити за `UserId` (і дозволяти системні `IsSystem=true`); чужий `productId` → 404. Рівно як уже зроблено в інших модулях (звіт підтвердив, що per-record IDOR там закритий — узяти той самий патерн).
- **Фільтрацію заборонених (`Forbidden`) рецептів робити на сервері** через RuleEngine (пересічення тегів інгредієнтів із забороненими тегами юзера), а не ховати в UI. Сервер не повертає заборонені рецепти в стрічці зовсім (spec §4.6: «блюда с нехваткой/запретом не показываются вообще»).
**Перевірка:** `poc/06-food/*idor*` → чужий продукт 404; `*forbidden-recipe*` → заборонений рецепт відсутній у відповіді API, не лише прихований.

## P1-9. Здоров'я: мед-дані відкритим текстом + самостійне розблокування модулів  _(вкладка 07)_

**Що зламано:** діагнози/ліки/нотатки лежать у MySQL відкритим текстом (без шифрування/аудиту); mass-assignment профілю дозволяє юзеру виставити собі `StudentType/IsWorking` і **самому розблокувати модулі**.
**Як виправити:**
- **Mass-assignment (робити зараз, просто):** прибрати `StudentType`, `IsWorking`, `Gender` з DTO, що біндиться у профільних/health-ендпойнтах. Зміна цих полів — лише через контрольований шлях (і вона напряму зав'язана на гейтинг P0-2). Це закриває самостійне розблокування.
- **Шифрування мед-даних (окремий, більший крок):** для диплома достатньо (а) обмежити доступ лише власнику (вже є через `[Authorize]`+скоуп), (б) задокументувати в тексті роботи, що чутливі поля — кандидати на шифрування на рівні стовпця/БД. Повноцінне шифрування стовпців — опційне покращення; відзначити як свідому межу (пор. `sections/03-ukrainian-law-compliance.md`).
**Перевірка:** `poc/07-health/*mass-assign*` → спроба виставити `IsWorking:true` через профіль ігнорується; Робота лишається 403 (P0-2).

## P1-10. Налаштування: зміна статі/статусу не має обнуляти дані; експорт під ре-авторизацією  _(вкладка 13)_

# 🟨 P2 — Валідація, ліміти, напіввідкриті вектори

## P2-1. Відкликання токена і коротший час життя  _(S4)_
**Зламано:** токен живе 90 днів, без `jti`, logout лише в localStorage — вкрадений/старий токен чинний місяцями.
**Як (просто):** скоротити час життя access-токена (напр., 1–7 днів); додати до `UserProfile` поле `TokenVersion` (int) — у claim токена кладеться поточна версія, при logout/зміні пароля/видаленні акаунта версія інкрементується, а валідація відкидає токени зі старою версією. Це простіше за повноцінний refresh+blocklist і достатньо для диплома. `Корінь: JwtService.cs:34`, `App.jsx:115`.
**Перевірка:** `poc/14-system/03`, `poc/13-settings/*deleted-account*` → токен після logout/видалення → 401, не 500.

## P2-2. Серверні ліміти довжини на всіх текстових полях  _(S8)_
**Зламано:** зберігається 8 КБ–200 КБ сміття (назви, нотатки, категорії, color — часто `longtext`).
**Як:** додати `[MaxLength(n)]` на поля DTO/моделі (title ~200, description/нотатки ~5–10 КБ, назви ~100, color ~32) + відповідні довжини стовпців у міграції. Перевищення → 400. Проста атрибутна валідація.
**Перевірка:** PoC зі «сміттям» по кожній вкладці → 400.

## P2-3. GET-ендпойнти не повинні мутувати  _(S9)_
**Зламано:** `CycleController` GET пише (закрито в P1-6), `WorkController /settings`, повторне додавання в Food shopping — неідемпотентні.
**Як:** будь-яка мутація — тільки `POST/PUT/PATCH/DELETE`. Авто-ініціалізацію (створення дефолтних settings) робити при реєстрації або ліниво через окремий POST, не в GET.
**Перевірка:** `poc/10,11,06/*get-writes*` → повторний GET не змінює БД.

## P2-4. Нотатки: валідація кольору (CSS-ін'єкція)  _(вкладка 12)_
**Зламано:** довільний рядок у `color` (напр. `url(https://evil/..)`) зберігається й підставляється в `style={{background:note.color}}` → зовнішній fetch/beacon на рендері.
**Корінь:** `client/src/components/.../Notes.jsx:77` + `color` як `longtext` без ліміту на сервері.
**Як:** на сервері валідувати `color` за allowlist/патерном (`#RRGGBB` або один із пастельних токенів теми з coding-guide §5). Не-колір → 400. Ліміт довжини (P2-2). На фронті підставляти лише валідований колір.
**Перевірка:** `poc/12-notes/*css-injection*` → `url(...)` відхилено (400), на рендері немає зовнішнього запиту.

## P2-5. Фінанси: allowlist категорій, прив'язка балансу до реєстру  _(вкладка 08)_
**Зламано:** категорія без allowlist (`<script>`, 300 символів, emoji → «сироти» поза UI); баланс відв'язаний від транзакцій, але керує бюджетом Їжі/Покупок; `OccurredAt` керується клієнтом (backdate 1900/2099); `stats?year=0/-1/10000` → 500.
**Як:** категорії — фіксований серверний enum/allowlist (spec §3.6 — усе вручну, але набір категорій скінченний); `year` у stats валідувати діапазоном (напр. 2000–поточний+1) → 400 не 500; `OccurredAt` обмежити розумним вікном; баланс рахувати/звіряти з сумою транзакцій (або чітко задокументувати, що `FinanceAccount.Balance` — ручне поле, spec §3.6, і не давати від'ємних/абсурдних значень).
**Перевірка:** `poc/08-finance/01-stats-year-dos`, `*category*` → 400; категорія поза allowlist відхилена.

## P2-6. Реєстрація/вхід: rate-limit, lockout, без енумерації  _(вкладка 01)_
**Зламано:** 6-значний код брутфорситься (~102 реєстр/с, без lockout, 5 кодів чинні одночасно); енумерація акаунтів (`send-code` 400 `email_taken` vs 200); Gmail-alias обходить квоту; bcrypt 72-byte колізія.
**Як (просто):**
- **Код:** один чинний код на email (новий інвалідовує старі), ліміт спроб вводу (напр. 5 → інвалідувати код), rate-limit на `send-code`/`register`/`login` за IP+email (вбудований `AddRateLimiter` в ASP.NET, без пакетів).
- **Енумерація:** `send-code` і `login` повертати **однакову нейтральну відповідь** незалежно від того, існує email чи ні («якщо email є — надіслали код»).
- **Gmail-alias:** нормалізувати email (прибрати `+suffix` і крапки для gmail) перед перевіркою унікальності/квоти.
- **bcrypt 72 байти:** обмежити довжину пароля на вводі (напр. 8–64 символи) — закриває колізію усічення.
**Перевірка:** `poc/01-auth/*bruteforce*`, `*enumeration*`, `*gmail-alias*` → lockout спрацьовує; відповіді не розрізняють існування акаунта; аліаси не множать квоту.

## P2-7. Quick Add: TOCTOU у лічильнику безкоштовних спроб  _(вкладка 02)_
**Зламано:** 12 паралельних `consume` → 8 пройшло при ліміті 3 (гонка).
**Корінь:** `server/Services/BillingService.cs:63`.
**Як:** інкремент лічильника — атомарно в одній транзакції з перевіркою (`UPDATE ... SET used = used+1 WHERE used < limit` і дивитись на кількість змінених рядків), або оптимістичний конкаренсі-токен EF. Без розподілених локів — достатньо однієї атомарної умови в БД.
**Перевірка:** `poc/02-quickadd/*toctou*` → при ліміті 3 рівно 3 проходять, решта 402/403.

## P2-8. Перегляд: осиротіле нагадування + гонка розкладу  _(вкладка 04)_
**Зламано:** при видаленні книги cascade не чистить `ReturnTaskId` → осиротіле нагадування про повернення; `/schedule` race (6 паралельних → 6 подій, 5 сиріт); минулі дати дедлайну приймаються.
**Корінь:** `server/Services/TaskService.cs:485`.
**Як:** FK з `ON DELETE SET NULL`/каскад або явне прибирання пов'язаної задачі при видаленні; створення return-задачі зробити ідемпотентним (унікальність на `(BookId)` або перевірка існування в транзакції); дедлайн у минулому → 400 (spec: дедлайни підсвічуються, але не в минулому для нових).
**Перевірка:** `poc/04-watchlist/*orphan*`, `*race*` → після видалення немає осиротілих задач; паралельні запити дають одну задачу.

## P2-9. Покупки: спам plan-trip і автокатегоризація  _(вкладка 05)_
**Зламано:** 5 кліків plan-trip → 5 задач-дублікатів; автокатегоризація «паста»→Гігієна (помилкові секції).

**Перевірка:** `poc/05-shopping/*plan-trip-spam*` → повторний клік не плодить задачі.

## P2-10. Робота/оцінки: серверні інваріанти розкладу і сум  _(вкладки 10, 09)_
**Зламано:** розклад max-5/overlap/унікальність — лише клієнт; дохід без стелі (1e9); clamp оцінок залежить від `StudentType`.

# Порядок виконання (фази)

1. **Фаза 0 — Безпека-фундамент (P0-1…P0-3).** Без неї решта безглузда. Після неї: підробка токена неможлива, модулі гейтяться, пейвол не обходиться. Перезапустити `poc/01`, `poc/09-11/01`, `poc/02`, `poc/14` — мають стати 401/403/400.
2. **Фаза 1 — Стабільність і цілісність (P1-1…P1-10).** Прибрати self-DoS (500→400/401), подвійний облік грошей, IDOR їжі, втрату даних профілю. Спільний helper userId (P1-1) і глобальний обробник (P1-2) зробити **першими в фазі** — вони зачіпають усі контролери.
3. **Фаза 2 — Валідація і ліміти (P2-1…P2-10).** Відкликання токена, ліміти довжини, allowlist-и, rate-limit, ідемпотентність.
4. **Фаза 3 — Якість (P3).** Продуктивність, a11y, мертвий код, i18n.

Між фазами — прогін усіх PoC відповідної вкладки (`for f in NN-*/*.mjs; do node "$f"; done`): кожен має перемкнутися з `CONFIRMED` на `REFUTED`/очікувану відмову (401/403/400). Це і є критерій «виправлено».
