# Adversarial review — Здоров'я

> Обсяг: `client/src/pages/Health.jsx` (+ `Health.css`), `client/src/api/{medicineCabinet,healthProfile,checkup}.js`, `client/src/utils/validation.js`, серверні `MedicineCabinetController` / `HealthProfileController` / `CheckupController`, сервіси `MedicineService` / `CheckupService`, моделі `Medicine`/`UserMedicine`/`UserCondition`/`UserProfile`/`HealthVisit`, довідники ДРЛЗ (`Medicine`/`Substance`/`MedicineForm`) та DDInter (`SubstanceInteraction`).
>
> Легенда пріоритетів: 🔴 критично · 🟠 суттєво · 🟡 помірно · 🔵 дрібниця/UX.

## 1. Фронтенд — сторінка, профіль-шапка, вкладки Аптечка/Хвороби/Чекап, логіка

- 🟠 **Оптимістичні оновлення без відкату.** `handleMedState` спершу змінює стан у `setMedicines`, а потім `await apiSetMedicineState`. Якщо сервер поверне помилку (мережа/404), UI вже показує новий стан — жодного revert чи повідомлення немає. Користувач бачить «Немає», а в БД лишилося «Є». Те саме у `cancelVisit` (фільтрує локально) і в `handleAddCondition`.
- 🟠 **`window.confirm` для «Закінчується → покупки».** Блокуючий нативний діалог (`t('health.lowAddConfirm')`) ламає UX SPA, не стилізується, не локалізується поза текстом, не тестується e2e. Якщо користувач натискає три-стан швидко (клік на жовтому колі кілька разів) — на кожен клік окремий `confirm`.
- 🟠 **`inShopping` протухає.** Множина `inShopping` будується один раз при завантаженні зі `getShoppingList`. Якщо користувач видалив ліки зі списку покупок у вкладці «Покупки» і повернувся — тут вони все ще «вже додані», тож повторний confirm не з'явиться, поки не перезавантажити сторінку. Зворотний бік: додавання в іншій вкладці теж не відобразиться.
- 🟡 **`tab` стартує з `'meds'`, а коментар каже `'meds' | 'cond'`** — третій стан `'checkup'` з'явився пізніше, коментар на рядку 49 застарів. Немає нормалізації: якщо `tab` колись задати іншим значенням, рендериться гілка `else` (чекап) мовчки.
- 🟡 **Візити вантажаться окремим `useEffect` від основного `Promise.all`.** Два незалежні завантаження → на екрані «Завантаження…» (основний `loading`) не враховує стан візитів; лічильник вкладки «Чекап» може стрибнути з 0 на N після того, як решта вже відмальована.
- 🟡 **`openSchedule` скидає форму щоразу.** Якщо користувач почав заповнювати візит до одного лікаря й натиснув «Запланувати візит» біля іншого — введене пропадає без попередження (форма одна на всю сторінку, `schedKey` перемикається).
- 🔵 **`reloadCabinet` дублює логіку завантаження взаємодій** з основного `useEffect` (той самий `Promise.all(meds.map(getInteractions))`). Дублювання коду + подвійний N+1 (див. §11).
- 🔵 **Сортування «За наявністю» ставить `RunningLow` першим, потім `Available`, потім `OutOfStock`.** Це нетипове очікування (зазвичай «немає» або «є» зверху); навмисно підсвічує «скоро закінчиться», але без підказки користувачу це виглядає як баг сортування.

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, таблиці, модалка візиту

- 🟠 **Таблиця ліків — `table.data-table` у `.table-scroll`.** На вузькому екрані 5 колонок (Назва/Категорія/Речовина/Стан/Взаємодії) не влазять; горизонтальний скрол — єдиний порятунок. Перевірити, що `.table-scroll` справді `overflow-x:auto`, а не ріже контент. Колонка «Взаємодії» з багатьма тегами може розпирати рядок по висоті непередбачувано.
- 🟠 **Модалка візиту (`checkup-modal`) — `onClick` на бекдропі закриває без підтвердження.** Випадковий клік повз модалку → введені дата/час/місце/нотатка втрачаються. Немає `Esc`-обробника взагалі (ні закриття, ні фокус-пастки — див. §5).
- 🟡 **Світла/темна тема.** У `Health.css` 168 згадок `var(--…)`/`@media` — тема начебто через CSS-змінні. Треба перевірити, що кольори три-ступеневого перемикача (`stock-circle--ok/warn/bad`) і бейджів правил (`rule-badge--warn/bad`, `conflict-tag--major/moderate/minor/unknown`) мають достатній контраст у **обох** темах, а не лише у світлій (зелений/жовтий/червоний на темному тлі часто провалюють контраст).
- 🟡 **Числові поля профілю стилізовані «під текст» (`profile-field-input`).** Нативні стрілки `type=number` та одиниця (`кг`/`років`/`см`) поруч можуть накладатися; на мобільному `inputMode` заданий, але ширина поля під «—» placeholder може зрізати трицифрові значення (напр. зріст 185).
- 🔵 **`conflict-tag--${(it.level||'unknown').toLowerCase()}`** — якщо DDInter колись віддасть level в іншому регістрі/написанні (напр. `High`), клас стане `conflict-tag--high`, для якого стилю немає → тег без кольору. Жодного fallback-стилю на невідомий клас.

## 3. Фронтенд — валідація вводу (вага/вік/зріст clamp), стани

- 🟠 **Клампінг «мовчки».** `saveProfile` через `clampNumber` тихо обрізає 600 кг → 500, 0 → 1, -5 → 1 і одразу переписує поле (`setWeightInput(String(weight))`). Користувач не отримує пояснення, чому його «600» стало «500». Виглядає як баг вводу. Потрібне повідомлення/підказка меж.
- 🟡 **`clampNumber` і нескінченність/наукова нотація.** `type=number` приймає `1e999` → `Number('1e999') = Infinity` → `Math.min(500, Math.max(1, Infinity)) = 500`. Працює, але побічно: `'1e3'` стане 500 без натяку, що введено 1000. Для віку `Math.round(clamp(...))` — `1e999`→120.
- 🟡 **Вік ↔ рік народження — втрата точності.** `age → birthYear = currentYear - age`, назад `age = currentYear - birthYear`. Зберігається лише рік, тож вік округлюється до року (±1 залежно від місяця народження). Наступного календарного року той самий `birthYear` покаже вік на 1 більший, хоча користувач нічого не міняв — це «правильно», але для «естетичного» поля може спантеличити. Також мінімальний серверний `birthYear = nowYear-1` дасть вік 1, а не 0.
- 🟡 **Порожнє поле = `null`.** `empty(s) → null` стирає значення в профілі. Якщо користувач випадково виділив і видалив вагу й зняв фокус — вага обнулиться на сервері без підтвердження.
- 🔵 **`currentYear` у `useEffect`-залежностях** (`[profile, currentYear]`) — `currentYear` рахується з `new Date()` при кожному рендері, але значення стабільне в межах сесії; залежність зайва, хоча й нешкідлива.

## 4. Інтернаціоналізація (i18n) — назви ліків/лікарів/форм, невикористані ключі

- 🟡 **Мертві ключі.** У `uk.json`/`en.json` присутні, але **ніде не рендеряться**:
  - `health.col.expiry` / `health.expiryPrefix` — колонки «Термін» у таблиці немає (модель `UserMedicine.ExpiresAt` існує, у коментарі прямо «без окремої колонки Термін»). Поле протягується через API (`setMedicineState(..., m.expiresAt)`), але **задати його з UI неможливо** — напівреалізована фіча.
  - `health.addMedTitle` — панель додавання використовує `health.addMed`, заголовок не виводиться.
  - `checkup.primary` («основний»/«primary») — сімейний лікар виділяється лише CSS-класом `checkup-row--primary`, текстовий бейдж не рендериться.
- 🟡 **Реюз чужих неймспейсів.** Сортування ліків бере ключі `food.sortBy` / `food.sort.default|alpha|availability`, а підписи три-стану — `food.state.Available|RunningLow|OutOfStock`. Якщо колись розведуть «Їжу» і «Здоров'я» за змістом (напр. «availability» для ліків vs продуктів), тексти поїдуть разом. Прихована зв'язність.
- 🟡 **Назви ліків/речовин не перекладаються по-справжньому.** `NameEn`/`SubstanceEn` у довіднику імпортуються з ДРЛЗ/DDInter; для багатьох рядків `NameEn` — це транслітерація або копія укр. `conditionName` взагалі фолбечить `c.nameEn || c.nameUk`, а `AddConditionAsync` пише `NameEn = nameUk.Trim()` (той самий укр. текст!). Тож в англ. інтерфейсі захворювання показуються українською — i18n-дірка на рівні даних.
- 🔵 **Тег у підказці показується «навпаки» між мовами** (`pickTag`, рендер `cond-tag-suggestion`): для `en` показуємо `s.key`, для `uk` — `s.displayName`. Для англ. користувача ключ `lactose` читабельний, але якщо `DisplayName` українською, а `Key` латиницею — у списку хвороб `tagKey` показується англ. завжди (рядок 636), що для укр. UI неконсистентно з формою.

## 5. Доступність (a11y): триступеневий перемикач стану, пошук, модалка

- 🟠 **Три-стан = три `<button>` лише з `title`.** `stock-circle` не має ні тексту, ні `aria-label`, ні `aria-pressed`, ні `role="radiogroup"`. Скрінрідер озвучить «кнопка» × 3 без сенсу; `title` читається ненадійно. Активний стан передається лише класом `--on` (візуально), не семантично. Потрібні `aria-label`+`aria-pressed`/`role=radio aria-checked`.
- 🟠 **Модалка візиту без фокус-пастки й `Esc`.** `checkup-modal` не переводить фокус усередину, не повертає його назад, не замикає Tab, не має `role="dialog"`/`aria-modal`/`aria-labelledby`. Закриття лише кліком по бекдропу або кнопкою — клавіатурнику важко.
- 🟡 **Пошук препарату/тегів без ARIA-комбобокса.** `med-search-results`/`cond-tag-suggestions` — звичайні `<ul>`, без `role="listbox"`/`aria-activedescendant`, без навігації стрілками. Лише миша. `autoFocus` на полі пошуку може дезорієнтувати при відкритті панелі.
- 🟡 **Повідомлення про невідомий тег / порожні стани** не мають `role="status"`/`aria-live` — зміна (напр. поява `tag-unknown-notice` після додавання) не оголошується.
- 🔵 **Кнопки-іконки «скасувати візит»/«видалити хворобу»** мають `aria-label`, добре; але `data-tooltip` як єдиний візуальний підпис залежить від CSS `::after` — для touch недоступний.

## 6. Бекенд — API, статус-коди, валідація

- 🟠 **`CheckupController.AddVisit` не валідує `DoctorKey` проти переліку.** Перевіряється лише `IsNullOrWhiteSpace`. Будь-який рядок (`"xyz"`, емодзі, 10 КБ тексту) приймається, зберігається і **створює подію календаря**. Оскільки фронт показує лише 16 відомих ключів (`CHECKUP_DOCTORS`), візит із чужим ключем стає «сиротою»: подія в календарі є, а в розділі «Чекап» його не видно → **скасувати з UI Health неможливо** (див. §9).
- 🟠 **Немає серверних обмежень довжини** (див. §10) на `Place`/`Note`/`DoctorKey`/`DoctorName`/`NameUk`/тег. `MAX_LEN` живе лише на клієнті (`maxLength`, `limitText`, `filterWords`). Прямий запит в обхід UI пише як завгодно довгі значення.
- 🟡 **`AddConditionRequest.Relation`/`AddVisit` не перевіряють enum на вході контролера.** `Relation` нормалізується в сервісі (`== "Forbidden" ? "Forbidden" : "Avoid"`) — безпечно, але мовчки: надіслане `"Prefer"` чи сміття стане `Avoid` без помилки. `UpdateMedicineRequest.State` валідується лише в `UpdateCabinetAsync` (повертає `false`→404 замість 400 Bad Request).
- 🟡 **Невідповідність статус-кодів.** Невалідний `State` → `UpdateCabinetAsync` повертає `false` → контролер віддає **404 NotFound** (а мало б 400). Так само `AddToCabinetAsync` на неіснуючі ліки → 404, а на вже додані → 200 (ідемпотентно, але клієнт не відрізнить «додав» від «вже був»).
- 🟡 **`CurrentUserId => int.Parse(User.FindFirst(Sub)!.Value)`** з null-forgiving. Якщо токен без claim `sub` (теоретично) — `NullReferenceException` → **500**, а не 401. Повторюється в усіх трьох контролерах.
- 🔵 **`AddCondition` повертає `200 Ok` з тілом `ConditionDto`**, а `AddVisit` — `{ id }`. Непослідовність форматів відповіді між ендпоінтами розділу.

## 7. Авторизація та власність (IDOR над чужою аптечкою/захворюваннями/візитами/профілем)

- 🟢 **IDOR не виявлено — усі запити скоуповані `CurrentUserId`.** Перевірено поіменно:
  - Аптечка: `GetCabinet/Update/Remove/GetInteractions` — скрізь `x.UserId == userId && x.MedicineId == medicineId`.
  - Взаємодії: `GetInteractionsAsync` спершу вимагає, щоб `medicineId` **був у аптечці користувача** (`FirstOrDefaultAsync(x.UserId==userId && ...)`), інакше порожньо. Чужі/довільні id не зондуються.
  - Хвороби: `DeleteConditionAsync(... x.Id==conditionId && x.UserId==userId)`, `GetConditionsAsync(Where UserId)`.
  - Візити: `GetVisitsAsync/DeleteVisitAsync` — `x.UserId == userId`.
  - Профіль/обмеження: `UserProfiles.FindAsync(CurrentUserId)` (PK = UserId), `UserTagPreferences.Where(UserId)`.
- 🟠 **Мас-ассайнмент на `/api/health-profile` PUT.** `UpdateHealthProfileRequest` біндить ще й `StudentType` та `IsWorking`, яких на сторінці «Здоров'я» немає (їх задають у Налаштуваннях). Клієнт Health шле лише 4 поля, але **ендпоінт приймає всі 6**. Користувач прямим запитом може змінити власний `StudentType`/`IsWorking` і так відкрити собі розділи «Навчання»/«Робота» в обхід UI налаштувань. Це маніпуляція **власними** даними (не чужими) — не витік, але перемішані відповідальності: косметичний профіль і module-gating поля ділять один незахищений ендпоінт.
- 🟡 **`DeleteVisitAsync` викликає `_taskService.DeleteTaskAsync(userId, taskId, cascadeSource:false)`** — добре, що передає `userId` (тобто TaskService теж має перевіряти власність задачі). Варто підтвердити, що TaskService не видаляє чужу задачу за самим `taskId`.

## 8. Безпека (XSS у назвах захворювань/нотатках візиту, масове призначення)

- 🟢 **XSS у React-рендері — немає.** Назви хвороб, теги, нотатки/місця візитів виводяться як текстові вузли (`{conditionName(...)}`, `{v.place}`, `title={it.mechanism}`). `dangerouslySetInnerHTML` у розділі не використовується. React екранує за замовчуванням.
- 🟠 **Stored-поле йде в календар.** `CheckupService.AddVisitAsync` будує `title = "Візит: {doctorName}"` і `description = "{place} · {note}"` з клієнтських даних і **зберігає як задачу** (`moduleCode="health"`). `doctorName` береться з клієнта **as-is** (сервер не звіряє, що він відповідає `doctorKey`) — тобто заголовок події повністю контролює клієнт. Якщо будь-де календар/експорт (iCal, email-нагадування, PDF) рендерить ці рядки **без екранування** — це збережений вектор. У самому React-календарі безпечно, але поверхню треба перевірити в модулі календаря/нагадувань.
- 🟠 **Немає серверної санітизації/обмеження на ці рядки** (довжина — §10). `Note`/`Place`/`DoctorName` можуть містити `\n`, керуючі символи, дуже довгий текст — це потрапляє в заголовок/опис задачі.
- 🟡 **`Gender` приймається без enum-перевірки** (`if (!IsNullOrWhiteSpace) profile.Gender = request.Gender`) — будь-який рядок. Див. §9 щодо наслідків для «Циклу».
- 🔵 **Тег алергену створюється на льоту** (`Namespace="allergen"`, `Key=norm`) і з форми хвороби, і з `/restrictions`. Користувач може засмічувати таблицю `Tags` довільними ключами (спам-запис у глобальну таблицю, хоч і прив'язаний через `UserTagPreference` лише до себе). Немає дедуплікації регістру на рівні БД (робиться в пам'яті).

## 9. Бізнес-логіка та інваріанти

- 🟢 **Взаємодії лише між наявними ліками.** `GetInteractionsAsync` будує `medBySubstance` **виключно з аптечки користувача** (`UserMedicines.Where(UserId && MedicineId != self)`) і фільтрує `SubstanceInteractions` по `otherIds`, що містяться в аптечці. Жодна пара з довідника, де друга речовина **не** в аптечці, не повертається — зайвого не витікає. Обидва напрямки (A-B/B-A) враховано. Комбіновані засоби (`SubstanceId == null`) взаємодій не дають — коректно.
- 🟠 **Невідповідність джерела даних і дисклеймера.** DDInter — довідкові дані (CC BY-NC-SA, `Source="DDInter"`); рівні `Major/Moderate/Minor/Unknown`. Дисклеймер «Дані довідкові…» є лише у вкладці «Аптечка» під таблицею. Повідомлення `health.noConflicts` = «у базі не знайдено взаємодій» (не «конфліктів немає») — коректно обережне формулювання, але для **комбінованих** ліків показується `health.notSubstance` «комбінований засіб», що користувач може сприйняти як «безпечно». Потрібно, щоб обережність була і там.
- 🟠 **Невідомий тег хвороби → не фільтрує, але попередження крихке.** `AddConditionAsync` зберігає хворобу навіть з «вигаданим» тегом; `tagKknown = ProductTags.AnyAsync(TagId)`. Клієнт показує `tagNotice`/`tagUnknownBadge` **лише** якщо `created.tagKnown === false`. Проблема: тег вважається «відомим» тільки якщо стоїть **хоч на одному продукті** — якщо продукти з цим тегом з'являться/зникнуть пізніше, статус `tagKnown` не перераховується на старих записах до наступного `getConditions`. Також: правило вже записане в `UserTagPreference` і **фільтруватиме їжу**, навіть поки тег «невідомий» порожній — інваріант «невідомий тег не фільтрує» тримається лише тому, що фільтрувати нема чого (немає продуктів із тегом), а не завдяки явній перевірці.
- 🟠 **«Впливає на їжу» без тега — тихе зниження.** Якщо користувач увімкнув перемикач, але не ввів тег, `AddConditionAsync` робить `AffectsFood = affectsFood && tagId != null` → `false`. Хвороба зберігається як «не впливає на їжу» **без будь-якого попередження**, попри увімкнений перемикач. Користувач думає, що налаштував фільтр.
- 🟠 **Рік народження ↔ вік.** Клієнт: `birthYear = currentYear - age`. Сервер додатково клампить `birthYear` у `[nowYear-120, nowYear-1]`. Подвійний кламп узгоджений, але якщо колись розійдуться межі `RANGES.age` (1..120) і серверні (120/1) — виникне «мертва зона», де клієнт показує одне, сервер зберігає інше. Зараз збігаються.
- 🟠 **«Закінчується» → покупки, секція «Аптека».** `handleMedState('RunningLow')` пропонує `addShoppingItem({ section:'Pharmacy', medicineId })`. Інваріант «тільки якщо ще не в списку» тримається на клієнтському `inShopping` (протухає, §1). Повторний перехід OutOfStock→RunningLow після видалення зі списку може не запропонувати додати. Також: при `OutOfStock` (червоний) — **нічого** не пропонується, хоча «немає» — найсильніший сигнал купити; логіка прив'язана лише до жовтого.
- 🟡 **Сімейний лікар завжди перший** — забезпечено статичним масивом `CHECKUP_DOCTORS[0]='family'` + клас `--primary`. Інваріант тримається, але він **суто фронтовий**: якщо візит прийшов з `doctorKey='family'`, усе гаразд; порядок не залежить від даних — ок.
- 🟠 **Планування візиту ↔ подія календаря (синхронізація/скасування).**
  - Створення: `AddVisitAsync` зберігає `HealthVisit`, потім створює задачу, потім пише `visit.TaskId`. Якщо `CreateTaskAsync` впаде між цими кроками — лишиться візит без `TaskId` (нема події в календарі), і повторно прив'язати нічим.
  - Скасування: видаляє задачу (`cascadeSource:false`) і сам візит. Якщо задачу вже видалили з календаря напряму — `visit.TaskId` вказує в нікуди; `DeleteTaskAsync` має це пережити (перевірити).
  - **Редагування візиту не підтримано** — щоб змінити час, треба скасувати й створити заново (подія календаря теж перестворюється з новим id).
  - **Візит із невідомим `doctorKey`** (див. §6) створює подію, але не показується в «Чекап» → подію можна скасувати лише з календаря, не з Health. Розсинхрон UI.

## 10. Дані, межі (реалістичність, RANGES), приватність медичних даних, Unicode

- 🔴 **Приватність медичних даних — зберігання у відкритому вигляді.** Найчутливіші дані розділу (діагнози/`UserCondition.NameUk`, перелік ліків `UserMedicine`, візити з нотатками `HealthVisit.Note/Place`, стать, вага/зріст/вік) зберігаються в MySQL **звичайними колонками без шифрування на рівні полів**. Немає ознак at-rest-шифрування специфічно для цих таблиць, маскування чи аудиту доступу. Для диплома це варто принаймні задокументувати як свідоме рішення + покладання на шифрування диска/TLS; інакше — компрометація БД = розкриття медичної історії.
- 🟠 **Логування.** Треба переконатися, що `Note`/`Place`/назви хвороб/ліків **не потрапляють у логи** (напр. при 500-й помилці серіалізації запиту, у middleware, у логах EF із параметрами). Чутливі поля в логах — типовий витік. Код логування в розділі не видно — перевірити глобальний pipeline.
- 🟠 **Відсутні серверні `MAX_LEN`.** Жодна з моделей (`UserCondition.NameUk`, `HealthVisit.Place/Note/DoctorKey`, `Tag.Key/DisplayName`) не має `[MaxLength]`/конфігурації довжини в наведеному коді. Клієнтські `MAX_LEN.name=60` / `MAX_LEN.description=200` — лише UX. Прямий API-запит пише рядки довільної довжини (обмежені хіба типом колонки MySQL за замовчуванням). Ризик: роздування БД, обрізання посеред UTF-8 на рівні драйвера, DoS.
- 🟡 **Реалістичні межі.** `RANGES` (вага 1..500 кг, зріст 30..300 см, вік 1..120) продубльовані на сервері (`Math.Clamp` у `HealthProfileController`) — добре, подвійний захист. Але межі жорсткі: немовля <1 року (вік 0) неможливе; зріст <30 см — ок. Для «естетичного» профілю прийнятно.
- 🟡 **Unicode/скрипт-детект у пошуку.** `DetectScript` вважає «кирилицею» діапазон `Ѐ..ӿ`, «латиницею» — лише `a..z` (малі!). Великі латинські літери `A..Z` **не** позначають `hasLatin` (запит у `ToLowerInvariant()` вже знижено, тож на практиці ок). Але: цифри, апострофи, дефіси ігноруються; **змішаний** укр+лат запит (напро «Корвалол L») → `null` → порожня видача без пояснення. Також назва ліків з латинськими вкрапленнями (бренди) може не знаходитись кириличним запитом.
- 🔵 **`filterWords` для тега** лишає `[A-Za-zА-ЯҐЄІЇа-яґєіїʼ' -]` і ріже до 40 символів — цифри/спецсимволи в назві алергену неможливі (напр. «Омега-3» втратить «3»). Для тегів продуктів здебільшого ок, але обмеження неочевидне.

## 11. Продуктивність і надійність (N+1 getInteractions, гонки, профіль на blur)

- 🔴 **N+1 на взаємодіях — і мережевий, і БД.** При завантаженні аптечки (`useEffect` та `reloadCabinet`) робиться `Promise.all(meds.map(m => getInteractions(m.medicineId)))` — тобто **окремий HTTP-запит на кожні ліки**. Кожен `GetInteractionsAsync` сам виконує 2–3 запити до БД (ліки+речовина, уся аптечка з Include, таблиця `SubstanceInteractions`). Для аптечки з N ліків це **N HTTP round-trip × ~3 SQL = ~3N запитів до БД**, причому **вся аптечка перечитується N разів** (кожен виклик тягне `UserMedicines.Where(UserId).Include(Medicine.Substance)` цілком). Для 30+ ліків — десятки запитів і сотні SQL. Це DoS-поверхня (будь-хто з великою аптечкою навантажує сервер) і повільний старт сторінки. **Правильно**: один ендпоінт, що повертає всі взаємодії аптечки за один прохід (матриця пар), одним SQL.
- 🟠 **Подвійне завантаження при додаванні ліків.** `handleAddMed` → `reloadCabinet` → знову весь N+1. Додав 3 ліки поспіль — тричі перегнав усю матрицю взаємодій.
- 🟠 **Пошук без debounce.** `handleMedSearch` і `handleTagSearch` б'ють у мережу на **кожне натискання** (від 2 символів). Серверний `SearchAsync` щоразу **витягує всі ~2038 рядків довідника** легкою проекцією і рахує триграмну схожість **у пам'яті** на кожен запит (`candidates = _db.Medicines.Where(!inCabinet).ToListAsync()` → LINQ-скоринг). Швидке друкування = десятки повних сканів таблиці. `SearchTagsAsync` так само тягне всі теги продуктів щоразу. Немає ні debounce на клієнті, ні кешу/повнотекстового індексу на сервері.
- 🟠 **Серверний пошук не має мінімальної довжини.** Клієнт відсікає `< 2` символи, але `SearchAsync`/`SearchTagsAsync` відсікають лише **порожній** рядок (`q.Length == 0`). Прямий запит `?q=а` (1 літера) запускає повний скан+скоринг 2038 рядків — дешева DoS-ін'єкція навантаження повз UI-обмеження.
- 🟠 **Профіль зберігається на кожен `onBlur`.** Три поля → до **3 окремих PUT** при проході Tab'ом по шапці, і кожен PUT шле **всі** поля (вага+зріст+вік+стать). Гонка: `saveProfile` читає `weightInput/heightInput/ageInput` із замикання на момент blur — встигле значення коректне, але `gender: profile?.gender` береться зі **стану `profile`**, який оновлюється асинхронно (`setProfile` у тому ж виклику) — за швидких послідовних blur є ризик надіслати застарілий gender. Також нема debounce/«брудного» прапорця: blur без змін теж шле PUT.
- 🟡 **`cancelled`-guard є лише в головному `useEffect`.** `reloadCabinet`, `submitVisit`, `handleAddCondition`, `getVisits()` у `cancelVisit`/`submitVisit` не мають захисту від оновлення стану після розмонтування — попередження React про setState на демонтованому компоненті + можливі гонки, якщо користувач швидко пішов зі сторінки.
- 🟡 **`submitVisit` робить `setVisits(await getVisits())` після POST** — зайвий round-trip (міг би додати повернутий `{id}` локально), подвоює навантаження на кожне планування.
- 🔵 **`forms`/`visibleMeds` у `useMemo`** залежать від `language` (через `medName(...).localeCompare`) — зміна мови перераховує сортування, ок; але `visibleMeds` не залежить від `interactions`, тож перемальовування взаємодій окремо — дрібна зайва робота. Некритично.

### Зведення найгостріших пунктів

1. 🔴 **N+1 завантаження взаємодій** (десятки HTTP + сотні SQL на велику аптечку) — DoS/продуктивність, §11.
2. 🔴 **Медичні дані у відкритому вигляді**, без шифрування полів/аудиту; ризик логування нотаток — §10.
3. 🟠 **Серверний пошук без min-довжини + без debounce** — повний скан довідника на кожен символ/прямий запит, §11.
4. 🟠 **Немає серверних обмежень довжини** на нотатки/місця/назви/ключі лікарів — §6/§10.
5. 🟠 **`DoctorKey`/`DoctorName` не валідуються** → події-сироти в календарі, які не скасувати з UI; клієнт контролює заголовок події — §6/§8/§9.
6. 🟠 **Мас-ассайнмент `StudentType`/`IsWorking` через health-profile PUT**; **`Gender` без enum** — §7/§8. Доступ до «Циклу» (`gender==='female'`) — **суто клієнтський** (`App.jsx` route), `CycleController` взагалі не перевіряє стать, лише `[Authorize]`+userId: підмінити «стать» тривіально, але це лише власні дані — не витік, проте «захист доступу» статтю є фіктивним.
7. 🟠 **Тихі зниження інваріантів**: «впливає на їжу» без тега → мовчки вимикається; кламп профілю без пояснення; невідомий тег все одно пише `UserTagPreference` — §3/§9.
