# Adversarial review — Робота

Огляд модуля «Робота»: `client/src/pages/Work.jsx`, `client/src/components/work/*`
(`ScheduleTab`, `ContactsTab`, `LeaveTab`, `MeetingsTab`, `ObligationsTab`,
`ProcessTab`, `workShared.js`), `client/src/api/work.js`, `client/src/utils/phone.js`,
`client/src/utils/recurrence.js` та серверних `WorkController.cs` + `WorkService.cs`
(+ `TaskService.cs` для правил повторення/подій календаря). Чек-лист навмисне «злий»:
кожен пункт — питання «а що як користувач/зловмисник зробить навпаки».

> Легенда серйозності: 🔴 критично (безпека/цілісність) · 🟠 суттєво · 🟡 помірно · ⚪ дрібно/косметика.

---

## 1. Фронтенд — сторінка, гейтинг isWorking, вкладки, логіка

- 🟠 **Гейтинг розділу суто клієнтський.** Видимість пункту меню — `Sidebar.jsx:32`
  (`item.key === 'nav.work' → Boolean(isWorking)`), редірект — `App.jsx:205`
  (`isWorking ? <Work/> : <Navigate to="/app" replace/>`). `isWorking` приходить із
  `GET /api/health-profile` і кешується у React-стані. Жодна серверна перевірка статусу
  в `WorkController` немає (див. §7) — тобто меню/маршрут лише ховають UI, дані доступні
  напряму через API без увімкненого «Працюю».
- 🟠 **Увесь розділ падає на одному збої header-запиту.** `Work.jsx:41-47` робить
  `Promise.all([getWorkSettings(), getNextShift()])`; будь-яка помилка (навіть тимчасовий
  502 на `next`) → `setError(true)` і весь розділ показує `common.error` замість того, щоб
  деградувати частково. `getNextShift` залежить від генерації правил на 120 днів — якщо
  вона впаде, уся «Робота» недоступна.
- 🟡 **`settings` може лишитись `null` і все одно рендеритись.** Якщо `getWorkSettings`
  повернув `null`/порожнечу без кидання помилки, `ScheduleTab` отримає `settings={null}` —
  `settings?.payType`/`settings?.rate` дадуть `earnings = null` (ок), але `saveWorkProfile`
  (`Work.jsx:56-71`) збере payload із дефолтами (`payType:'hourly'`, `regime:'standard'`…)
  і на blur **перезапише** реальні серверні налаштування дефолтами, якщо вони ще не
  підвантажились. Гонка «надрукував у заголовку швидше, ніж приїхали settings».
- 🟡 **`saveWorkProfile` викликається на кожен `onBlur` трьох полів** (назва/посада/
  роботодавець, `Work.jsx:102-105`). Три послідовні Tab'и = три PUT `/settings`, кожен
  тягне з собою весь профіль. Немає дебаунсу/дедуплікації; остання відповідь може прийти
  раніше за передостанню (гонка, див. §11).
- 🟡 **Вкладка — локальний стан без скидання.** `tab` дефолт `'schedule'`
  (`Work.jsx:23`); при зміні `isWorking` на `false` компонент демонтується (редірект), тож
  тут ок, але жодна вкладка не читається/не пишеться в URL — глибоке посилання на «Контакти»
  неможливе, F5 завжди повертає на «Графік».
- ⚪ **Іконки вкладок семантично дивні**: «Зустрічі» — `bell` (дзвіночок), «Відпустки й
  лікарняні» — `health`, «Планування процесу» — `board`. Косметика.

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, календар змін, канбан, drawer контактів

- 🟠 **Текст чипа зміни в календарі має жорстко зашитий колір `#243`** (`Work.css:303`,
  `.work-cal-chip { color: #243 }`) поверх користувацького `background: s.color`. Палітра
  `SHIFT_COLORS` — 8 світлих пастелей, тож на світлих фонах темний текст читається, але:
  (а) колір не реагує на тему — у темній темі чип лишається світлим прямокутником із темним
  текстом, вибиваючись зі стилю; (б) якщо колір приходить з API довільним (сервер його не
  валідує, див. §6/§8) — наприклад темно-синій — білого тексту немає, контраст провалюється.
- 🟡 **Модалки «Типи змін»/«Графік» — `overflow-y:auto` з фіксованою висотою** (`Work.css:254-266`).
  На низькому екрані форма типу (name+kind+4 поля часу+8 свотчів) скролиться всередині, а
  кнопка «Зберегти» та рядок помилки (`task-form-error`) опиняються нижче за згин — легко
  не помітити, чому «не зберігається».
- 🟡 **Адаптив майже не описаний**: єдиний `@media (max-width:600px)` (`Work.css:237`)
  чіпає лише `.work-cal-head`. Сітка календаря — `repeat(7, minmax(0,1fr))` (`Work.css:285`):
  на 320px клітинка ≈40px, чип зміни з назвою до 24 символів обрізається в еліпсис, по суті
  нечитабельний. `work-inline-form` (форма зустрічей із 4 полями) на мобільному стискається.
- 🟡 **Канбан процесу — просто `work-process-list`** (вертикальний список карток), не колонки;
  переміщення лише стрілками. Drag-and-drop немає (і не заявлений), але при багатьох задачах
  у «Планую» вкладка стає довгим скролом без групування за дедлайном усередині.
- 🟡 **Drawer контактів (`ContactsTab` 265-342) без блокування скролу body й без фокус-пастки.**
  `drawer-backdrop` закриває по кліку, але Escape не обробляється; за відкритого drawer можна
  і далі крутити список контактів позаду.
- ⚪ **`work-cal-day` має `overflow:hidden`** (`Work.css:297`) — при рівно 3 змінах третій
  чип може підрізатись по висоті клітинки; «Забагато змін» показується лише від 4-х.
- ⚪ **Легенда типів — кольорові `span` без підпису**, назва лише в `title` (`ScheduleTab:254`).
  На тач-пристроях `title` недоступний — легенда стає набором безіменних крапок.

## 3. Фронтенд — валідація вводу, стани

- 🟠 **`LeaveTab` не валідує й не показує помилок.** `submit` (`LeaveTab:19-24`) лише
  перевіряє, що `start`/`end` непорожні, і одразу POST. Кінець < початку — не блокується
  (сервер мовчки свопить, `OrderDates`, §9), перекриття/дублі відпусток — не перевіряються,
  майбутня дата на 50 років — приймається. `leaveDays` рахує будь-який діапазон (§10).
- 🟡 **`MeetingsTab` дозволяє зустріч у минулому** — `date` дефолт «сьогодні», але можна
  обрати будь-яку дату; валідації «не в минулому» немає, тож нова зустріч одразу падає в
  групу «Минулі». Час дефолт `10:00`, порожній «з ким» ловиться, місце — вільний рядок.
- 🟡 **`ProcessTab`/`ObligationsTab` — поля назви й опису без `maxLength`** (на відміну від
  контактів і заголовка роботи). Назва задачі процесу / обов'язку може бути як завгодно
  довгою; сервер теж не ріже (`Title.Trim()` без обмеження довжини, §6). Ризик «гігантський
  текст ламає верстку картки» + зберігання необмеженого рядка.
- 🟡 **Типи змін: час не валідовано на осмисленість.** `<input type="time">` дає `HH:MM`,
  але start==end (нульова зміна) проходить → `segmentHours` поверне 24 год (§10). Для `split`
  перевіряється лише непорожність обох пар (`ScheduleTab:80`), не те, що друга пара після
  першої / не перетинається.
- 🟡 **`onCallMultiplier` — `type=number min=1 step=0.1`, але без верхньої межі й без перевірки
  на нечислове.** `Number(typeForm.onCallMultiplier)` від порожнього/«1.5abc» → `NaN`; у payload
  піде `null` лише якщо falsy, інакше `Number('1,5')=NaN` (кома!) теж. Кома як десятковий
  роздільник (укр. розкладка) дасть NaN → коефіцієнт мовчки зникне.
- 🟡 **Форма типу змін при зміні `kind` не чистить поля.** Перемкнув split→normal — у стані
  лишаються `startTime2/endTime2`; клієнт їх занулить у payload (`kind!=='split'`), але якщо
  знову split — старі значення повертаються без попередження. Для oncall аналогічно з
  множником. Плутанина при редагуванні.
- ⚪ **`editingEntryId` при видаленні типу зміни не скидається** — якщо редагувати запис
  графіка й у цей час видалити тип, форма лишиться у «custom»-режимі з неіснуючим `pickTypeId`;
  спроба зберегти дасть `errPickType`. Дрібно, але стан неузгоджений.

## 4. Інтернаціоналізація (i18n) — типи змін/вкладки uk/en

- ✅ **Ключі `work.*` збігаються**: 206 ключів у `uk.json` і 206 у `en.json`, діфф порожній
  (`shiftKind.*`, `leaveKind.*`, `process.*`, `tab.*`, `regime.*`, помилки, merge-тексти).
- 🟡 **Назва місяця в заголовку календаря форматується через `toLocaleDateString`**
  (`ScheduleTab:221`) з `LOCALE[language]`, а не через i18n-формат → для `en` буде «November
  2026», для `uk` «листопад 2026» — залежить від ICU браузера, а не від обраного `dateFormat`
  у Налаштуваннях. Непослідовно з рештою дат, які йдуть через `formatDate`.
- 🟡 **`MeetingTitle`/`BuildShiftDescription` зашиті українською на сервері**
  (`WorkService:484` «Зустріч: …», `:204-205` «(чергування)»/«(гнучко)», `SyncProcessCalendarAsync:584`
  «Задача: …»). Ці тексти потрапляють у спільний календар і показуються англомовному
  користувачеві українською — локаль ігнорується, бо заголовок матеріалізується на бекенді.
- 🟡 **`landing.moneyCurrency` («грн») використовується як валюта доходу** (`ScheduleTab:247`).
  Валюта зашита; для англійської локалі все одно «грн». Запозичення ключа з Landing — крихко.
- ⚪ **Назва оператора однакова для uk/en** (`phone.js:53`, Kyivstar/Vodafone/lifecell) — це
  бренди, ок; але `operatorOther`/`operatorNone`/`phoneCountryUnknown` локалізовані окремо —
  переконатися, що вони є в обох файлах (є, діфф порожній).

## 5. Доступність (a11y): модалки типів/графіка, канбан-стрілки, календар

- 🟠 **Модалки типів/графіка — `div.work-modal-overlay`, не діалог.** Немає `role="dialog"`,
  `aria-modal`, `aria-labelledby`, фокус-пастки й повернення фокуса; Escape не закриває
  (`ScheduleTab:298-301`, 375-378). Клавіатурний користувач може «вийти» фокусом за модалку
  в контент позаду. Закриття лише кліком по оверлею або по хрестику.
- 🟠 **Клітинки календаря — некерабельні з клавіатури.** `work-cal-day` — `div` без
  `tabindex`/`role`; чипи змін — `span` із `title`. Жодної семантики «день X, зміна Y» для
  скрінрідера; інформація про зміну лише у `title` (миша/хавер).
- 🟡 **Канбан-стрілки спираються на `data-tooltip`** (`ProcessTab:77-80`) — це CSS-підказка,
  не ARIA; `aria-label` є (добре), але `disabled` крайніх стрілок не озвучує «далі нікуди».
  Переміщення статусу лише мишею/клавішею по двох кнопках — ок, але без оголошення зміни стану
  (no `aria-live`), користувач не чує, що картка переїхала.
- 🟡 **Свотчі кольору мають `aria-label={c}`** — тобто «#ffd59e» (`ScheduleTab:332`). Скрінрідер
  читає HEX замість назви кольору; вибраний стан (`work-swatch--active`) не має `aria-pressed`.
- 🟡 **Легенда активних типів — `span` з `title`** без тексту (§2), недоступна скрінрідеру.
- 🟡 **`window.confirm`/`alert` для злиття контактів і «видалити минулі»** (`ContactsTab:98,146`,
  `MeetingsTab:47`) — нативні, доступні, але блокують і не локалізуються стилем; зміст залежить
  від i18n-рядка (ок).
- ⚪ **Поля заголовка роботи — `input` без `<label>`**, лише `placeholder` (`Work.jsx:95-105`).
  Placeholder зникає при вводі; скрінрідер не має назви поля «Посада»/«Роботодавець».

## 6. Бекенд — API, статус-коди, валідація

- 🟠 **Немає валідації довжин і форматів.** `WorkController` перевіряє лише непорожність
  ключових рядків (`Name`/`FullName`/`Title`/`WithWhom`). Назва роботи/посади/типу зміни/
  контакту/задачі приймаються будь-якої довжини — клієнтські `maxLength` (60/40/24) легко
  обійти прямим запитом. У БД — колонки без явного ліміту.
- 🟠 **`Color` типу зміни не валідується.** `WorkShiftTypeRequest.Color` пишеться as-is
  (`WorkService:146,159`). Можна записати будь-який рядок (`"javascript:…"`, `"red; }"`,
  довжелезний). Він іде в `style={{ background: s.color }}` на клієнті (інлайн-стиль) — CSS
  injection обмежений (React ставить як властивість), але зламана верстка/невидимі чипи — так.
- 🟠 **Унікальність типів змін (назва/колір/час) — лише на клієнті** (`ScheduleTab:82-85`).
  Сервер `AddShiftTypeAsync`/`UpdateShiftTypeAsync` жодних перевірок дублів не робить →
  прямий POST створює кілька типів з однаковими назвою/кольором/часом, легенда й календар
  стають неоднозначними.
- 🟠 **Обмеження графіка (max 5, без перетину) — лише на клієнті** (`ScheduleTab:150-157`).
  `AddScheduleEntryAsync` (`WorkService:237`) не рахує кількість і не перевіряє перетин → через
  API можна завести 100 записів графіка однієї зміни з повним перекриттям → у кожен день по
  багато дублів, «Забагато змін», важкі генерації (§11).
- 🟠 **Параметри повторення не валідуються на сервері.** `CreateRecurrenceRuleAsync`
  (`TaskService:528`) зберігає `Type/IntervalDays/EndDate/MonthDays…` без перевірки
  (клієнтський `validateRecurrenceValue` / «максимум рік» — обходяться). Можна `EndDate=null`
  або «9999-12-31», `IntervalDays=0`/від'ємний, довільний `Type`. Наслідки — §11 (генерація).
- 🟡 **Статус-коди бідні.** Усі мутації повертають `Ok()`/`Ok({id})` або `NotFound()`; немає
  `201 Created`, немає тіла помилки для «дубль/перетин/ліміт» (бо їх і не перевіряють). BadRequest
  лише на порожню назву. Клієнт не може розрізнити «не знайдено» від «чуже» (обидва 404 — і це
  добре для IDOR, але погано для діагностики).
- 🟡 **`WorkMeetingRequest.When` — `DateTime` без зони/меж.** Приймається будь-яка дата (рік 0001
  чи 9999). Жодної перевірки «розумного» діапазону.
- 🟡 **`GetSettingsAsync` робить запис у БД на GET** (`WorkService:83-91`) — створює порожній
  `WorkSettings` при першому читанні. GET із побічним ефектом (не ідемпотентний) + зайвий запис
  для користувачів, що лише зазирнули в розділ.
- 🟡 **`schedule/calendar` без обмеження діапазону `from..to`** (`WorkController:103`). Клієнт
  шле місячну сітку, але API прийме `from=2000-01-01&to=2100-01-01` — генерація за 100 років
  (§11).

## 7. Авторизація та власність (гейтинг isWorking на сервері; IDOR)

- 🔴 **Сервер не перевіряє `isWorking`.** `WorkController` має лише `[Authorize]`
  (`WorkController.cs:25`) і ніде не читає `UserProfile.IsWorking`. Будь-який автентифікований
  користувач — навіть з вимкненим «Працюю» — може викликати всі `/api/work/*` (створювати зміни,
  контакти з ПДН, зустрічі, що лізуть у спільний календар). Клієнтський редірект (`App.jsx:205`)
  і приховування меню — косметика. Порівняти зі Study (теж м'який гейтинг) — тут навіть редіректу
  в маршруті для work нема проблеми, бо справжня діра — на сервері.
- 🟠 **Дані зберігаються й доступні після вимкнення «Працюю».** Toggle `isWorking=false` лише
  ховає UI; `WorkSettings`, контакти, зустрічі, графік лишаються в БД і повертаються по API.
  Зустрічі/дедлайни процесу далі висять у спільному календарі (`ModuleCode="work"`) і в «Важливих
  боргах», хоча розділ «вимкнено».
- ✅ **IDOR на рівні сервісу закрито коректно.** Усі `FirstOrDefaultAsync(x => x.Id==id &&
  x.UserId==userId)` і `Where(x => x.UserId==userId)` (shift-types, schedule, contacts, leaves,
  meetings, obligations, process). Чужий `id` → `NotFound()`, не витік. `userId` береться з JWT
  (`CurrentUserId`), не з тіла.
- 🟠 **`WorkScheduleRequest.ShiftTypeId` перевіряється на власність** (`AddScheduleEntryAsync:239`
  `x.UserId==userId`) — добре; але `UpdateScheduleEntryAsync` дозволяє **переприв'язати** запис
  на будь-який СВІЙ тип. Не IDOR, але у парі з відсутністю перевірки перетину (§6) дозволяє легко
  зробити кашу.
- 🟠 **Зв'язок meeting↔task і process↔task через `TaskId`** зберігається сервером, видалення
  йде `DeleteTaskAsync(userId, taskId, cascadeSource:false)` (`WorkService:477,574`) — `userId`
  скоупить, тож IDOR над чужим `taskId` неможливий. Але `TaskId` береться з запису в БД, не з
  клієнта — добре, клієнт не може підсунути чужий taskId.
- 🟡 **`GetScheduleCalendarAsync`/`GetNextShiftAsync` вантажать лише свої правила** (userId-скоуп) —
  ок; але правила живуть у спільній таблиці `RecurrenceRules`. Переконатися, що видалення типу
  зміни (`DeleteShiftTypeAsync`) не лишає «осиротілих» правил без запису (воно видаляє і правило —
  `:189`, ок).

## 8. Безпека (XSS, масове призначення, приватність ПДН контактів)

- 🟠 **Приватність ПДН третіх осіб.** Контакти містять ПІБ, до 3 телефонів, email, Telegram,
  день народження — персональні дані інших людей. Зберігаються у відкритому вигляді (без
  шифрування), повертаються повним списком (`GetContactsAsync`), ймовірно потрапляють у
  «Експорт даних (JSON)» з Налаштувань. Жодної згоди суб'єкта, жодного обмеження/маскування.
  Для диплома варто хоча б згадати це як обробку ПДН.
- 🟡 **Масове призначення / over-posting.** `WorkContactRequest` приймає застарілі `Status`,
  `Socials`, `Viber`, `GroupName` (`WorkController:13`); `WorkObligationRequest` — `DueDate`/`IsDone`,
  яких UI вже не використовує (`Work.cs:111-124`). Клієнт шле порожнє/`null`, але API дозволяє їх
  виставити довільно. Зайва атакова поверхня на «мертвих» полях.
- 🟡 **XSS — збережений, але нейтралізований React-ом.** Назва роботи/посади/контакту/зустрічі/
  задачі рендеряться як текстові вузли (`{c.fullName}`, `{m.withWhom}`, `{task.title}`) — React
  екранує. `dangerouslySetInnerHTML` у модулі немає. Ризик лишається для *інших* споживачів тих
  самих даних: JSON-експорт, календарні заголовки (`Зустріч: <withWhom>`), якщо колись
  відрендерити їх поза React. `s.color` як інлайн-стиль — не JS-вектор, але див. §6.
- 🟡 **E.164-валідація телефону лише на клієнті** (`ContactsTab:128-132` через `parsePhone`).
  Сервер `NormalizePhones` (`WorkService:64-72`) лише розбиває по комі, бере 3 унікальні й
  склеює — формат не перевіряє. Прямий POST збереже `phone: "<script>"`/будь-який сміттєвий
  рядок. На картці він покажеться як «телефон» (екранований), але дані брудні.
- 🟡 **Telegram/email на сервері не валідуються** (`Trim` і все). Email-regex — лише клієнт
  (`ContactsTab:13`). `@@@`/довгий рядок пройдуть через API.
- ⚪ **`alert(t('work.phonesCapped'))`** при злитті >3 номерів (`ContactsTab:98`) — блокуючий,
  але нешкідливий.

## 9. Бізнес-логіка та інваріанти

- 🟠 **Дедуплікація/злиття контактів перезаписує мовчки й ненадійно.** `findDuplicate`
  (`ContactsTab:74-90`) матчить за `normName(fullName)` (трим+lower+стиск пробілів), потім за
  будь-яким спільним номером (по цифрах), потім за `normTg`. Проблеми: (1) різні люди з однаковим
  ПІБ («Іван Петренко») вважаються дублем і зливаються; (2) `mergeIntoEdit` бере ПІБ/email/
  telegram **зі старого** запису, нові — відкидає (крім телефонів і порожніх полів), тобто
  виправлення не застосуються без ручного звіряння; (3) дедуп працює лише при створенні, не при
  редагуванні — редагуванням можна зробити двійника навмисне. «Підробка»: знаючи ПІБ, інший
  запис не підробиш (усе userId-скоуп), але в межах свого списку легко ненавмисно затерти.
- 🟠 **Графік → правило повторення: час правила = початок зміни** (`ScheduleTab:170`, `WorkService:243`).
  Для `oncall`/`flexible` це ок, але для `split` **друга частина дня не стає окремою подією** —
  у календар іде один інстанс на `StartTime`, опис містить «, 13:00–17:00» лише текстом
  (`BuildShiftDescription`). Тобто розділений день у спільному календарі виглядає як одна подія
  зранку; друга половина не блокує «вільні години».
- 🟠 **Унікальність кольору/часу/назви — обходиться** (повтор §6): інваріант «один колір = один
  тип» тримається лише формою. Через API — ламається; у легенді дві однакові крапки.
- 🟠 **Max 5 записів графіка й «та сама зміна не перетинається» — клієнтський інваріант** (§6).
  Сервер не тримає. «Різні зміни можуть перетинатись» реалізовано правильно на клієнті
  (`scheduleGuard` фільтрує `e.shiftTypeId !== type.id`), але вся перевірка обходиться.
- 🟡 **`toggleTypeActive` неактивного типу ховає зміни з календаря** (`LoadEntriesWithRulesAsync:295`
  фільтрує `ShiftType.IsActive`), але **правила повторення лишаються** й шаблон-задачі теж.
  «Наступна зміна» їх не покаже (теж фільтр), проте в головному календарі-планувальнику
  (інший шлях, `TaskService.GetTasksForRangeAsync`) ці `ModuleCode="work"` інстанси **не
  фільтруються за IsActive** — перевірити, чи деактивований тип не продовжує світитись у
  спільному календарі. Потенційна розбіжність «вимкнув зміну, а в календарі вона є».
- 🟡 **Зустрічі → події календаря**: створення робить `SaveChanges` двічі (щоб отримати Id і
  прив'язати task, `WorkService:449-454`). Якщо `CreateTaskAsync` кине виняток між ними —
  лишиться зустріч без `TaskId` (видима в розділі, але без події календаря). Немає транзакції.
- 🟡 **Процес-задача з дедлайном → «Задача: …» у календар** лише доки `DueDate!=null &&
  Status!="done"` (`SyncProcessCalendarAsync:583`). Перемикання done→doing назад відтворює подію
  з часом `09:00` (`:587`) — початковий час втрачається щоразу. «Важливі борги» головного
  календаря беруть прострочені з цього ж джерела — узгоджено, але дата дедлайну завжди о 9:00.
- 🟡 **`isOverdue` (клієнт, `ProcessTab:46`) і серверний `shouldHave` розходяться в понятті
  «сьогодні».** Клієнт рахує `dueDate < todayApiDate()` (локальна дата браузера), сервер
  `DueDate < сьогодні` (`DateTime.Now` сервера). У різних таймзонах задача може бути
  «прострочена» в боргах процесу, але ще «в календарі» (або навпаки).
- 🟡 **Відпустки: підрахунок днів без урахування перекриттів і типу.** KPI «Відпустка
  використано» = сума `leaveDays` усіх записів типу vacation (`LeaveTab:28`). Дві відпустки, що
  перетинаються, порахуються двічі; немає звірки з `ExtraVacationDays`/нормою. Лікарняний і
  вихідні всередині відпустки не виключаються — днів більше, ніж реально.
- ⚪ **Зобов'язання — статичний перелік без дедлайнів** (за дизайном), але модель ще має
  `DueDate/IsDone` (`Work.cs:122-123`) і API їх приймає (§8) — мертві інваріанти.

## 10. Дата/час, межі, валідація телефонів E.164, Unicode

- 🟠 **Години зміни через північ — коректно для одного проміжку, але 24-годинна пастка.**
  `segmentHours` (`workShared.js:38-44`): якщо `mins<=0` додає 1440. Для start==end (00:00–00:00
  чи 09:00–09:00) дає рівно **24 год** замість 0 — беззмістовна «цілодобова» зміна проходить і
  роздуває «Годин цього місяця» та дохід.
- 🟠 **Коефіцієнт тарифу → «орієнтовний дохід»: без стелі.** `paidHours = Σ годин × множник`
  (`ScheduleTab:212`), `earnings = paidHours × rate` (`:216`). Множник на сервері лише `is > 0`
  (`WorkService:134`) — верхньої межі немає; `rate` теж лише `> 0`. Через API множник=1e9 або
  rate=1e9 → «≈ <астрономічне число> грн» без форматування/клампу. Від'ємний відсікається
  (`is > 0 → null`), тож хоч мінуса немає.
- 🟡 **Нічні/розділені/чергування в сумі місяця рахуються по `shiftTotalHours`** (`:210`), але
  **без прив'язки до фактичної дати перетину місяця**: зміна 22:00–06:00 1-го числа «належить»
  дню старту (чипу), її 6 нічних годин зараховано в місяць старту повністю — не ділиться по
  днях/місяцях. Для «годин цього місяця» на межі місяця можливий зсув.
- 🟡 **Таймзони.** Календар/наступна зміна рахуються від `DateTime.Now` сервера (`GetNextShiftAsync:313`);
  клієнт — від локального браузера (`todayApiDate`). Зустрічі зберігаються як `DateTime When`
  без зсуву зони (`When = \`${date}T${time}:00\``, `MeetingsTab:31`) — тлумачаться як локальні,
  але чиї? Якщо сервер в UTC, а користувач у +2 — «наступна зміна»/межа «майбутні/минулі» зустрічі
  зсунуться на кілька годин.
- 🟡 **`leaveDays` через `new Date(y,m-1,d)` і ділення на 86400000** (`workShared.js:62-68`).
  На переході зимового/літнього часу доба може бути 23/25 год → `Math.round` рятує для сусідніх
  днів, але для багатомісячних діапазонів через DST можлива похибка ±1. Межі діапазону не
  обмежені (відпустка на 100 років → 36525 днів у KPI).
- 🟡 **E.164: межа 3 телефони тримається і на клієнті, і на сервері** (`MAX_PHONES=3`,
  `NormalizePhones.Take(3)`) — ✅; але формат валідний лише на клієнті (§8). `parsePhone`
  (`phone.js:95-104`): код «1» (США) матчить **будь-який** номер, що починається з 1 →
  11-значний «1XXXXXXXXXX» вважається валідним US; код «7» — Росія/Казахстан валідний (нюанс).
  Невідомий код → будь-які 8–15 цифр «валідні». Тобто валідація дуже м'яка — хибно-позитивів
  багато.
- 🟡 **Unicode / нормалізація імен.** `normName` робить `toLowerCase` + стиск пробілів, але не
  робить Unicode-нормалізацію (NFC/NFD) і не прибирає діакритику → «é» (composed) і «é»
  (decomposed) вважаються різними контактами; дедуп не спрацює. Ініціали `name[0]?.toUpperCase()`
  (`ContactsTab:207`) для емодзі/сурогатних пар візьме пів-символа.
- ⚪ **День народження зберігається як `2000-MM-DD`** (`ContactsTab:138`) — рік-заглушка; 29
  лютого (2000 — високосний) збережеться, але в невисокосний рік показ через `new Date(2000,…)`
  усе одно від 2000 — ок. Сортування «за ДН» по `birthday.slice(5)` (MM-DD) ігнорує рік — вірно.

## 11. Продуктивність і надійність

- 🟠 **DoS генерації правил — як у Календарі, тут навіть ширший.** `schedule/calendar` без меж
  діапазону (§6) + відсутність серверної валідації `IntervalDays`/`EndDate` (§6) + обхід «max 5»
  (§6): зловмисник створює 100 записів `EveryNDays` з `IntervalDays=1`, `EndDate=null` і запитує
  `calendar?from=2000-01-01&to=2100-01-01` → `GetEffectiveOccurrences` згенерує мільйони
  `DateTime` у пам'яті (`WorkService:304-308`, `TaskService:208`). Так само `GetNextShiftAsync`
  завжди генерує на 120 днів × N правил на кожен запит заголовка.
- 🟠 **`IntervalDays=0`/від'ємний** (не валідується, §6) у `GenerateBaseDates` (EveryNDays) —
  ризик нескінченного/некоректного циклу або ділення; треба перевірити, що `TaskService` не
  зациклюється. Якщо крок 0 — цикл дат не просувається → зависання запиту.
- 🟠 **Гонки мутацій графіка.** Усі дії (`addQuick`/`addCustom`/`deleteEntry`/`toggleTypeActive`)
  роблять мутацію й одразу `afterScheduleMutation()` → три паралельні GET
  (`types`, `entries`, `next`) + окремий GET `calendar` (`ScheduleTab:49-53`). Швидкі
  послідовні дії дають накладені перезавантаження; відповіді можуть прийти не в порядку
  (застарілий `calendar` перетре свіжий). `scheduleGuard` рахує по `entries` зі стану, який під
  час польоту запиту ще старий → можна проскочити «max 5»/перетин навіть на клієнті.
- 🟠 **«Видалити минулі зустрічі» — N окремих DELETE через `Promise.all`** (`MeetingsTab:48`).
  10 минулих = 10 запитів; якщо частина впаде — видалиться лише частина, а `reload` покаже
  неузгоджений стан без повідомлення про помилку. Немає bulk-ендпоінта, немає транзакції;
  кожен DELETE ще й окремо чистить пов'язану подію календаря (`DeleteTaskAsync`).
- 🟠 **Поділ «майбутні/минулі» зустрічі по `now` на кожен рендер** (`MeetingsTab:40-43`).
  `now = new Date()` у тілі компонента → перераховується щоразу; зустріч рівно «зараз» може
  миготіти між групами. Дрібно, але також означає, що без оновлення сторінки межа не рухається
  (зустріч, що настала, лишається «майбутньою» до наступного рендеру).
- 🟡 **Узгодженість шапки «Наступна зміна».** Заголовок (`Work.jsx`) і `ScheduleTab` незалежно
  тягнуть `getNextShift` (два джерела правди). `ScheduleTab` оновлює свій `nextShift` на кожну
  мутацію, а шапка — лише через `onScheduleChange → reloadHeader`. Якщо `onScheduleChange`
  відпрацює раніше, ніж сервер матеріалізує правило (гонка §11), шапка покаже стару «наступну
  зміну». Два запити `next` на кожну дію графіка — надлишок.
- 🟡 **`monthStats` фільтрує календар по `getMonth()` без року** (`ScheduleTab:208-209`).
  У межах однієї сітки місяця безпечно (сусідні місяці мають інший номер), але код крихкий:
  якщо `calendar` колись міститиме дані з того ж номера місяця іншого року — порахується зайве.
- 🟡 **`GetSettingsAsync` пише в БД на кожен перший GET** (§6) — під навантаженням зайві INSERT
  і потенційна гонка «двоє паралельних GET створюють два рядки» (PK=UserId врятує другим
  виключенням, але це 500).
- ⚪ **`getScheduleCalendar` перезапитується на кожну зміну `visibleMonth`** навіть туди-назад —
  немає кешу по місяцях; гортання календаря = запит на кожен крок.

### Зведення найгострішого

1. 🔴 **Сервер не перевіряє `isWorking`** — увесь `/api/work/*` доступний будь-якому
   автентифікованому користувачу (§7).
2. 🟠 **Усі ключові інваріанти графіка/типів — лише на клієнті** (унікальність кольору/назви/
   часу, max 5 записів, заборона перетину, «максимум рік») — обходяться прямим API (§6, §9).
3. 🟠 **Немає серверної валідації повторення + необмежений `calendar?from..to`** → DoS генерації
   (мільйони інстансів, `IntervalDays=0` зависання) (§6, §11).
4. 🟠 **Приватність ПДН контактів** без шифрування/згоди + E.164/email/Telegram валідуються лише
   на клієнті (§8, §10).
5. 🟠 **Дохід без стелі** (множник × rate × години, start==end → 24 год) (§10) і **дедуп/злиття
   контактів мовчки затирає/плутає однофамільців** (§9).
