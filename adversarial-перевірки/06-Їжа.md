# Adversarial review — Їжа

Чек-лист перевірок для вкладки **«Їжа»** планувальника «Всетута».
Джерела коду: `client/src/pages/Food.jsx`, `client/src/api/food.js`, `client/src/api/shopping.js`, `server/Controllers/FoodController.cs`, `server/Services/RecipeService.cs`, `server/Models/Food.cs`, `server/RuleEngine/RuleEvaluator.cs`, `server/Controllers/ShoppingListController.cs` + `ShoppingService.AddItemAsync`.

Легенда пріоритетів: 🔴 критично · 🟠 суттєво · 🟡 помірно · ⚪ дрібно/косметика.

## 1. Фронтенд — сторінка, вкладки Меню/Страви/Запаси, логіка

- [ ] 🔴 **Forbidden-страви витікають усюди, крім стрічки «Страви».** Жорстке приховування `if (recipe.health?.forbidden) return false` живе **лише** у `visibleRecipes`. Але:
  - `favoriteRecipes = recipes.filter((r) => selected.includes(r.id))` — **без** фільтра forbidden → заборонена страва показується у панелі «Обрані страви», у пікері меню та у вкладці «Меню».
  - `recipeMap[id]` у вкладці «Меню» рендерить будь-який рецепт, зокрема forbidden, якщо його колись додали до меню (а потім обмеження стало жорстким).
  - Перевірити, чи це задумано; за §2.3/§4.6 forbidden має бути прихований повністю.
- [ ] 🟠 **`recipes.length` у лічильнику вкладки «Страви»** рахує ВСІ рецепти (разом із forbidden), хоча у стрічці їх менше, ніж показано в метаданих `tabDishesMeta` — розбіжність лічильника й фактично видимого.
- [ ] 🟡 **Меню зберігає `recipeId`, а не знімок страви.** Якщо рецепт зник із довідника (зміна сіду/версії), `recipeMap[id]` → `undefined` → `return null` (чіп тихо зникає), але `menuCount` усе одно рахує «мертвий» id у `tabMenuMeta`. Розбіжність лічильника й видимих чіпів.
- [ ] 🟡 **`addToMenu` дозволяє дублі** однієї страви в одному дні (немає перевірки `includes`). Перевірити, чи це бажано.
- [ ] 🟡 Кнопка «Додати страву» в меню `disabled={favoriteRecipes.length === 0}`, але **наявні чіпи меню лишаються**, навіть якщо користувач зняв усі галочки обраного — меню «застигає» на старих обраних.
- [ ] 🟡 Відмітка галочки «обране» на картці рецепта **одночасно** додає в обрані і відкриває вікно готовки (`if (willSelect) openCooking(recipe)`). Несподівана подвійна дія; зняття галочки — без вікна. Перевірити UX-очікування.
- [ ] ⚪ Клік по фото рецепта відкриває готовку, а чекбокс усередині фото зупиняє спливання (`stopPropagation`) — легко випадково відкрити вікно замість поставити галочку.
- [ ] ⚪ Перемикання вкладок не скидає відкриті Drawer/вікно готовки (стани `favoritesOpen`, `addStockOpen`, `cooking` живуть поверх будь-якої вкладки) — перевірити, чи немає «привидів» панелей після зміни вкладки.

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо)

- [ ] 🟠 **Немає rollback при помилці мутацій.** `handleStockState`, `handleAddStock`, `handleToggleFavorite`, `finishCooking` роблять оптимістичний `setStock/setSelected`, потім `await api…` **без try/catch**. Якщо запит упав — UI показує неправдивий стан, а помилка — unhandled rejection. Для `finishCooking` ще й модалка не закриється (`setCooking(null)` недосяжний після throw).
- [ ] 🟠 **Повносторінковий `error`-стан** вмикається лише якщо впав `getFoodOverview` (finance/shopping мають `.catch` із fallback). Немає кнопки «повторити» — лише текст `common.error`; треба перезавантажити сторінку.
- [ ] 🟡 **Балансовий фільтр при `balance = 0`** (finance недоступний → fallback `{balance:0}`): `range = {from:0, to:0}`, а умова `missingCost >= 0 && missingCost <= 0` у режимі «Все» показує **лише** рецепти з нульовою вартістю докупівлі. Більшість страв тихо зникає — користувач бачить майже порожню стрічку без пояснення причини.
- [ ] 🟡 **Невідома ціна трактується як 0.** `missingCost = missing.reduce((s,p)=>s+(p.personalPrice||0),0)` — продукт без особистої ціни додає 0. Страва з дорогим, але «безцінним» інгредієнтом показує «докупити N (~0 грн)» і завжди проходить бюджетний фільтр. Вводить в оману.
- [ ] 🟡 Інпути діапазону: `clamp` обмежує `[0, balance]`, але якщо `balance` від'ємний (теоретично з Фінансів) — `Math.min(Math.max(0,v), balance)` дасть від'ємне значення й зламає фільтр.
- [ ] ⚪ Порожні стани присутні й осмислені: `emptyRecipes`, `menuNoFavorites`, `menuDayEmpty`, `favoritesEmpty`. Перевірити, що `emptyRecipes` показується і коли стрічку спорожнив саме бюджетний фільтр (так, показується, але текст натякає лише на суму/«Все»).
- [ ] ⚪ Пошук у «Додати запаси» — `trim().toLowerCase().includes` без debounce; на великому довіднику перерендер списку на кожну літеру.

## 4. Інтернаціоналізація (i18n) — назви продуктів/рецептів/груп uk/en, невикористані ключі

- [ ] 🟠 **Користувацькі продукти не двомовні.** `AddStockByNameAsync` пише `NameUk = NameEn = clean`. Користувач з `language='en'` побачить український ввід, і навпаки. `productName` просто обирає поле — переклад не з'явиться.
- [ ] 🟠 **Невикористаний ключ `food.hiddenByHealth`** («Сховано {count} страв…») є в `uk.json` і `en.json` (рядок 647), але у `Food.jsx` ніде не рендериться. Спека обіцяє підказку про приховані страви — її немає. Або додати UI, або видалити ключ.
- [ ] 🟡 **Ключ `food.cookClose` відсутній** у словниках. `aria-label={t('food.cookClose') || 'Закрити'}` спрацює лише якщо `t` повертає falsy для відсутнього ключа; якщо `t` повертає сам ключ-рядок — у aria-label потрапить `"food.cookClose"`. Перевірити поведінку `t` на missing key.
- [ ] 🟡 **Хардкод «Закрити»** в aria-label/`data-tooltip` Drawer (`drawer-close`) і в `data-tooltip` кнопки вікна готовки — не локалізовано; en-користувач бачить українське.
- [ ] 🟡 **`food.group.*` має рівно 7 ключів** (vegetable, dairy, bakery, pantry, canned, meat, fruit). Будь-який інший `StorageGroup` з довідника (або `""` у user-продуктів) → `t('food.group.<невідоме>')` = відсутній ключ у пігулці фільтра. Імпортер продуктів має гарантувати лише ці 7 груп — перевірити.
- [ ] ⚪ Перевірити паритет `uk.json` ↔ `en.json` по всьому блоку `food.*` (ключі, плейсхолдери `{name}/{count}/{cost}/{n}/{tag}/{day}/{sel}`).
- [ ] ⚪ `food.minutes = "{n} хв"` — для рецепта з `cookTimeMinutes = 0` або дуже великим значенням перевірити формулювання.

- [ ] 🔴 **Триступеневий перемикач** — три порожні `<button>` зі стилем-кружечком; єдина семантика — `title`. Немає `role="radiogroup"`/`aria-pressed`/`aria-checked`, немає текстової мітки. Скрінрідер не повідомляє, який стан активний (`stock-circle--on` — суто візуально). Те саме у вікні готовки (крок 2).

- [ ] ⚪ `window.confirm` для «Закінчується» — модальний браузерний діалог; доступний, але вибивається зі стилю й не керований клавіатурними очікуваннями застосунку.

## 6. Бекенд — API, статус-коди, валідація

- [ ] 🟠 **`SetStockStateAsync` / `AddStockAsync` не перевіряють власність продукту** — лише `Products.AnyAsync(p => p.Id == productId)`. Див. §7 (IDOR).
- [ ] 🟡 **`stock-by-name` без обмежень:** `AddStockByNameRequest.Name` не має max-довжини, не санітизується; порожнє → `BadRequest(empty_name)`, але рядок із самих пробілів після `Trim()` теж дає `empty_name` (ок). Немає rate-limit → спам створення продуктів.
- [ ] 🟡 **`SetStockState` повертає `BadRequest(invalid_stock)`** як для невалідного стану, так і для неіснуючого продукту (обидва → `false`). Клієнт не розрізняє причину (а він і так ігнорує тіло відповіді).
- [ ] 🟡 **Overview віддає `Steps` рецептів**, яких клієнт взагалі не рендерить — зайвий payload (див. §10, продуктивність).
- [ ] 🟡 Немає пагінації/ліміту в `GetOverviewAsync` — повертає всі продукти + усі рецепти з інгредієнтами та кроками щоразу.
- [ ] ⚪ `MarkCookedAsync` використовує `DateTime.Now` (локальний час сервера), тоді як `StockItem.UpdatedAt` — `DateTime.UtcNow`. Неузгодженість часових зон у БД.
- [ ] ⚪ Усі ендпоінти `[Authorize]`; `CurrentUserId` = `int.Parse(sub)` — впаде `NullReferenceException/FormatException`, якщо токен без `sub` (малоймовірно, але без захисту).
- [ ] ⚪ Немає валідації, що `SelectedDishes` не накопичує дублі — `.Distinct()` в overview натякає, що дублі історично можливі; `ToggleSelectedAsync` перевіряє `current is null`, тож нові дублі не з'являться (ок).

## 7. Авторизація та власність (системні продукти/рецепти vs користувацькі запаси/обрані; IDOR)

- [ ] 🔴 **IDOR на станах запасів.** `SetStockStateAsync`/`AddStockAsync` перевіряють лише існування продукту за `Id`, не власність. Користувач може викликати `PUT /api/food/stock/{id}` або `POST /api/food/stock/{id}` із **чужим приватним `productId`** (створеним іншим користувачем через `stock-by-name`). Створюється `StockItem(userId, productId)`, що посилається на чужий приватний продукт → підтверджує існування чужого продукту і дозволяє протягнути його у власний overview (де `productName` покаже чужу назву). Треба обмежити до `IsSystem || CreatedByUserId == userId`, як це зроблено у пошуку `AddStockByNameAsync`.
- [ ] 🟠 **`toggleSelected`/`markCooked` над будь-яким рецептом.** Перевірка лише `Recipes.AnyAsync(Id)`. Рецепти системні, тож крос-юзер витоку через них менше, але: (а) можна обрати/позначити приготованим **forbidden**-рецепт (сервер не фільтрує обмеження); (б) неіснуючий id → `NotFound` (404) — ок.
- [ ] 🟠 **Сервер не фільтрує forbidden** ні в overview (віддає всі рецепти з порахованим `health`), ні в `toggleSelected`. Приховування — суто клієнтське (§1). Хто читає відповідь `/overview`, бачить заборонені страви та їхні інгредієнти.
- [ ] 🟡 Користувацькі продукти ізольовані у пошуку за назвою (`IsSystem || CreatedByUserId == userId`) — чужий приватний продукт за назвою **не** знаходиться (добре; дублікат створиться у власному просторі). Але див. 🔴 вище — через прямий `productId` ізоляція обходиться.
- [ ] 🟡 `SelectedDish`/`StockItem`/`UserRecipeState` вибираються строго за `userId` в overview — крос-юзер читання стану закрите (добре).
- [ ] ⚪ Немає перевірки, що рецепт, який кладуть у меню (localStorage), взагалі належить до відданих overview — але меню клієнтське, ризик лише локальний.

## 8. Безпека (XSS у назвах власних продуктів, масове призначення стану)

- [ ] 🟠 **Stored-вміст у назвах власних продуктів.** `AddStockByNameAsync` зберігає `name` як є (тільки `Trim()`), без екранування/валідації символів. У React назви рендеряться як текст (`{productName(...)}`) — DOM-XSS мітигований React-екрануванням. **Але** ризик зберігається для не-React поверхонь: експорт даних у JSON (Налаштування → «Експортувати дані»), будь-який майбутній рендер через `dangerouslySetInnerHTML`, лист/звіт, лог. Санітизувати/обмежити на вводі.
- [ ] 🟠 **Сміття та дублі в довіднику продуктів.** Немає ліміту довжини, нормалізації (окрім `ToLower` при пошуку), заборони спецсимволів/емодзі/керуючих символів. «Молоко», «молоко », «Молоко.» дадуть різні продукти. DB-bloat + засмічений пошук «Додати запаси».
- [ ] 🟡 **Масове призначення стану:** `SetStockStateRequest.State` валідується білим списком (`Available|RunningLow|OutOfStock`) — добре, інше → `false`. `AddShoppingItemRequest.Section` теж білий список у `AddItemAsync`. Перевірити, що немає інших полів, які приймаються з тіла без перевірки.
- [ ] 🟡 Клієнт формує `addShoppingItem({ section: 'Groceries', productId })` — `section` хардкод, добре; але `productId` надсилається клієнтом → можна передати чужий/невалідний id (сервер `AddItemAsync` не валідує існування/власність продукту для shopping-item). Перевірити ShoppingService.
- [ ] ⚪ `window.confirm` із `{name}` — підстановка в текст діалогу браузера безпечна (plain text), XSS немає.

## 9. Бізнес-логіка та інваріанти

### Фільтр за бюджетом із «Фінансів»
- [ ] 🟠 **Баланс — суто клієнтський фільтр.** `getFinance().balance` впливає лише на межі діапазону й на те, які картки показати. «Докупити» нічого не купує й не списує грошей — тож підміна балансу на клієнті **не** дає фінансового експлойту, але дає оманливу картину «що по кишені». Жодної серверної перевірки бюджету немає (і не потрібно, але зафіксувати, що це декоративний фільтр).
- [ ] 🟡 `range.to` ініціалізується балансом; якщо користувач поповнив Фінанси вже після завантаження Їжі — діапазон не оновиться (дані тягнуться раз у `useEffect([])`).

### Наявність інгредієнтів
- [ ] 🟡 Наявність рахується на клієнті (`isPresent` = `Available|RunningLow`) і на сервері (`MissingProductIds`) **окремо** — дві реалізації однієї логіки. Клієнт ігнорує серверний `MissingProductIds` (не використовує його з DTO). Ризик розходження, якщо правила «що є присутнім» зміняться лише в одному місці.
- [ ] 🟡 `RunningLow` рахується як «присутній» і для наявності страви, і для готовки — страва «✓ все є», хоча інгредієнт закінчується. Перевірити, чи це бажано.

### Фільтрація за обмеженнями Здоров'я (forbidden/avoid)
- [ ] 🔴 Див. §1/§7: forbidden ховається лише у стрічці «Страви»; у «Обраних», «Меню» і в overview-відповіді — ні. **Avoid** показується як примітка «небажано: {tag}» лише на картці стрічки; у меню/обраних/запасах по-різному (у запасах є прапорець health; у чіпах меню прапорця немає взагалі).
- [ ] 🟡 `tagLabel(hs.avoid)` бере `displayName` з `restrictions`; якщо обмеження прибрали, але страва ще має `avoid` з кешу — можливий показ `tagKey` замість назви (fallback у `tagLabelFrom`). Перевірити узгодженість після зміни обмежень у «Здоров'ї» без перезавантаження Їжі.
- [ ] 🟡 Health страви агрегується з тегів **наявних** (`Value != "No"`) інгредієнтів; алерген `Unknown` трактується як присутній (небезпечний). Перевірити, що це не дає хибно-forbidden для страв з невизначеними тегами (over-blocking).

### Вікно готовки → оновлення запасів → список покупок
- [ ] 🔴 **Дублі в списку покупок при готовці.** `finishCooking` для кожного інгредієнта, що став `OutOfStock` і `wasPresent`, викликає `addShoppingItem` **без перевірки `inShopping`** і без дедуплікації на сервері (`AddItemAsync` завжди вставляє новий рядок). Повторні готовки тієї ж страви → кілька однакових позицій «Groceries».
- [ ] 🟠 **Часткові збої готовки.** `calls` виконуються через `Promise.all`; якщо хоч один `apiSetStockState`/`addShoppingItem` упаде — `await Promise.all` кине, `markCooked` не виконається, модалка не закриється, а `setStock(nextStock)` вже застосовано локально (оптимістично) → стан клієнта розходиться з сервером (частина збережена, частина ні). Немає атомарності/транзакції.
- [ ] 🟡 `keepAll=true` («Все лишилось як було») все одно викликає `markCooked` — ок за задумом (готував, нічого не змінив), але жодних запасів не чіпає.
- [ ] 🟡 Крок «result» ініціалізує стан інгредієнта як поточний або `OutOfStock` (якщо не було). Якщо на кроці «confirm» користувач зняв галочку «маю» — це **не** впливає на початковий стан результату (`have` і `states` незалежні). Перевірити, чи задум зрозумілий користувачу.

### Стан «Немає»/«Закінчується» → список покупок
- [ ] 🔴 **`OutOfStock` завжди додає в покупки, без перевірки `inShopping`.** `handleStockState` для `OutOfStock` безумовно викликає `addShoppingItem`. Тогл `Available→Немає→Available→Немає` плодить дублі (сервер не дедуплікує). Контраст: `RunningLow` перевіряє `!inShopping.has(productId)` і питає `confirm`.
- [ ] 🟠 **`inShopping` — лише клієнтський кеш сесії**, наповнюється з `shop.items.filter(!isChecked && productId!=null)` при завантаженні. Після перезавантаження позиція, додана через готовку (яка не оновлює `inShopping` узгоджено для всіх шляхів), може знову запропонуватися/додатися. Неузгоджена «єдина правда» про те, що вже в списку.
- [ ] 🟡 `OutOfStock` прибирає продукт зі списку запасів (`stockRows` фільтрує `!== 'OutOfStock'`) — тобто картка зникає відразу після кліку «Немає». Користувач не бачить підтвердження, куди вона поділася.
- [ ] 🟡 `RunningLow` використовує блокуючий `window.confirm` — на повільному зʼєднанні користувач може встигнути ще раз клікнути перемикач до відповіді (гонка з наступним станом).

### Меню в localStorage
- [ ] 🔴 **Тижневе меню живе ЛИШЕ в `localStorage` (ключ `food:weeklyMenu`).** Наслідки:
  - Втрата даних при очищенні кешу/іншому браузері/режимі інкогніто.
  - Немає кросдевайс-синхронізації (на телефоні меню інше).
  - `loadMenu` має `try/catch`: пошкоджений JSON → fallback на порожні 7 днів (дані мовчки губляться, без повідомлення користувачу).
  - `raw[d]` не-масив → замінюється `[]` (часткова втрата теж тиха).
  - **Немає міжвкладкової синхронізації** (`storage` event не слухається) — дві вкладки перезаписують меню одна одній (last-write-wins на кожну зміну через `useEffect([menu])`).
- [ ] 🟡 Меню індексоване 1..7 (ISO-день), а `orderedWeekDays` залежить від налаштування «перший день тижня». Перевірити, що зміна першого дня тижня не плутає прив'язку страв до днів (індекс `weekdays[i]` vs ключ `day`).
- [ ] ⚪ `menuCount` рахує й «мертві» id (рецепт зник) — лічильник вкладки завищений.

## 10. Дані, межі, Unicode, дуже довгі назви, велика кількість рецептів/продуктів

- [ ] 🟠 **Немає ліміту довжини назви** у `AddStockByNameAsync` — назва на кілька КБ пройде, збережеться, зламає верстку всюди, де рендериться продукт (Їжа, Список покупок, QuickAdd).
- [ ] 🟡 **Unicode/емодзі/керуючі символи** у назві продукту не фільтруються; `ToLower()` без культури може некоректно порівняти турецьку «I» тощо (крайній кейс дедуплікації).
- [ ] 🟡 **Велика кількість рецептів/продуктів:** `recipe-grid` і `stock-cards` рендеряться без віртуалізації; `availability` (useMemo по всіх рецептах × інгредієнтах) перераховується на кожну зміну `stock`. На сотнях рецептів — помітні лаги при кожному перемиканні стану запасу.
- [ ] 🟡 **Overview віддає всі `Steps`** рецептів, які клієнт не використовує — зайвий трафік/памʼять, що росте з розміром довідника.
- [ ] ⚪ `recipe.cookTimeMinutes` довідкове, не валідується (може бути 0/від'ємне з імпорту) → «0 хв».
- [ ] ⚪ `ingredientAmount` — вільний текст («2 шт», «300 г»), не парситься; дуже довгий amount ламає рядок інгредієнта.
- [ ] ⚪ Дуже багато обраних страв → панель «Обрані» і пікер меню — довгі списки без пошуку/пагінації.

## 11. Продуктивність і надійність (гонки зміни стану запасів, markCooked, синхронізація з балансом/покупками)

- [ ] 🟠 **Гонки швидких кліків по перемикачу.** `handleStockState` async, без блокування кнопок під час запиту. Потрійний швидкий клік → кілька паралельних `PUT` (last-write-wins, порядок не гарантований) + кожен `OutOfStock` додає окрему позицію покупок.
- [ ] 🟠 **`finishCooking` — `Promise.all` без транзакції й без обробки помилок** (див. §9): частковий успіх лишає БД у змішаному стані, а клієнт — у повністю оптимістичному.
- [ ] 🟠 **`handleToggleFavorite`/`handleAddStock` без відкату** на помилку — оптимістичний стан «прилипає», навіть якщо сервер відмовив.
- [ ] 🟡 **`markCooked` не перевіряє, що страва взагалі готувалася/обрана** — будь-який валідний recipeId оновлює `LastCookedAt`. Плюс `DateTime.Now` vs `UtcNow` (неузгодженість часу).
- [ ] 🟡 **Синхронізація з балансом/покупками одноразова** (`useEffect([])`): зміни у Фінансах/Списку покупок в інших вкладках не відображаються в Їжі без перезавантаження; `inShopping` застаріває.
- [ ] 🟡 **Запис меню в localStorage на кожну зміну** (`useEffect([menu])`) — для частих правок дешево, але міжвкладковий last-write-wins губить правки іншої вкладки.
- [ ] ⚪ `productMap`/`recipeMap` перебудовуються на кожну зміну `products`/`recipes` (useMemo) — ок, але залежність `availability` від `productMap` + `stock` означає повний перерахунок наявності на будь-який тогл.
- [ ] ⚪ Відсутні індикатори «збереження…» для точкових дій (тогл стану, обране) — користувач не знає, завершився запит чи ні.

### Зведення найгостріших пунктів
1. 🔴 Forbidden-страви приховані лише у стрічці «Страви», але витікають у «Обрані», «Меню» і в overview-відповіді; сервер їх не фільтрує взагалі.
2. 🔴 IDOR: `stock`-ендпоінти не перевіряють власність `productId` (можна посилатися на чужий приватний продукт).
3. 🔴 Дублі у списку покупок: `OutOfStock` і готовка додають позиції без дедуплікації (сервер `AddItemAsync` не дедуплікує, клієнтський `inShopping` не консультується у шляху `OutOfStock`/готовки).
4. 🔴 Тижневе меню — лише `localStorage`: втрата даних, відсутність кросдевайс/міжвкладкової синхронізації, тиха деградація при пошкодженому JSON.
5. 🔴 a11y триступеневого перемикача та клікабельних `<div>`/модалок без семантики діалогу й клавіатури.
6. 🟠 Оптимістичні мутації без rollback/обробки помилок; `finishCooking` неатомарний.
7. 🟠 `addStockByName` створює користувацькі продукти без ліміту довжини/санітизації/нормалізації (сміття, дублі, вміст для не-React поверхонь).
