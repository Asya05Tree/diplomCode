# Adversarial review — Спільне: оболонка, навігація, автентифікація, інтеграція

> Системний (наскрізний) чек-лист. Це НЕ окрема вкладка, а спільні аспекти всього застосунку:
> оболонка (`App.jsx` → `Layout`), бічна навігація (`Sidebar.jsx`), i18n (`i18n/*`), глобальні стилі
> (`Layout.css`, `Sidebar.css`), HTTP-шар клієнта (`api/client.js`, `api/http.js`) та конфігурація
> сервера (`Program.cs`, `appsettings*.json`, `Services/JwtService.cs`, усі `Controllers/*`).
>
> Легенда пріоритету: **[critical]** — здатне скомпрометувати дані/акаунти; **[major]** — функційний
> дефект, помітний користувачу; **[minor]** — косметика/UX; **[audit]** — потрібно перевірити вручну
> по кожному модулю.
>
> **Головний системний висновок наперед:** клієнтські захисти (редіректи в `App.jsx`, фільтр пунктів у
> `Sidebar.jsx`) — це лише UX. Єдина реальна лінія оборони — `[Authorize]` + scope по `CurrentUserId`
> на кожному ендпоінті. Тому кожен пункт нижче треба перевіряти прямими HTTP-запитами (curl/Postman),
> а не лише через UI.

---

## 1. Оболонка застосунку та маршрутизація (App.jsx, захищені маршрути, редіректи)

Факти з коду: `AppContent` тримає `user`, `authChecked`, `themeMode/paletteStyle/palette`,
`studentType/isWorking/gender`. Публічні маршрути `/`, `/reg`, `/login`; захищена гілка `/app/*`
рендериться лише якщо `user` != null, інакше `<Navigate to="/" replace />`. Catch-all `*` → `/`.

- [ ] **[critical] «Захищені маршрути» існують лише на клієнті.** `<Route path="/app" element={user ? <Layout/> : <Navigate/>}>` нічого не захищає — це рендер React. Будь-хто з валідним (чи підробленим — див. §6) токеном б'є напряму в `/api/...`. Перевірити: витягти дані всіх модулів через curl із Bearer-токеном, узагалі не відкриваючи SPA. Очікування: кожен ендпоінт сам вимагає `[Authorize]` і сам фільтрує по `userId` (див. §7).
- [ ] **[major] `user` завантажується з `/api/auth/me`, але містить лише `{nickname, email}`** (AuthController.Me). Тобто весь стан авторизації на клієнті — «є будь-який валідний токен». Жодної ролі/скоупу. Перевірити, що немає UI, який покладається на «права», яких сервер не знає.
- [ ] **[major] Гонка `authChecked`:** поки `/me` не відповів, `if (!authChecked) return null` — білий екран. Перевірити при повільній/впалій мережі: `getMe` кидає → `.catch` прибирає токен, `.finally` ставить `authChecked=true` → користувача мовчки викидає на landing навіть якщо токен був валідний, а просто сервер тимчасово лежав. Тобто будь-який мережевий збій = примусовий вихід. Відрізнити 401 від 500/мережевої помилки тут не вміють.
- [ ] **[major] `handleAuthed`/`handleLogout` і стан профілю.** Після логіну `loadStudyStatus()` викликається без await і без обробки помилки (`.catch(()=>{})`). Якщо профіль не підвантажився — sidebar покаже урізане меню (немає study/work/cycle), хоча вони мали бути. Перевірити вхід при тимчасовій помилці `/api/health-profile`.
- [ ] **[major] Умовні вкладені маршрути дублюють гейт лише частково.** `work` і `cycle` мають клієнтський редірект (`isWorking ? <Work/> : <Navigate/>`, `gender==='female' ? <Cycle/> : <Navigate/>`), а **`study` — ні**: `<Route path="study" element={<Study/>}/>` рендериться завжди (сторінка сама показує «оберіть школяр/студент»). Непослідовно. Головне — жоден із трьох не захищений на сервері (§2).
- [ ] **[minor] `key={location.pathname}` на `.app-content`** ремонтує DOM при кожній зміні маршруту (навмисна fade-анімація). Перевірити, що це не скидає стан, який мав би пережити навігацію, і не плодить зайвих перемонтувань/перезапитів.
- [ ] **[minor] Catch-all `*` → `/`.** Для залогіненого користувача неіснуючий `/app/xyz` впаде в `*` → `/` → (бо `user`) `Navigate to="/app"`. Тобто 404 нечутно ковтається редіректом. Немає сторінки «не знайдено». Перевірити помилкові/застарілі закладки.
- [ ] **[audit] Прямий перехід за URL на кожен модуль** (вставити `/app/finance` тощо в адресний рядок, F5): переконатися, що працює перезавантаження (BrowserRouter потребує SPA-fallback на хостингу — на dev-сервері Vite ок, у проді треба перевірити rewrite).

## 2. Бічна навігація (Sidebar) та умовні модулі (study/work/cycle)

Факти: `NAV_ITEMS` (12 пунктів) фільтрується: `nav.study` ← `studentType in {pupil, student}`; `nav.work` ← `isWorking`; `nav.cycle` ← `gender==='female'`. Решта — завжди.

- [ ] **[critical] Гейтинг умовних модулів НЕ продубльовано на сервері.** `StudyController`, `WorkController`, `CycleController` мають лише `[Authorize]` + `CurrentUserId`; grep по `StudentType/IsWorking/Gender/UserProfile` у `StudyController.cs` — **0 збігів**. Отже будь-який залогінений користувач (чоловік, непрацюючий, не-студент) може напряму створювати/читати дані навчання, роботи й циклу через `/api/study/*`, `/api/work/*`, `/api/cycle/*`. Приховати пункт у меню — не захист. Перевірити: вимкнути всі три статуси в налаштуваннях, потім curl'ом POST'нути предмет/зміну/запис циклу. Очікуваний дефект: усе створюється.
- [ ] **[major] Розсинхрон меню та справжнього стану.** `isWorking/studentType/gender` беруться з `/api/health-profile` **окремим** запитом після `/me`. Якщо профіль оновили в іншій вкладці/пристрої — sidebar тут не знає, доки не перелогінишся. Перевірити зміну статі/роботи в одній сесії й стале меню в іншій.
- [ ] **[major] `gender` лише `'female'` відкриває цикл**, а реєстрація дозволяє «Жіноча/Чоловіча/Інша», і в Налаштуваннях лише «Жіноча/Чоловіча». Перевірити: що зберігає сервер для «Інша» і чи не застрягає користувач без доступу до циклу, якщо колись обрав «Інша». Також — чи немає шляху зробити `gender=female` через профіль-API без UI.
- [ ] **[major] Мертва гілка `!item.to`** (sidebar-item--disabled, tooltip «Скоро») — у поточному `NAV_ITEMS` усі пункти мають `to`, тож ця гілка недосяжна. Мертвий код + захардкоджений україномовний tooltip «Скоро» (не через `t()`). Прибрати або локалізувати.
- [ ] **[minor] Бренд-tooltip «Всетута» і `data-tooltip="Скоро"`/`data-tooltip-pos`** — захардкоджені рядки в розмітці (не i18n). Для en-локалі лишаться українськими.
- [ ] **[minor] Активний пункт** визначається `NavLink` + `end` лише для `/app`. Перевірити, що `/app/food` не підсвічує водночас «Календар», а вкладені стани (напр. `/app/study` з під-вкладкою) тримають підсвітку.
- [ ] **[minor] Логотип `alt=""`** (порожній) — для скрінрідера бренд-посилання озвучиться лише текстом «Всетута» поруч; прийнятно, але перевірити, що лінк має доступне ім'я.

## 3. Глобальні стилі, теми, палітри, адаптивність, перший кадр без блимання

Факти: тема/стиль/палітра читаються синхронно в ініціалізаторі `useState(getThemeMode)` і застосовуються як `className={theme-${mode}}`, `data-style`, `data-palette` на кореневому div. Адаптив — `@media (max-width:760px)` робить sidebar горизонтальним.

- [ ] **[major] Перший кадр без блимання — лише для теми/палітри, не для авторизації.** Тема справді без FOUC (читається до першого рендера). Але `authChecked` дає порожній екран (return null) до відповіді `/me` — це «блимання в нічого». Перевірити на повільному 3G: скільки триває білий екран.
- [ ] **[major] `data-palette`/`data-style`/`theme-*` виставляються на обгортці всередині `AppContent`, а не на `<html>`.** Якщо десь використовують `position:fixed` модалки з кольорами з CSS-змінних — перевірити, що змінні доступні (каскад від обгортки). Коментар у Layout.css прямо попереджає про баг із `containing-block` для fixed-модалок — перевірити, що модалки всіх модулів центруються по viewport, а не з'їжджають.
- [ ] **[audit] Контраст у всіх 7 палітр × 2 теми × 2 стилі (пастель/насичений).** `--color-accent-ink`, `--color-on-accent`, `--sidebar-hover` тощо. Перевірити WCAG AA для тексту пунктів sidebar і активного пункту (`text-shadow` як милиця для контрасту — ознака недостатнього контрасту). Особливо «Пастельний» стиль на світлій темі.
- [ ] **[major] Адаптив — єдиний брейкпоінт 760px.** Нижче — sidebar стає горизонтальною стрічкою `overflow-x:auto`. Перевірити: (а) чи влазять 12 пунктів, чи не ховається «Налаштування» за краєм без видимого скролу; (б) що робоча область під «липким» хедером-сайдбаром не підрізається; (в) модалки/шторки (drawer) на 360px ширині.
- [ ] **[minor] Анімація `fade-in-up` при кожній навігації** — для `prefers-reduced-motion` нема вимкнення. Перевірити наявність `@media (prefers-reduced-motion: reduce)` глобально (анімації появи, hover-transform sidebar, scale іконок).
- [ ] **[minor] Немає авто/системної теми** (лише Світла/Темна вручну) — зафіксовано у специфікації як намір, не баг, але перевірити, що відсутній `prefers-color-scheme` не ламає перший кадр.
- [ ] **[audit] Перевірити, що немає горизонтального скролу body** на жодній сторінці в жодній палітрі (широкі таблиці Фінансів/Навчання/Роботи мають скролитись у своєму контейнері).

## 4. Інтернаціоналізація (i18n) системно: повнота uk/en, збіг ключів, інтерполяція, fallback

Факти: `t(key, params)` → `dict[key] ?? key`; інтерполяція `text.replace('{name}', val)`. `uk.json` і `en.json` мають **по 1018 рядків-ключів** (однакова кількість, але це НЕ доводить збіг множин ключів).

- [ ] **[critical для якості] Відсутній ключ показується користувачу як сам ключ.** `dict[key] ?? key` → на екрані буде `finance.someMissingKey`, а не текст. Перевірити: програмно звести множини ключів `uk.json` vs `en.json` (а не лише count 1018=1018) — symmetric diff має бути порожнім. Рівна кількість легко маскує «в uk є A, нема B; в en навпаки».
- [ ] **[major] Інтерполяція замінює лише ПЕРШЕ входження плейсхолдера.** `String.prototype.replace` без `/g`. Якщо переклад містить `{name}` двічі (напр. en-формулювання) — друге лишиться літералом `{name}`. Перевірити всі ключі з повторюваними плейсхолдерами в обох мовах.
- [ ] **[major] Немає форм множини (pluralization).** Лічильники «лишилось {n}», «{count} задач», «{n} міс. тому» підставляються в єдиний рядок. Українська має 3 форми множини (1 задача / 2 задачі / 5 задач), англійська — 2. Перевірити всі місця з числами: буде граматично некоректно (напр. «5 задача»).
- [ ] **[major] Відсутня валідація плейсхолдерів між мовами.** Якщо uk-рядок має `{from}`/`{to}`, а en-рядок — ні (або інші назви), підстановка тихо не спрацює. Перевірити парність імен плейсхолдерів у кожному спільному ключі.
- [ ] **[major] Захардкоджені рядки поза i18n.** Знайдено: бренд `Всетута`, tooltip `«Всетута»`, `data-tooltip="Скоро"` у `Sidebar.jsx`; `ProductName` у appsettings. Прогнати grep по JSX на кириличні літерали поза `t(...)` — усі такі місця не перекладаються в en.
- [ ] **[minor] Дата/час/тиждень формуються окремо** (`formatDate/formatTime/formatClock`, `weekStart`) і не залежать від `language` — перевірити, що назви місяців/днів беруться з того ж словника, що й активна мова (інакше en-UI з українськими днями тижня).
- [ ] **[audit] Мертві (невикористані) ключі.** Для кожного з 1018 ключів перевірити, чи є `t('key')` у коді. Невживані роздувають bundle і плутають перекладача. Автоматизувати: grep кожного ключа по `client/src`.
- [ ] **[minor] `weekdaysShort` парситься через `.split(',')`** — крихко: зайвий пробіл/кома в перекладі зсуне всі дні. Перевірити обидві мови.

## 5. Доступність (a11y) системно: клавіатура, фокус, модалки/drawer, контраст, скрінрідери

- [ ] **[major] Фокус-пастки й ESC у модалках/шторках по ВСЬОМУ застосунку.** Модалок/drawer багато: планування візиту (Health), типи/графік змін + модалки (Work), шторка вводу ціни (ShoppingList), вікно готовки (Food), модалка підтвердження швидкого додавання (QuickAdd), модалки видалення даних/акаунта (Settings), меню дня в календарях (Planner/Cycle). Для КОЖНОЇ перевірити: (а) фокус переходить усередину при відкритті; (б) Tab/Shift+Tab не виходить за межі (focus trap); (в) Esc закриває; (г) фокус повертається на елемент-ініціатор при закритті; (д) клік по бекдропу закриває; (е) `role="dialog"`/`aria-modal`/`aria-labelledby`.
- [ ] **[major] Навігація з клавіатури по sidebar.** `NavLink` фокусується, але disabled-пункт — це `<div>` (недосяжний із клавіатури й без `aria-disabled`). Перевірити видимий фокус-рінг на всіх пунктах.
- [ ] **[major] `confirm()`-діалоги** (дедуплікація контактів у Work, можливо інші) — нативні, виривають фокус і не стилізуються; перевірити, що критичні підтвердження (видалення акаунта/даних) не покладаються на `window.confirm`, а мають доступну модалку.
- [ ] **[audit] Тристани-перемикачі (Є/Закінчується/Немає)** у Food/Health — перевірити, що це доступні радіо/кнопки з підписами для скрінрідера, а не лише колір.
- [ ] **[minor] Іконки Heroicons** у кнопках-діях (готово/видалити/перенести) — перевірити `aria-label`, бо кнопки часто лише з іконкою.
- [ ] **[minor] Полотно «Дошка» (Notes)** — `<canvas>` недоступне для скрінрідера за визначенням; перевірити наявність текстової альтернативи/попередження.
- [ ] **[audit] Контраст активного пункту sidebar** (градієнт + `text-shadow`) у всіх палітрах — див. §3.
- [ ] **[minor] Мова документа.** Перевірити, що `<html lang>` змінюється разом із `settings:language` (uk/en) — зараз мова тримається в контексті, але атрибут `lang` на `<html>`, схоже, не оновлюється.

## 6. Автентифікація/сесія (JWT)

Факти: `JwtService` — HS256, claims `sub`+`email`, **термін дії 90 днів**, без refresh. Токен у `localStorage['authToken']`, додається як `Bearer`. Валідація: Issuer/Audience/Lifetime/SigningKey = true. Вихід = `localStorage.removeItem` + `navigate('/')`.

- [ ] **[critical] JWT у `localStorage` → викрадення через XSS.** Будь-який інжектований скрипт (чи вразлива залежність) читає `localStorage.getItem('authToken')` і виносить токен. Немає `HttpOnly`-cookie. Оскільки токен живе 90 днів і не відкликається — викрадений токен = повний доступ на 3 місяці. Рекомендація до перевірки: чи є хоч одна точка innerHTML/dangerouslySetInnerHTML (§8), яка робить XSS можливим.
- [ ] **[critical] Немає серверного відкликання/виходу.** `handleLogout` лише стирає `localStorage`. Якщо токен уже скопійований — «Вийти» його не вбиває, він валідний 90 днів. Перевірити: зберегти токен, натиснути «Вийти», потім curl'ом із тим самим токеном — дані все ще доступні (очікуваний дефект). Немає blacklist/token-version/`SecurityStamp`.
- [ ] **[critical] Підроблений/непідписаний токен.** Перевірити: (а) `alg:none` — має відхилятись (ValidateIssuerSigningKey=true, тож ок, але підтвердити); (б) токен, підписаний іншим ключем, → 401; (в) **ключ за замовчуванням `CHANGE_ME_TO_A_LONG_RANDOM_SECRET_IN_PRODUCTION` лежить у `appsettings.json` у репозиторії** (§8) — якщо задеплоять як є, будь-хто підробить токен для довільного `sub` і зайде під будь-яким акаунтом. Це найсерйозніший ризик.
- [ ] **[major] Протермінований токен.** `ValidateLifetime=true` → 401 після 90 днів. Клієнт: будь-який 401 у `getMe` на старті → токен прибирається, користувач на landing. Але 401 у звичайних запитах (`apiGet/apiSend`) НЕ обробляється глобально як «розлогінь» — `throwApiError` просто кидає Error, і сторінка показує загальну помилку, не викидаючи на вхід. Перевірити поведінку, коли токен протух під час роботи (застряг у «залогіненому» UI з усіма запитами 401).
- [ ] **[major] `ClockSkew` за замовчуванням 5 хв** не критично при 90-денному житті, але перевірити, що немає сюрпризів із UTC (`DateTime.UtcNow` всюди).
- [ ] **[major] Нема rate-limiting на `/api/auth/login`.** Credential stuffing/brute-force пароля без лімітів і без лок-ауту. `invalid_credentials` однаковий для «нема юзера» і «невірний пароль» (добре — без enumeration), АЛЕ `/api/auth/send-code` повертає `email_taken` → enumeration зареєстрованих email (§8).

## 8. Безпека системно (XSS/CSP, CSRF, CORS, заголовки, секрети, логування, HTTPS, залежності)

- [ ] **[critical] Секрети в репозиторії.** `.gitignore` НЕ виключає `appsettings*.json`. У git лежать: (а) `appsettings.json` → `Jwt:Key = "CHANGE_ME_TO_A_LONG_RANDOM_SECRET_IN_PRODUCTION"` (плейсхолдер-ключ підпису токенів!); (б) `appsettings.Development.json` → рядок підключення MySQL з паролем `planner_dev_password`, а також `Billing.WayForPay.MerchantSecretKey = "flk3409refn54t54t*FNJRET"` і `MerchantAccount=test_merch_n1`. SMTP порожній (ок). **Дія:** винести всі секрети в user-secrets/ENV, додати `appsettings*.json` (окрім шаблонного) у `.gitignore`, ПЕРЕГЕНЕРУВАТИ всі ключі (історія git уже скомпрометована), згенерувати довгий випадковий `Jwt:Key`, і додати перевірку на старті, що ключ != плейсхолдер.
- [ ] **[critical] Якщо `Jwt:Key` лишиться плейсхолдером у проді** — токени підробляються будь-ким (див. §6). Перевірити, що немає шляху запустити сервер із дефолтним ключем.
- [ ] **[major] CORS — дев-політика застосовується завжди.** `app.UseCors(DevClientPolicy)` викликається беззастережно (не лише в `IsDevelopment`), а політика жорстко прибита до `http://localhost:5173` з `AllowAnyHeader/AllowAnyMethod`. У проді (інший origin) CORS не дозволить клієнта, або доведеться міняти код. Перевірити, що origin конфігурований через ENV, а не захардкоджений. (Credentials не вмикаються — токен у заголовку, не cookie, тож `AllowCredentials` не потрібен.)
- [ ] **[major] Немає заголовків безпеки.** У `Program.cs` відсутні: HSTS, `UseHttpsRedirection`, CSP, `X-Content-Type-Options: nosniff`, `X-Frame-Options`/`frame-ancestors` (клікджекінг), `Referrer-Policy`, `Permissions-Policy`. Додати middleware. CSP особливо важлива, бо токен у localStorage (пом'якшує XSS-крадіжку).
- [ ] **[major] HTTPS.** Немає `UseHttpsRedirection`/HSTS. Bearer-токен ходить відкрито, якщо задеплоять по http. Перевірити конфіг реверс-проксі/хостингу.
- [ ] **[major] CSRF.** Токен передається вручну в `Authorization`-заголовку (не cookie) → класичний CSRF не застосовний (добре). АЛЕ `[AllowAnonymous]` ендпоінти білінгу (`/api/billing/callback`, `/api/billing/return`) приймають зовнішні POST — перевірити, що callback ОБОВ'ЯЗКОВО валідує HMAC-підпис WayForPay (інакше хто завгодно підтвердить оплату й розблокує фічу безкоштовно). `return` робить лише редірект із `orderReference` із query — переконатися, що він нічого не зараховує (саме зарахування — у `confirm`, що `[Authorize]` і перевіряє статус на боці WayForPay).
- [ ] **[critical] Білінг-callback = довірена межа.** Перевірити `BillingService.HandleCallbackAsync`: чи звіряє підпис секретом, чи не можна підробленим POST'ом на `/api/billing/callback` позначити чужий `orderReference` оплаченим. Також `/api/billing/confirm` — чи реально перевіряє статус у WayForPay, чи в mock-режимі (`Billing:Mock=true` за замовчуванням!) просто вертає `paid=true`. У проді `Mock` має бути `false`.
- [ ] **[major] XSS.** Прогнати grep по `dangerouslySetInnerHTML`/`innerHTML` у клієнті. React екранує за замовчуванням, але нотатки/відгуки/опис — користувацький текст; перевірити, що ніде не рендериться як HTML. Дошка-canvas і JPEG-експорт — безпечні.
- [ ] **[major] Логування.** `Logging.LogLevel` для EF Core = `Information` у Development → у логи потрапляють SQL із параметрами (можливо з PII/паролями при реєстрації? Ні — пароль хешується, але email/коди видно). Переконатись, що в проді не логуються коди підтвердження, токени, тіла запитів auth/billing.
- [ ] **[major] Валідація вводу на сервері.** Нікнейм/email/пароль валідуються (regex, gmail-only, довжина 6..72). Перевірити інші модулі: чи є ліміти довжини (нотатка 280, опис 300 — чи форсить сервер, а не лише клієнт?), числові кламп-межі (баланс 0..1млрд, вага/вік/зріст), інакше можна записати гігантські/від'ємні значення прямим API.
- [ ] **[major] Коди підтвердження.** 6-значний, 10 хв, `Random.Shared` (НЕ криптостійкий — для кодів краще `RandomNumberGenerator`). Немає ліміту спроб вводу коду й ліміту надсилань → брутфорс коду (10^6, але 10 хв вікно) та email-флуд через `/api/auth/send-code` (немає rate-limit). Перевірити.
- [ ] **[major] Enumeration.** `/api/auth/send-code` і `/api/auth/register` повертають `email_taken` → зловмисник перевіряє, чи зареєстрований email. Login — generic (добре). Зважити, чи прийнятно.
- [ ] **[audit] Залежності.** `npm audit` для клієнта (react 19, react-router 7, vite 8, oxlint) і `dotnet list package --vulnerable` для сервера (BCrypt.Net, JwtBearer, Pomelo MySQL, HttpClient). Зафіксувати відомі CVE.
- [ ] **[minor] Паролі — BCrypt** (добре), work factor за замовчуванням; підтвердити, що не обрізаються >72 (сервер уже відкидає >72 — ок).

## 9. Інтеграція модулів (спільний календар moduleCode; осиротілі події; консистентність)

Факти: календарні сутності несуть `ModuleCode` + опційні `SourceModule`/`SourceEntityId` (для разових задач) або прив'язку через `RecurrenceRuleId` (для правил). `DeleteTaskAsync(cascadeSource=true)` каскадить у джерело **ЛИШЕ для `SourceModule=="media"`**. `DeleteRecurrenceRuleAsync` видаляє правило + шаблон-задачу, але НЕ чіпає `WorkShiftEntry`/`StudyScheduleEntry`, що посилаються на `RecurrenceRuleId`.

- [ ] **[critical] Осиротілі ПРАВИЛА повторення (Work/Study).** `WorkService.AddScheduleEntryAsync` і графік змін створюють `RecurrenceRule` і зберігають `RecurrenceRuleId` у `WorkShiftEntry`; `StudyService` так само для пар (`moduleCode="study"`). Якщо користувач видалить це правило з планувальника (режим «Повторювані» → `DeleteRecurrenceRuleAsync`), рядок `WorkShiftEntry`/`StudyScheduleEntry` лишиться вказувати на НЕіснуюче правило. Наслідки: календар змін тихо дропає (бо `rules.ContainsKey(...)` фільтрує), але на вкладці Робота/Навчання запис графіка/розкладу або зникне з календаря, або зламає рендер. **Перевірити:** створити зміну/пару → видалити відповідне правило в «Повторюваних» → відкрити Роботу/Навчання. Очікуваний дефект: висяча прив'язка, неузгоджений стан.
- [ ] **[critical] Осиротілі ДЖЕРЕЛА при видаленні події з календаря (health/work).** `CheckupService` створює задачу `sourceModule="health"`, `WorkService.AddMeetingAsync` — задачу з `meeting.TaskId`, process-задачі — `p.TaskId`. Але `DeleteTaskAsync` каскадить лише `"media"`. Тож видалення в календарі **візиту до лікаря** або **робочої зустрічі** видалить задачу, але ЗАЛИШИТЬ запис візиту/зустрічі з `TaskId`, що вказує в нікуди. **Перевірити кожну пару:**
  - [ ] Watchlist ↔ календар: видалив медіа-сеанс у календарі → зник запис у Watchlist? (має — cascade media) І навпаки: видалив запис у Watchlist → зникла подія? (MediaController робить це сам — перевірити).
  - [ ] Health візит ↔ календар: видалив подію візиту в календарі → лишився осиротілий візит у «Чекап»? (очікуваний дефект — немає каскаду health).
  - [ ] Work зустріч ↔ календар: видалив подію зустрічі → лишилась зустріч у Work? (очікуваний дефект).
  - [ ] Work process-задача ↔ календар: те саме.
  - [ ] Study пара ↔ календар, Work зміна ↔ календар: видалення правила (див. вище).
  - [ ] Cycle ↔ календар: дні менструації відмічаються в обох — перевірити двобічну синхронність (Planner DayView «Місячні: Початок/Кінець/Прибрати» ↔ Cycle).
- [ ] **[major] Зворотний бік — видалення джерела лишає інстанси?** Коли джерело видаляє задачу через `DeleteTaskAsync(cascadeSource:false)` — чи прибираються майбутні віртуальні інстанси/нагадування/нерозподілені, породжені нею?
- [ ] **[critical] Консистентність балансу Фінансів у наскрізних розрахунках.** Баланс (`Finance.SetBalanceAsync`) використовується в: підборі страв «у межах балансу» (Food ціновий діапазон), «Докупити в межах бюджету» (ShoppingList), ShoppingTaskTabs (QuickAdd «Піти в магазин» → `findMaximalCombos` по балансу). Перевірити: (а) усі читають ОДНЕ й те саме значення; (б) витрата при «куплено» (ShoppingList check із ціною пише транзакцію-витрату) оновлює баланс/нетто, і наступний підбір бачить новий бюджет; (в) немає кешу, що показує стару суму.
- [ ] **[critical] Консистентність запасів Їжі ↔ Список покупок.** Потоки в обидва боки: закінчився інгредієнт під час готовки (Food «вікно готовки») → авто-додається в Список покупок; стан запасу «Немає»/«Закінчується» → у покупки; відмітка «куплено» в ShoppingList із `ProductId` → поповнює запас; `addStockByName` із QuickAdd. Перевірити: (а) немає дублів у списку покупок при повторному «закінчився»; (б) купівля справді повертає стан запасу в «Є»; (в) медичні позиції (ліки «Закінчується» → розділ «Аптека») так само поповнюють скриньку, а не лише список.
- [ ] **[major] Транзакція при купівлі** (ShoppingList check → FinanceService витрата + ShoppingService поповнення запасу + фіксація ціни). Це кілька записів у РІЗНИХ сервісах — перевірити атомарність: якщо один крок упаде, чи не лишиться напіввиконаний стан (списано ціну, але запас не поповнився, або навпаки). Чи є транзакція БД?
- [ ] **[audit] moduleCode-фільтрація в календарі.** Перевірити, що задачі з усіх модулів (`tasks/media/health/work/study/cycle`) коректно показуються й розрізняються в Planner, і що «Важливі борги» (Study+Work прострочені) та «Нерозподілені» рахуються по правильних `moduleCode`.

## 10. Надійність та продуктивність системно

- [ ] **[major] N+1 та ефективність запитів.** `GetRecurrenceRulesAsync` робить `Include` + окремий запит шаблонів + `ToDictionary` (норм). Перевірити по сервісах важкі місця: `GetScheduleCalendarAsync` (розгортання правил у діапазон), `GetOverviewAsync` (Food — продукти+рецепти+інгредієнти+наявність), `GetStatsAsync` (Finance — агрегація по тижнях). Прогнати з увімкненим EF-логом SQL на акаунті з багатьма записами; шукати запити в циклі.
- [ ] **[critical] Відсутня пагінація.** Жоден list-ендпоінт (транзакції, задачі за період, медіа, контакти, ліки) не має пагінації/ліміту — `ToListAsync()` тягне все. Перевірити поведінку на 1000+ транзакцій/задач: розмір відповіді, час, рендер таблиць без віртуалізації. Період календаря обмежений місяцем (добре), але Історія Фінансів/Нерозподілені — ні.
- [ ] **[major] Обробка помилок мережі на клієнті — непослідовна.** `apiGet/apiSend` кидають Error; `getMe`/`login` мають власні. Немає глобального перехоплювача 401/5xx/offline. Перевірити КОЖЕН модуль: чи показує стан loading і стан error, чи не зависає на «порожньо» при помилці (помилку легко сплутати з порожнім списком).
- [ ] **[audit] Стани loading/error/empty скрізь.** Для кожної сторінки перевірити три стани: завантаження (скелет/спінер), помилка (повідомлення + ретрай), порожньо (текст). Специфікація згадує лише empty-стани — ризик, що loading/error відсутні.
- [ ] **[major] Ретраї/ідемпотентність.** Подвійний клік по «Створити»/«Додати»/«Відмітити» при повільній мережі → дублі (немає ідемпотентних ключів). Перевірити debounce/disabled-під-час-запиту на всіх сабмітах (QuickAdd «Створюємо…» має це; інші?).
