# Adversarial review — Перегляд і читання (Watchlist)

> Обсяг: `client/src/pages/Watchlist.jsx`, `client/src/pages/Watchlist.css`, `client/src/utils/watchlistTaxonomy.js`, `client/src/utils/validation.js`, `client/src/api/media.js`, `server/Controllers/MediaController.cs`, `server/Models/MediaItem.cs`, `server/Services/TaskService.cs`, ключі `client/src/i18n/uk.json`.
>
> Легенда: `[ ]` — перевірити. Позначка **БАГ/РИЗИК** — підтверджений у коді дефект або небезпечна поведінка; **ПИТАННЯ** — вимагає рішення/уточнення; решта — регресійні перевірки.

## 1. Фронтенд — сторінка, дворівневі вкладки (вид×статус), логіка

- [ ] Дворівнева структура: під-вкладки `KINDS` (video/book) × вкладки статусу `STATUSES` (planned/in_progress/done) + `DEBT_STATUS` (лише книги). Перевірити, що вкладка «Борги» рендериться тільки для `kind === 'book'` (`statuses = kind === 'book' ? [...STATUSES, DEBT_STATUS] : STATUSES`).
- [ ] `switchKind` скидає `genreFilter`, `typeFilter`, `draft` і при переході на відео примусово відводить зі статусу `debt` на `planned`. Перевірити зворотний бік: `switchKind` **НЕ** скидає відкритий поповер `sched`, `editId`, `editForm`, `reviewEditId`, `edits`. **ПИТАННЯ:** відкрити планування/редагування картки книги → перемкнути на «Відео» → стан поповера зберігається; картка не видима, тож поповер не рендериться, але при поверненні на «Книги» він «вистрибує» знову. Перевірити, що це не плутає користувача і що `submitSchedule`/`handleSaveEdit` не застосують дані до не того запису.
- [ ] Лічильники вкладок: `counts.planned`/`in_progress` рахують `!it.isDebt`, `done` рахує всі `done`, `debt` рахує `it.isDebt`. Переконатися, що боржницька книга **не враховується** у «У процесі»/«У планах» (не подвійний облік).
- [ ] Один набір станів-поповерів на всю сторінку (`sched`, `editId`, `reviewEditId` — скаляри). Перевірити, що відкриття редагування на другій картці не лишає «висіти» форму на першій. `startEdit` чистить `reviewEditId`, але `openSchedule` **не чистить** `editId`, а `startReview` не чистить `sched`. **РИЗИК:** одночасно виставлені `editId` і `sched` для одного `item` → рендер віддає пріоритет `sched` (перша гілка тернарника), форма редагування «зникає» без явного скасування.
- [ ] Кнопка «Завершити» показується для будь-якого не-`done` (зокрема для `planned`). Перевірити, що завершення прямо з «У планах» (минаючи планування) — свідома поведінка: створюється `done` без `StartDate`, без події календаря. **ПИТАННЯ:** чи коректно, що бібліотечна книга, завершена з «У планах», лишається з активним нагадуванням про повернення й невидима в «Боргах» (бо `IsDebt` виключає `done`), хоча фізично не повернена.
- [ ] Форма додавання рендериться лише в `status === 'planned'`. Перевірити, що в інших вкладках додати не можна (і що це узгоджено з бекендом — `Add` завжди ставить `Status="planned"`).
- [ ] Повторний клік по активній зірці скидає рейтинг у 0 (`onChange(n === value ? 0 : n)`). Перевірити, що 0 → `rating || null` → `null` на сервер (очищення рейтингу працює).

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, сітка карток

- [ ] Усі кольори беруться зі змінних теми (`--color-*`), жодного хардкоду, крім `#f5b301` для активної зірки (`.watch-star--on`). **Перевірити** контраст цього жовтого в темній темі (фіксований колір на темному тлі) і що він читається.
- [ ] Сітка карток `grid-template-columns: repeat(auto-fill, minmax(240px, 1fr))`. Перевірити на вузькому екрані (320px): `minmax(240px,…)` + `padding: clamp(16px…)` — чи не виникає горизонтального скролу (240px картка + падінги сторінки можуть перевищити 320px).
- [ ] Адаптив: єдиний медіа-запит `@media (max-width: 600px)` робить `.watch-add .btn-accent` на всю ширину. Перевірити тулбар (пошук+2 селекти) і ряд під-вкладок/статусів на 360px — вони `flex-wrap`, але перевірити, що лічильники/іконки не ламають рядок некрасиво.
- [ ] Довгий заголовок: `.watch-card-title { word-break: break-word }` — ок. **Але** `.watch-card-author` не має `word-break`; хоча автор фільтрується до літер (без суцільних довгих токенів), перевірити дуже довге прізвище без пробілів.
- [ ] `.watch-library` (бібліотечна примітка) та `--debt` варіант: переконатися, що тривожне (danger) забарвлення боргу видиме в обох темах і не зливається з `--color-danger-soft`.
- [ ] Поповер `.watch-sched` (dashed border, accent-soft фон) та форма редагування використовують один клас — перевірити, що в темній темі читається текст/інпути.
- [ ] Анімація `anim-fade-in-up` на кожній картці: перевірити, що при великому списку (сотні карток) немає ривків і що анімація не програється повторно на кожному `reload()` (ремоунт → повторний fade).
- [ ] Сітка `align-items: start` — картки різної висоти не розтягуються. Перевірити вигляд ряду, де одна картка має блок відгуку/зірок, а сусідні — ні.

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо), пошук/фільтри

- [ ] Стани: `loading` → `common.loading`; `error` → `common.error`; порожній список → `watchlist.empty` («Порожньо»). **РИЗИК:** стан `error` — глухий кут, немає кнопки «повторити»; тулбар/вкладки взагалі не показуються. Єдиний вихід — перезавантаження сторінки.
- [ ] Порожня назва: `handleAdd` робить `title.trim()` і при порожньому `return` (тихо, без повідомлення). Перевірити, що кнопка «Додати» при порожньому полі не дає зворотного зв'язку (жодного disabled/помилки).
- [ ] `limitText(…, MAX_LEN.title=120)` на назві + `maxLength={120}` в атрибуті. Перевірити вставку тексту >120: обрізається. Автор: `filterWords(…, MAX_LEN.name=60)` + `maxLength={60}`.
- [ ] **БАГ (UX-копірайт):** плейсхолдер пошуку `watchlist.searchPlaceholder` = «Пошук за назвою…», але код шукає й за автором: `(it.title||'').includes(q) || (it.author||'').includes(q)`. Плейсхолдер вводить в оману (ОПИС і логіка кажуть «за назвою **та** автором»).
- [ ] Пошук регістронезалежний: `search.trim().toLowerCase()` проти `.toLowerCase()` полів. Перевірити кирилицю (укр. великі/малі), змішаний регістр.
- [ ] Спецсимволи в пошуку: використовується `String.includes` (НЕ regex) → безпечно від regex-ін'єкцій (`.*`, `[`, `(` трактуються буквально). Перевірити пошук за `.` чи `(` — має шукати літерал.
- [ ] Діакритика/нормалізація: пошук не робить Unicode-нормалізацію (NFC/NFD). «café» (введене з комб. акцентом) може не знайтися за «cafe». Малоймовірно для цього поля, але зафіксувати.
- [ ] `maxLength` пошукового інпута = `MAX_LEN.title` (120) — довільно велике для поля пошуку; перевірити, що не заважає.
- [ ] Фільтр за жанром застосовується до обох видів; фільтр за видом — лише `kind === 'video'` (`typeFilter` ігнорується для книг). Перевірити.
- [ ] **ПИТАННЯ (стала фільтра):** `genreFilter`/`typeFilter` скидаються лише у `switchKind`, не при зміні статусу. Перевірити, що перемикання статусних вкладок зберігає фільтр (очікувано), і що жоден фільтр не містить ключа чужого виду (бо скидається при зміні виду).
- [ ] Форма: `genre`/`type`/`author`/`isLibrary`/`returnDeadline` — усі необов'язкові, крім назви. Перевірити, що додавання лише з назвою створює запис.

## 4. Інтернаціоналізація (i18n) — назви жанрів/видів uk/en, невідомі ключі

- [ ] Назви жанрів/видів беруться з `watchlistTaxonomy.js` (`language === 'en' ? g.en : g.uk`), а **не** з i18n-json — тож завжди локалізовані навіть без запису в `en.json`. Перевірити повноту пар uk/en у `VIDEO_TYPES`, `VIDEO_GENRES`, `BOOK_GENRES`.
- [ ] Статусні/кнопкові підписи йдуть через `t('watchlist.*')`. Перевірити, що для `language === 'en'` існує `en.json` з ключами `watchlist.*` (інакше покажеться сирий ключ або fallback). У `uk.json` ключі присутні (рядки 561–594).
- [ ] **Невідомий ключ жанру/виду:** `genreName`/`typeName` → `label()` повертає `key` як є, якщо не знайдено (`if (!item) return key || ''`). Перевірити сценарій: у БД збережено ключ, якого вже немає в довіднику (наприклад після зміни таксономії) → у бейджі показується сирий англ. ключ (`"documentary"`), не локалізований. **РИЗИК** регресії при зміні наборів.
- [ ] Збіги ключів між наборами: `scifi/fantasy/detective/melodrama/thriller` є і у відео, і в книгах, але з різними людськими назвами (`thriller`: відео «Трилер» vs книга «Трилер / жахи»). Перевірити, що `genreName(key, lang, item.kind)` передає саме `item.kind`, а не поточний `kind` сторінки (у картці — `item.kind` ✓).
- [ ] Відгук/назва/автор, введені кирилицею/латиницею, коректно відображаються незалежно від мови інтерфейсу (це дані, не переклад).
- [ ] Текст «Повернути до {date}» (`watchlist.returnBy`) форматує дату через `formatDate` — перевірити відповідність обраному в Налаштуваннях формату дати для uk/en.
- [ ] Назви службових подій календаря («Подивитися: », «Прочитати: », «Повернути книгу: ») **захардкоджені українською** на сервері (`MediaController`), незалежно від мови користувача. **ПИТАННЯ:** англомовний користувач побачить укр. префікси у календарі.

## 5. Доступність (a11y): зірки-рейтинг, чекбокси, фокус

- [ ] **БАГ (a11y):** зірки — `<button aria-label={`${n}`}>` — мітка лише число («1»…«5») без контексту «зірок/stars/рейтинг». Скрінрідер промовляє «1, кнопка». Немає `aria-label` на контейнері з поточним значенням рейтингу.
- [ ] ReadOnly-зірки (`<Stars readOnly />`) рендеряться як `disabled` кнопки — група disabled-кнопок без ролі `img`/тексту «оцінка N з 5». Перевірити подачу рейтингу асистивним технологіям у «Завершено» (перегляд).
- [ ] Символ `★` — текстовий вміст кнопки (не приховано від AT як декоративний) → дублюється з `aria-label`. Перевірити «балакучість» скрінрідера.
- [ ] Чекбокси «Повернено» та «Бібліотечна книга» обгорнуті `<label>` з текстом — асоціація є ✓. Перевірити, що `disabled` чекбокс «Повернено» (після повернення) має зрозумілий стан для AT.
- [ ] **БАГ (фокус):** відкриття поповерів планування/редагування/відгуку **не переміщує фокус** у форму; закриття (Скасувати/збереження) не повертає фокус на кнопку-ініціатор. Немає focus-trap і обробки `Esc` для закриття поповерів.
- [ ] Кнопки-іконки «Редагувати»/«Видалити»/олівець мають `aria-label` і `data-tooltip` ✓. Перевірити, що тултіп (`data-tooltip`) доступний і з клавіатури (hover-only тултіпи недоступні).
- [ ] Клавіатурна навігація по вкладках виду/статусу: це `<button>` у ряд — Tab працює, але немає `role="tablist"`/`aria-selected`/стрілкової навігації між вкладками. **ПИТАННЯ:** чи достатньо для вимог.
- [ ] Поле `type="date"`/`type="time"` — перевірити доступність нативних пікерів і що відсутність `min` (у редагуванні) не плутає AT.
- [ ] Контраст плейсхолдерів і `--color-text-muted` у бейджах/примітках — перевірити WCAG AA в обох темах.

## 6. Бекенд — API, статус-коди, валідація жанрів/видів (allowlist)

- [ ] `Add`: `kind` нормалізується (`Trim().ToLowerInvariant()`) і перевіряється по `Kinds {video,book}` → інакше `400 invalid_kind`. Порожня/пробільна назва → `400 missing_title`. Перевірити обидва.
- [ ] **Жанр/вид — allowlist, але БЕЗ відмови:** `CleanGenre`/`CleanType` при невідомому ключі повертають `null` (тихо), а не `400`. Перевірити: POST з `genre:"<script>"` чи `genre:"xxx"` → запис створюється з `genre=null`, статус `200`. Клієнт не отримує жодного сигналу про відкинутий жанр. **ПИТАННЯ:** прийнятно чи треба 400/валідацію.
- [ ] `CleanType` повертає `null`, якщо `kind != "video"` — вид неможливо задати книзі навіть напряму через API. Перевірити POST книги з `mediaType:"film"` → `null`.
- [ ] Жанр валідується по набору **за видом**: відео з `genre:"poetry"` (книжковий ключ) → `null`; книга з `genre:"documentary"` → `null`. Перевірити перехресні ключі.
- [ ] `Schedule`: якщо `item.Status != "planned"` → `400 already_scheduled`. Неіснуючий `id` → `404`. Перевірити.
- [ ] `SetStatus`: невідомий цільовий статус → `400 invalid_status`; крок назад/на місце (`targetIdx <= currentIdx`) → `400 backward_not_allowed`; ціль `in_progress` → `400 use_schedule`. Перевірити всі три.
- [ ] `Update`: порожня назва → `400 missing_title`; неіснуючий id → `404`.
- [ ] `SetReturned`: не-бібліотечний запис → `400 not_library`; неіснуючий → `404`. Повторний виклик з тим самим станом (`Returned==IsReturned`) → ідемпотентно повертає `200` без змін. Перевірити.
- [ ] `Delete`: неіснуючий → `404`; успіх → `200` (без тіла або `{deleted:true}` у return-гілці). Перевірити консистентність форматів відповіді.
- [ ] Числові/рядкові межі на сервері (дзеркало клієнта): `TitleMax=120`, `AuthorMax=60`, `ReviewMax=200` — збігаються з `MAX_LEN`. `DurationMinutes` клампиться `1..1440`. Перевірити, що клієнтські `MAX_LEN` і серверні константи не розійдуться (дубльовані «магічні числа» в двох місцях).
- [ ] Усі ендпоінти під `[Authorize]`; без JWT → `401`. Перевірити.
- [ ] `Get` не має пагінації — повертає всі записи користувача. Перевірити поведінку на дуже великому списку (див. §11).

## 7. Авторизація та власність (IDOR над чужими записами медіа / подіями календаря)

- [ ] Усі запити скоплені `x.UserId == CurrentUserId` (`Get`, `Schedule`, `SetStatus`, `Update`, `Delete`, `SetReturned`). Перевірити кожен ендпоінт із чужим `id` → має бути `404` (не `403` з витоком існування, але й не доступ).
- [ ] `CurrentUserId` береться з JWT-claim `sub` (`User.FindFirst(Sub)!.Value`) — клієнт **не передає** userId у тілі. Перевірити, що жоден DTO не містить `UserId` (немає mass-assignment власності).
- [ ] **IDOR над `taskId` події календаря:** клієнт **ніде не надсилає** `taskId`. `scheduleMedia` не приймає taskId; `updateMedia(…, startDateTime)` використовує **серверний** `item.TaskId` (не з запиту). Перевірити, що немає шляху передати довільний `taskId` → не можна перепризначити/зачепити чужу подію.
- [ ] `TaskService.UpdateTaskAsync`/`DeleteTaskAsync` також фільтрують `t.UserId == userId`. Перевірити, що навіть якби `item.TaskId` вказував на чужу задачу (неможливо штатно), сервіс не чіпав би чужу.
- [ ] `RemoveReturnTaskAsync`/`SyncReturnTaskAsync` оперують `item.ReturnTaskId` (серверне поле) під `CurrentUserId`. Перевірити неможливість впливу на чужий календар через повернення книги.
- [ ] Каскад з календаря: видалення події `sourceModule="media"` з чужого акаунта неможливе (скоп по userId у `DeleteTaskAsync`). Перевірити, що каскад не перетинає межі користувачів (`m.UserId == userId` у вибірці media).

## 8. Безпека (XSS у назві/авторі/відгуку, масове призначення статусу/рейтингу)

- [ ] **XSS:** `title`, `author`, `review` рендеряться як текстовий вміст JSX (`{item.title}`, `{item.review}`) — React екранує. Немає `dangerouslySetInnerHTML`. Перевірити, що введення `<img src=x onerror=alert(1)>` у назву/відгук показується як текст, не виконується. Те саме для бейджів жанру/виду.
- [ ] Відгук із `white-space: pre-wrap` у `<p>` — лишається текстом (перенесення рядків зберігаються, HTML не інтерпретується). Перевірити багаторядковий відгук із «<», «&».
- [ ] Назва події в календарі («Подивитися: {title}») успадковує title користувача — перевірити, що календарні в'юхи теж рендерять це як текст (XSS не переноситься в інший модуль).
- [ ] **Mass assignment статусу:** `Update` (`PUT /api/media/{id}`) **не містить** поля `status` у `UpdateMediaRequest` → статус не можна змінити в обхід правил «лише вперед». Перевірити, що немає іншого шляху виставити статус, окрім `/status` і `/schedule`.
- [ ] **Призначення рейтингу поза контекстом:** `Update` виставляє `item.RatingStars`/`item.Review` для **будь-якого** статусу (не лише `done`). Перевірити: PUT на `planned`-запис із `ratingStars:5` → збережеться рейтинг у не-`done`. Клієнт цього не робить (передає поточні значення), але API дозволяє — злегка порушує інваріант «рейтинг лише у Завершено».
- [ ] **Рейтинг поза 1–5:** `Math.Clamp(RatingStars, 1, 5)` у `SetStatus` і `Update`. Перевірити прямі виклики: `0 → 1` (!), `-5 → 1`, `999 → 5`, `null → null`. **РИЗИК:** `ratingStars:0` стає **1 зіркою**, а не «без рейтингу» (клієнт рятує, бо шле `rating || null`, але API — ні). Зафіксувати.
- [ ] `isReturned`/`StatusBeforeReturn`/`TaskId`/`ReturnTaskId`/`UserId` — **не** приймаються в `UpdateMediaRequest`/`AddMediaRequest` (немає mass-assignment внутрішніх полів). Перевірити DTO на зайві поля.
- [ ] `isLibrary`/`returnDeadline` приймаються в `Update`, але застосовуються лише якщо `item.Kind == "book"`. Перевірити, що відео не можна зробити «бібліотечним» через API.
- [ ] Довжина відгуку/назви/автора на сервері ріжеться (`Clean` → `t[..max]`), не відхиляється. Перевірити POST із назвою 10 000 символів → обрізається до 120, `200` (не 400, не падіння).
- [ ] CSRF: автентифікація через Bearer-токен (localStorage), не cookie → CSRF малоймовірний. Перевірити, що немає cookie-авторизації.

## 9. Бізнес-логіка та інваріанти

**Статус лише вперед:**
- [ ] `SetStatus` строго `targetIdx > currentIdx` і забороняє `in_progress` (лише через `/schedule`). Перевірити неможливість `done → planned`, `in_progress → planned`, `done → in_progress` через `/status`.
- [ ] **Відкат назад через `/return` (санкціонований):** реактивація (`Returned=false`) ставить `item.Status = StatusBeforeReturn` — це легітимний рух назад (`done → in_progress`/`planned`), поза перевіркою `/status`. Перевірити, що `StatusBeforeReturn` коректно збережений при поверненні й що реактивація не створює неможливих станів.
- [ ] `/schedule` єдиний шлях у `in_progress`; вимагає `Status=="planned"`. Перевірити, що двічі запланувати не можна (`already_scheduled`).

**Борги = прострочені бібліотечні; «повернено»:**
- [ ] `IsDebt` = `IsLibrary && !IsReturned && ReturnDeadline<Today && Status!="done"` — **обчислюване**, не зберігається. Перевірити межу: дедлайн == сьогодні → **не** борг (строго `< Today`); дедлайн вчора → борг.
- [ ] Завершені (`done`) ніколи не борг (за визначенням). Перевірити: прострочена, але `done` бібліотечна книга не з'являється в «Боргах», хоча не повернена. **ПИТАННЯ:** чи це бажано (користувач «дочитав», але бібліотеці винен).
- [ ] **Борг не дублюється** у звичайних вкладках: клієнт `visible` виключає `it.isDebt` із planned/in_progress, а `counts` рахує з `!it.isDebt`. Перевірити, що прострочена неповернена книга видима **тільки** в «Боргах».
- [ ] Логіка «повернено» (`SetReturned`, `Returned=true`):
  - [ ] `planned` і **не** борг → книгу не читали → **видаляється повністю** (+ подія `TaskId`). Перевірити, що не лишається запис/подія.
  - [ ] `in_progress`/борг → `done`, `StatusBeforeReturn` збережено, нагадування видалено. Перевірити.
  - [ ] `done` → лишається `done`, лише `IsReturned=true`. Перевірити.
- [ ] **ПИТАННЯ (неузгодженість «done»):** `/return` переводить у `done` **без** позначення пов'язаної події `TaskId` як `Done` (на відміну від `/status done`, що ставить `task.Status="Done"`). Тож книга, «завершена» через повернення, лишає активну (Planned) подію перегляду в календарі. Перевірити розбіжність двох шляхів у `done`.

**Планування → подія календаря; дедлайн повернення:**
- [ ] `Schedule` створює подію (`CreateTaskAsync`, `moduleCode="media"`, `sourceModule="media"`), пише `item.TaskId`, `StartDate`, `Status="in_progress"`. Перевірити появу в календарі.
- [ ] Бібліотечна книга з дедлайном при `Add`/`Update` отримує **окрему** подію-нагадування (`sourceModule="media_return"`, `ReturnTaskId`) з назвою «Повернути книгу: …». Перевірити, що це **друга** подія, незалежна від події читання.
- [ ] `SyncReturnTaskAsync`: нагадування потрібне лише якщо `IsLibrary && ReturnDeadline && !IsReturned`; інакше видаляється. Перевірити зняття бібліотечного прапорця/повернення → нагадування зникає.
- [ ] Якщо наявне нагадування видалили вручну в календарі, `SyncReturnTaskAsync` ловить `UpdateTaskAsync==false` і створює нове. Перевірити самовідновлення.

**Осиротілі події (ключовий ризик):**
- [ ] **БАГ (орфан):** `TaskService.DeleteTaskAsync(cascadeSource:true)` при видаленні події `sourceModule="media"` **з календаря** видаляє сам `MediaItem` (`_db.MediaItems.Remove(media)`), але **НЕ** викликає `RemoveReturnTaskAsync` — тобто подія-нагадування `ReturnTaskId` (`media_return`) лишається в календарі як **осиротіла** після того, як книги вже немає. Відтворити: бібліотечна книга з дедлайном → запланувати (є подія читання) → видалити подію читання в календарі → книга зникла, нагадування «Повернути книгу» висить. Виправлення: у каскаді прибирати й `media.ReturnTaskId`.
- [ ] Протилежний бік (ок): `MediaController.Delete` сам прибирає `TaskId` **і** `ReturnTaskId`, тож видалення **через вкладку Перегляд** орфанів не лишає. Перевірити обидва шляхи видалення.
- [ ] Видалення нагадування `media_return` у календарі **не** чіпає книгу (каскад реагує лише на `sourceModule=="media"`). Перевірити, що видалення нагадування не видаляє запис книги.
- [ ] `done` через `/status`: подія `TaskId` стає `Done`, але не видаляється («у календарі лише видалити, і те видалення прибере й запис»). Перевірити цей зв'язок і що він не плутається з каскадом.

## 10. Дані, межі, дата/час, Unicode, довгі назви

- [ ] **Дата повернення в минулому:**
  - [ ] Форма **додавання** має `min={todayApiDate()}` на `returnDeadline`. Перевірити, що браузер блокує минуле (але це лише UI).
  - [ ] **БАГ:** форми **редагування** (`status==='planned'` гілка, рядки ~594–597, і `in_progress` гілка ~609–611) **НЕ мають** `min` на полі `returnDeadline` → можна виставити минулу дату → запис миттєво стає боргом. Відтворити через редагування.
  - [ ] **РИЗИК:** сервер **взагалі не валідує**, що `ReturnDeadline >= Today` (ні в `Add`, ні в `Update`). Пряме API з минулою датою приймається → одразу борг. Зафіксувати.
- [ ] **Дата планування в минулому:** поповер планування має `min={todayApiDate()}` (UI), але сервер `Schedule` **не валідує** дату → подія перегляду створюється в минулому (одразу «прострочена»/потрапляє у «Нерозподілені» через `SweepStaleTasks`). Перевірити.
- [ ] Часові пояси: `IsDebt`/`SweepStaleTasks` використовують `DateTime.Today`/`DateTime.Now` (локальний час сервера), а `CreatedAt` — `UtcNow`. Проєкт свідомо «wall-clock без TZ» (коментар у `TaskService`). Перевірити off-by-one біля опівночі / при розбіжності TZ клієнта й сервера для статусу боргу.
- [ ] **Unicode в авторі — БАГ i18n:** `filterWords` (`WORD_CHAR = /[A-Za-zА-ЯҐЄІЇа-яґєіїʼ' -]/`) лишає **лише** латиницю + укр. кирилицю + пробіл/дефіс/апостроф. Отже:
  - [ ] Автори CJK (японські/китайські/корейські імена) — **повністю вирізаються** (поле стає порожнім при вводі).
  - [ ] Акцентована латиниця (é, ü, ö, ł, ñ) і неукр. кирилиця (ё, ы, э) — **вирізаються** посимвольно.
  - [ ] Цифри/крапки в іменах («J.R.R.», «50 Cent») — вирізаються. Перевірити всі випадки; для списку книг це суттєве обмеження.
- [ ] Назва (`limitText`) **не фільтрує** алфавіт → приймає будь-який Unicode, емодзі, RTL, керівні символи. Перевірити рендер емодзі/RTL у картці й календарі; перевірити, що керівні/невидимі символи не ламають верстку.
- [ ] Довгі значення: назва 120, автор 60, відгук 200 — межі і на клієнті, і на сервері. Перевірити рівно на межі й на +1 (обрізання, не помилка).
- [ ] `returnDeadline` надсилається як `"YYYY-MM-DD"`, поле моделі — `DateTime?`. Перевірити парсинг (північ) і що порівняння `.Date` коректне.
- [ ] Порожні/`null` необов'язкові поля (`author`, `genre`, `mediaType`, `review`, `returnDeadline`) — усюди `|| null`. Перевірити, що порожній рядок не зберігається замість `null`.
- [ ] `RatingStars` типу `int?` — перевірити дробові/рядкові значення з API (`"5"`, `5.5`) — модельне зв'язування ASP.NET + `Math.Clamp`.

## 11. Продуктивність і надійність

- [ ] **Багато записів:** `Get` тягне всі `MediaItems` користувача без пагінації/ліміту; клієнт фільтрує/рендерить усе в пам'яті (`items.filter(...)` на кожен рендер). Перевірити поведінку на 1 000+ записів (рендер усіх `visible` карток з анімацією).
- [ ] Кожна мутація робить `await reload()` = повний `GET /api/media`. Перевірити к-сть зайвих повних перезавантажень при серії дій; відсутність оптимістичних оновлень.
- [ ] **Гонка планування:** `Schedule` перевіряє `Status=="planned"`, потім створює подію — **без** транзакції/блокування. Два паралельні `/schedule` для одного запису можуть обидва пройти перевірку → створяться **дві** події календаря, `item.TaskId` перезапишеться другою → перша подія **осиротіє**. Відтворити подвійним кліком/дабл-запитом.
- [ ] **Гонка завершення/планування:** паралельні `/schedule` і `/status done`, або `/status done` і `/return` — перевірити кінцевий стан (`Status`, `TaskId`, статус події) на узгодженість.
- [ ] **Гонка повернення:** два швидкі `SetReturned(true)` на `planned`-книзі: перший видаляє запис; другий отримає `404` (запис уже видалено) — перевірити, що клієнт це переживає (після `reload` картка зникла).
- [ ] Подвійний клік «Видалити»/«Завершити»/«Повернено» — кнопки не стають `disabled` під час запиту (немає локального `busy`-стану). **РИЗИК:** подвійні запити. Перевірити ідемпотентність (повторний `Delete` → `404`; повторний `/status done` → `backward_not_allowed`).
- [ ] Синхронізація з календарем при серії: `Add`(бібліотечна)→`Schedule`→`Update`(зміна дедлайну)→`SetReturned`→реактивація — перевірити, що `TaskId` і `ReturnTaskId` завжди вказують на наявні події, немає задвоєння чи орфанів (з урахуванням §9-орфана).
- [ ] `Add` робить **два** `SaveChangesAsync` (спершу Id, потім подія) — не в одній транзакції. Якщо `SyncReturnTaskAsync` впаде, запис уже збережений без нагадування. Перевірити часткову відмову.
- [ ] `useEffect` початкового завантаження має guard `cancelled` при розмонтуванні — перевірити відсутність `setState` після unmount і подвійного виклику у React StrictMode (dev).
- [ ] `reload` (`setItems((await getMedia()) || [])`) без обробки помилки — якщо перезавантаження після мутації впаде, помилка «проковтнеться» (unhandled rejection), стан не оновиться. Перевірити поведінку при мережевій відмові в середині дії.
- [ ] Великий відгук/назва з `pre-wrap` і `break-word` — перевірити, що рендер багатьох довгих карток не деградує layout.

### Зведення підтверджених дефектів/ризиків (швидкий список)

1. **Орфан-нагадування:** видалення події читання в календарі каскадно видаляє книгу, але лишає подію «Повернути книгу» (`DeleteTaskAsync` не чистить `ReturnTaskId`). (§9)
2. **Минула дата повернення:** немає `min` у формах редагування і немає серверної валідації `ReturnDeadline >= Today`; так само дата планування не валідується на сервері. (§10)
3. **Автор — вузький алфавіт:** `filterWords` вирізає CJK, акцентовану латиницю, неукр. кирилицю, цифри, крапки — неможливо ввести багато реальних імен авторів. (§10)
4. **Рейтинг 0 → 1:** `Math.Clamp(0,1,5)==1` на сервері; прямий API з `ratingStars:0` дає 1 зірку замість «без рейтингу». (§8)
5. **Невалідний жанр/вид приймається тихо:** сервер не відхиляє (`400`), а обнуляє — жодного зворотного зв'язку. (§6)
6. **Гонка `/schedule`:** подвійний запит створює дві події, перша осиротіє. (§11)
7. **Неузгоджені шляхи в `done`:** `/return`→done не позначає подію читання `Done`, на відміну від `/status`→done. (§9)
8. **UX-копірайт:** плейсхолдер «Пошук за назвою…» ≠ фактичний пошук за назвою **та** автором. (§3)
9. **a11y:** зірки без змістовних міток, немає фокус-менеджменту/`Esc` для поповерів, стан `error` без «повторити». (§5, §3)
10. **Інваріант:** `Update` дозволяє писати рейтинг/відгук у не-`done` записи. (§8)
