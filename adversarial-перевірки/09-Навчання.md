# Adversarial review — Навчання

Огляд модуля «Навчання»: `client/src/pages/Study.jsx`, `client/src/components/study/*`
(`ScheduleTab`, `StudyScheduleViews`, `SubjectsTab`, `BellsTab`, `AssignmentsTab`,
`DebtsTab`, `ExtraTab`, `ProjectsTab`, `studyShared.js`), `client/src/api/study.js`,
`client/src/utils/debts.js`, серверних `StudyController.cs` + `StudyService.cs` і
`TaskService.cs` (правила повторення). Чек-лист навмисне «злий»: кожен пункт — це
питання «а що як зловмисник / реальний користувач зробить навпаки».

> Легенда серйозності: 🔴 критично (безпека/цілісність) · 🟠 суттєво · 🟡 помірно · ⚪ дрібно/косметика.

---

## 1. Фронтенд — сторінка, гейтинг школяр/студент, вкладки, логіка

- 🟠 **Гейтинг розділу тільки «м'який».** `App.jsx` для `work` і `cycle` робить
  `isWorking ? <Work/> : <Navigate to="/app"/>` і `gender==='female' ? … : <Navigate/>`,
  а маршрут `study` — просто `<Route path="study" element={<Study/>} />` **без Navigate**.
  Study.jsx сам показує заглушку `study.noStatus`, якщо `studentType` не `pupil`/`student`.
  Тобто поведінка розходиться з ОПИС-ВКЛАДОК (де сказано «прямий URL переадресовує на `/app`»):
  тут немає редіректу, лишається екран-заглушка. Непослідовно з іншими умовними розділами.
- 🟠 **`studentType` береться з `useOutletContext()` без фолбеку.** У Study.jsx — `const { studentType } = useOutletContext()` (без `?? {}`, на відміну від Planner/QuickAdd).
  Якщо компонент колись відрендериться поза Outlet (тест, зміна роутингу) — `TypeError`
  на деструктуризації і білий екран.
- 🟡 **Вкладка не скидається при зміні `studentType`.** `tab` — локальний стан із дефолтом
  `'subjects'`. Якщо студент відкрив `projects`, а потім у Налаштуваннях став школярем,
  масив `tabs` більше не містить `projects`; рендер `tab === 'projects' && isStudent`
  поверне порожнечу (жодна панель не показується), доки користувач не клацне іншу вкладку.
  Немає ефекту, що повертає tab на валідний.
- 🟡 **Форма навчання за замовчуванням `distance`** (`settings?.learningForm ?? 'distance'`).
  Якщо сервер повернув невідоме значення — Study.jsx покаже активним жодне з трьох (бо
  порівняння точне), але сервер уже нормалізує (див. §6), тож на практиці ок.
- ⚪ **Іконка вкладки «Предмети» — `user`**, «Великі роботи» — `notes`: семантично дивно
  (предмет ≠ людина), але це косметика.
- 🟡 **`handleSetForm` перезаписує весь об'єкт налаштувань.** `const next = { ...settings, learningForm: form }; setStudySettings(next)`. Разом із формою на сервер летять дати
  `studyStart/End`, `semesterEnd`, `yearEnd` з page-рівня `settings`. Якщо користувач
  редагував дати у `ScheduleTab` (там свій локальний `cfg`) і не зберіг, а потім перемкнув
  форму зверху — на сервер піде **стара** версія дат, а локальні зміни `ScheduleTab` при
  наступному `reloadSettings`/ре-рендері буде перетерто (див. §11, гонка).

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, таблиці/розклад

- 🟡 **Сітка розкладу `study-grid` має `min-width: 640px`.** На мобільному це змушує
  горизонтальний скрол у `.table-scroll` (ок), але 7 днів × колонка пар на 360px —
  дуже тісно, клітинки `study-grid-cell` стискаються. Для школяра з 7 уроками × 6 днів
  текст предметів переноситься в кашу. Немає мобільного «список-на-день» фолбеку для
  календарного подання.
- 🟡 **Статус-кольори бейджів задано локально в `.study-page`** (`--status-*`), для темної
  теми перевизначено лише `*-bg`, але **`*-text` для темної теми НЕ перевизначено** —
  `--status-ok-text:#1f8a4c`, `--status-bad-text:#d1453c` на темному фоні `#1f3a2b`/`#4a2320`.
  Контраст зелений/червоний текст по темному тлі треба перевірити — ймовірно нижче 4.5:1
  (особливо `--status-warn-text:#c77c10` на `#3f3320`). Потенційний a11y-фейл контрасту.
- 🟡 **`study-desc-cell` має `max-width:340px`** з `white-space:normal`. Опис до 300 символів
  (а сервер довжину не ріже — див. §6) розтягує рядок таблиці у висоту; на вузькому екрані
  таблиця й так скролиться, але колонка опису домінує.
- ⚪ **Дубль правил `.study-page h2`/`h4`** у CSS (двічі оголошено `h2`, двічі `h4`) — мертвий
  код, нешкідливо.
- ⚪ **Класи `.schedule-cell`, `.schedule-table`, `.grade-block`, `.grade-value-panel`,
  `.study-grade-value`, `.study-subject-name`, `.cat-dot`, `.month-*`, `.week-tabs-nav`,
  `.variant-note`, `.page-head`** лишилися в `Study.css`, але в поточних компонентах не
  використовуються (сітка розкладу тепер `study-grid`, місячного календаря в модулі немає).
  Мертвий CSS після переробки модуля.
- 🟡 **`.study-form-actions { margin-left:auto }`** притискає кнопку вправо; на вузькому
  екрані з `flex-wrap` кнопка «Додати» може опинитися на своєму рядку окремо — перевірити
  візуально, що не з'їжджає за край.
- ⚪ Сегментовані перемикачі (`study-seg`) і великі плитки-вкладки (`study-tab`) мають
  hover-transform; на тач-екранах hover «залипає» — дрібниця.

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо)

- 🟠 **Мутації не мають обробки помилок.** У всіх вкладках `addSubject/updateSubject/
  removeSubject`, `addAssignment/patchItem`, `apiSetBells`, `addScheduleEntry`,
  `addProject/addStep/...` викликаються `await` без `try/catch`. Якщо сервер відповів 4xx/5xx
  або мережа впала — unhandled promise rejection, **жодного повідомлення користувачу**,
  форма може залишитись у напів-стані (напр. `patchItem` уже оновив локальний стан
  оптимістично, а сервер відхилив — UI розійдеться з БД до наступного reload).
- 🟠 **Оптимістичні апдейти без відкату.** `AssignmentsTab.patchItem` і `DebtsTab.markDone`
  спершу `setItems(...)` локально, потім `await updateAssignment`. Помилка сервера → локальний
  стан бреше (показує «виконано»/оцінку, якої на сервері немає). Немає rollback.
- 🟡 **`error`-екран лише для первинного `Promise.all`.** Після успішного старту всі подальші
  збої API не піднімають `error`. Користувач бачить «робочий» екран, де нічого не зберігається.
- 🟡 **Порожні стани є не скрізь однаково.** `SubjectsTab`, `AssignmentsTab`, `DebtsTab`,
  `ExtraTab`, `ProjectsTab`, список розкладу — мають плейсхолдери. Але **`BellsTab` не має
  порожнього стану** — замість цього `seedDefaults` одразу підставляє дефолтну сітку, тож
  ключ `study.bellsEmpty` (є в i18n) ніде не використовується (див. §4).
- 🟡 **Клієнтська валідація дуже слабка:**
  - Предмет: `canSave = name.trim() && teacher.trim()` — викладач **обов'язковий на клієнті**,
    хоча сервер дозволяє `Teacher=null` (див. §9, «предмет без викладача»). Непослідовно.
  - Завдання: єдина перевірка `form.description.trim()`. Дедлайн-вид не перевіряється на
    сумісність; «До дати» без обраної дати → `dueDate:null` піде на сервер (deadlineKind='date'
    але DueDate null → ResolveDeadline поверне null → завдання «без дедлайну», хоча вид «До дати»).
  - Дзвінки: **немає перевірки `endTime > startTime`**, немає перевірки перекриття/зростання
    часу (детально §10).
  - Великі роботи: лише `name.trim()`.
- 🟡 **`<input type="date">` не має min/max.** Можна поставити `studyStart`=2099, `studyEnd`=1900
  тощо — клієнт мовчки прийме; серверної перевірки порядку дат немає (§6/§10).
- ⚪ Лічильник символів опису відсутній (на відміну від Нотаток), лише нативний `maxLength=300`.

## 4. Інтернаціоналізація (i18n) — предмети/терміни uk/en, невикористані ключі

- 🟡 **`SUBJECT_PRESETS`** мають пари `uk/en`, у `SubjectsTab` обирається за `language`. Ок, але
  це datalist-підказки — вільний ввід лишається, тож предмет може бути будь-якою мовою незалежно
  від локалі (нормально, але пошуку/нормалізації немає).
- 🟡 **Ймовірно невикористані ключі i18n** (знайдено в `uk.json`, але не зустрічаються в коді
  вкладок):
  - `study.bellsEmpty` — BellsTab замість порожнечі сидить дефолтами.
  - `study.assignmentTitle` («Назва завдання») — у завдань немає поля «назва», лише опис.
  - `study.col.room` («Кабінет») — SubjectsTab використовує `study.col.place`, не `col.room`.
  - `study.vacationStart` / `study.vacationEnd` («Канікули з/до») — **у ScheduleTab немає полів
    канікул**: рендеряться лише `studyStart/End`, `semesterEnd`, `yearEnd`. Проте модель і
    `SettingsDto` мають `VacationStart/VacationEnd` (§9) — фіча напівреалізована: бекенд і ключі
    є, UI немає.
  - `study.subjectTitle`/інші — варто прогнати lint на мертві ключі.
- 🟠 **Невідповідність uk/en для нових ключів.** Переглянуто лише `uk.json`; треба перевірити, що
  `en.json` має ВСІ ключі `study.*` (зокрема нові: `parity.*`, `scheduleView.*`,
  `weekNumerator/Denominator`, `cycleWeeksShort`, `manualNotSupported`, `projectKind.*`,
  `entryKind.*`, `bellsBounds`, `debts.*`). Якщо хоча б один відсутній — `t()` поверне ключ як
  текст (англомовний користувач побачить `study.parity.num`).
- 🟡 **`summarizeEntry` у `ScheduleTab` використовує `weekdaysIso`**, а в `ExtraTab` —
  `t('planner.weekdaysShort').split(',')`. Два різних джерела назв днів для одного й того ж
  хелпера; при розбіжності порядку/вмісту ISO-міток між цими джерелами підпис «коли» для
  консультацій і для пар може різнитись.
- ⚪ Жорстко зашитий рядок `"Заняття"` у `BuildTitleDescription` (StudyService) — назва
  шаблон-задачі в календарі для безіменної пари **не локалізується** (завжди укр.), англомовний
  користувач побачить «Заняття» у спільному календарі.

## 5. Доступність (a11y): сегментовані перемикачі, сітки днів, таблиці

- 🟠 **Сегментовані перемикачі — це просто `<button>` з класом `--active`.** Немає
  `role="tablist"`/`role="tab"`/`aria-selected` ні на `study-tabs`, ні на `study-seg`
  (форма навчання, парність, підвкладки боргів, види робіт, типи консультацій). Скрінрідер не
  повідомить, який варіант обрано, і що це група.
- 🟠 **Кнопки-дні тижня (`task-form-weekday`)** — toggl'и без `aria-pressed`. Користувач
  клавіатури/скрінрідера не зрозуміє, які дні ввімкнені.
- 🟠 **Поле оцінки студента (`GradeInput`, number) і select оцінки школяра не мають `<label>`**
  і `aria-label`. У таблиці заголовок колонки «Оцінка» є, але поле поза контекстом (скрінрідер
  читає просто «spin button»).
- 🟡 **Чекбокси «виконано» загорнуті в `<label>` з `title`**, але сам чекбокс без видимого тексту
  поруч (текст у `<span class="badge">` всередині лейбла — ок, читається). Прийнятно.
- 🟡 **Таблиці без `<caption>` і без `scope` на `<th>`.** Для сітки розкладу (двовимірної:
  пари × дні) відсутність `scope="col"`/`scope="row"` суттєво погіршує навігацію скрінрідером —
  незрозуміло, яка пара/день у клітинці.
- 🟡 **Порожні `<th/>`** (колонка дій) без `aria-label` — ок як decorative, але скрінрідер оголосить
  порожній заголовок.
- 🟡 **`data-tooltip` + `aria-label` на іконкових кнопках** — добре. Але `ProjectsTab` кнопка
  видалення роботи має лише `data-tooltip`, **без `aria-label`** (на відміну від інших) — іконка
  без доступної назви.
- 🟡 **Навігація тижнями (`WeekCalendar`)** — кнопки «Тиждень назад/вперед» ок, але зміна контенту
  таблиці не має `aria-live`; скрінрідер не повідомить, що діапазон/парність змінились.
- ⚪ Активна плитка-вкладка позначається лише кольором-градієнтом (не текстом «обрано») — для
  далтоніків покладається на `aria-selected`, якого немає (див. вище).

## 6. Бекенд — API, статус-коди, валідація

- 🟠 **Довжина рядків ніде не обмежена на сервері.** `Description` завдання, `Name`/`Teacher`/
  `Room`/`Link` предмета, `Name`/`Curator` роботи, `Name` етапу — лише `.Trim()`, без max-length.
  Клієнтський `maxLength=300` на опис обходиться прямим API-викликом → можна зберегти мегабайтний
  опис (DoS сховища / роздування відповідей / поломка верстки). Треба валідацію довжини (напр.
  опис ≤300, назви ≤200).
- 🟠 **`sessionKind`, `Form`, `parity`-похідні, `Room`, `Link` не валідуються** у
  `Add/UpdateScheduleEntry`. `sessionKind` може бути будь-яким рядком (не лише lecture/seminar),
  `Form` — будь-що (не з {distance,regular,mixed}). Зберігається як є і впливає на
  `BuildTitleDescription` (isSeminar = sessionKind=="seminar", інакше трактується як лекція).
- 🟠 **`Recurrence` приймається майже без перевірки.** Контролер перевіряє лише
  `EntryKinds.Contains(EntryKind)` і `Recurrence != null`. Тип правила, патерни
  (`WeekDaysPattern`, `MonthDays`, `MonthDayMode`) не валідуються — летять напряму в
  `TaskService.CreateRecurrenceRuleAsync`. Малформований `MonthDays` при `MonthDayMode="Specific"`
  викликає `int.Parse(...)` у `GenerateMonthDaysDates` без try → **`FormatException` → 500**
  при наступному перегляді календаря (не лише у Навчанні, а на головному планнері). Див. §11.
- 🟡 **Відсутня перевірка узгодженості дедлайну завдання.** Контролер валідує `DeadlineKind ∈ set`,
  але при `kind="date"` не вимагає `DueDate` (ResolveDeadline поверне null). І навпаки, при
  `kind≠"date"` клієнт/сервер ігнорують `DueDate` (`DueDate = kind=="date" ? … : null`) — ок.
- 🟡 **Коди статусу.** Загалом 200/400/404 розставлені розумно (`NotFound` при чужому/відсутньому
  id, `BadRequest{error}` при валідації). Але:
  - `UpdateSettings`/`ReplaceBells` завжди повертають `Ok()` навіть якщо нічого змістовного не
    сталося; `ReplaceBells(null)` → порожній список (мовчки стирає всю сітку — див. §11).
  - Немає `201 Created`/Location для POST (повертається `Ok{id}`) — дрібниця.
- 🟡 **`CurrentUserId` кидає `NullReferenceException`**, якщо токен без `sub` (`!`), → 500 замість
  401. Малоймовірно при валідному JWT, але крихко.
- ⚪ `GetSchedule`/`GetProjects` тихо ігнорують невалідний `kind` (трактують як «усі») — прийнятно.

## 7. Авторизація та власність (гейтинг за studentType; IDOR)

- 🔴 **Сервер НЕ перевіряє `studentType` взагалі.** `StudyController` має лише `[Authorize]`.
  Отже будь-який автентифікований користувач — зокрема з `studentType = null` («Нічого з цього»),
  якому клієнт ховає вкладку і показує заглушку — може **повноцінно користуватися всім API
  Навчання** напряму (створювати предмети, завдання, дзвінки, розклад, роботи). Клієнтський
  гейтинг суто косметичний.
- 🔴 **Школяр може створити студентські «Великі роботи» через API.** `POST /api/study/projects`
  перевіряє лише `Kind ∈ {diploma,coursework,practice}` і непорожню назву — **жодної прив'язки
  до `studentType="student"`**. Школяр (чи навіть «ніхто») створює диплом/курсову/практику з
  етапами без перешкод. Пряме порушення правила «Великі роботи — лише студент».
- 🔴 **Тип завдання не звірено зі `studentType`.** `ValidAssignment` дозволяє будь-який з
  `{homework,lab,exam,practical}`. Тож школяр через API ставить `type="exam"/"lab"/"practical"`
  (студентські), а студент — `type="homework"`. UI це приховує, бекенд — ні.
- 🔴 **IDOR: завдання може посилатися на ЧУЖИЙ предмет, і це витікає назву/викладача.**
  `AddAssignmentAsync`/`UpdateAssignmentAsync` присвоюють `SubjectId = subjectId` **без перевірки
  власності** (на відміну від `AddScheduleEntryAsync`, де предмет шукається з `x.UserId==userId`).
  `GetAssignmentsAsync` робить `Include(x => x.Subject)` і повертає `a.Subject?.Name` та
  `a.Subject?.Teacher`. Зловмисник створює завдання з `subjectId` з чужого діапазону → у відповіді
  GET бачить **назву предмета і прізвище викладача іншого користувача**. Перебором id — зліва вся
  чужа таблиця предметів. Серйозний витік через відсутність ownership-перевірки + навігаційний
  Include.
- 🟢 **Решта власності — коректно.** Предмети, дзвінки, записи розкладу, проєкти, етапи, оновлення/
  видалення скрізь фільтрують `x.UserId == userId` (етапи — через `s.Project!.UserId == userId`,
  AddStep — `AnyAsync(... UserId==userId)`). `AddScheduleEntry` шукає предмет лише серед своїх
  (чужий `subjectId` → null, безпечно). Тож IDOR локалізований саме у завданнях.
- 🟡 **Борги агрегуються на клієнті (`utils/debts.js`, `DebtsTab`)**, але джерело —
  `getAssignments()`, яке на сервері суворо `Where(UserId==userId)`. Тож **чужі борги не
  витікають через саму агрегацію** — за умови, що не спрацював IDOR із §7.4 (через нього у
  `subjectName` боргу може опинитись чужа назва). Сам список боргів — лише свій.

## 8. Безпека (XSS, масове призначення оцінок)

- 🟢 **Збережений XSS у назвах предметів/завдань/робіт** — React екранує текст за замовчуванням;
  назви/описи рендеряться як текстові вузли (`{s.name}`, `{a.description}`, `{project.name}`),
  `dangerouslySetInnerHTML` не використовується. Безпечно у вебі.
- 🟠 **`Link` предмета/консультації не валідується і не санітизується** як URL. Зараз він лише
  виводиться текстом (`placeCell`, `BuildTitleDescription` → опис задачі) — безпечно. Але якщо
  колись його зроблять клікабельним `href`, збережений `javascript:`/`data:` стане XSS. Плюс
  посилання потрапляє в опис шаблон-задачі спільного календаря — варто перевірити, чи там воно
  десь не стає посиланням.
- 🔴 **Mass assignment оцінок — мітигований, але з діркою.** `ClampGradeAsync` на сервері
  обмежує: школяр → `Clamp(round, 0, 12)`, інакше → `Round(Clamp(0..100), 2)`. Це захищає від
  від'ємних/`>max`/зайвих десяткових навіть в обхід UI — **добре**. АЛЕ:
  - **Клампінг залежить від `profile.StudentType`, а не від типу/контексту завдання.** Користувач
    зі `studentType=null` («ніхто», якому розділ недоступний у UI) потрапляє в гілку «інакше» →
    отримує шкалу **0–100**. Тобто «не-студент» через API зберігає 100-бальні оцінки. А якщо
    користувач перемкнув тип після виставлення оцінок — стара 100-бальна оцінка школяреві при
    наступному `Update` переобчислиться в 0–12 (мовчазна втрата значення).
  - **Нечислові/екстремальні decimal.** `Grade` — `decimal?`; дуже велике число в JSON у межах
    decimal клампиться (ок), але значення поза діапазоном decimal → помилка десеріалізації 400
    (прийнятно). `NaN`/нечислове тіло → 400 моделі.
- 🟡 **`IsDone`/`Grade` розсинхрон.** Сервер зберігає `Grade` лише коли `IsDone` (інакше null) —
  правильно. Але клієнт у `patchItem` надсилає `grade: next.isDone ? next.grade : null`; при
  знятті «виконано» оцінка губиться без попередження (очікувано, але варто попереджати).
- 🟡 **`ReplaceBells` як «mass replace»** дозволяє надіслати довільні `Index` (напр. дублікати,
  від'ємні, пропуски) — сервер зберігає як є (§10/§11).

## 9. Бізнес-логіка та інваріанти

- 🔴 **Різниця школяр/студент не забезпечена на сервері** — див. §7 (проєкти, типи завдань,
  sessionKind, оцінкова шкала через profile). Інваріант «школяр ≠ студент» тримається лише UI.
- 🟠 **Парність (чисельник/знаменник) vs головний календар — вразлива до зміни `studyStart`.**
  Домовленість: anchor = `studyStart`. При створенні пари `ScheduleTab` кладе
  `cycleAnchorDate = cycleWeeks>1 ? cfg.studyStart : null` і `startDate = cfg.studyStart`.
  Сервер (`GetWeekIndex`) бере `anchor = CycleAnchorDate ?? StartDate` і рахує від понеділка
  того тижня — **збігається** з `WeekCalendar`, що теж анкериться на `studyStart`. ОДНАК:
  - Якщо користувач **змінить `studyStart` після** створення пар, збережене правило лишається зі
    **старим** `CycleAnchorDate`/`StartDate` (правило не переписується), а `WeekCalendar` у
    Навчанні рахує парність від **нового** `cfg.studyStart`. → **Подання «Календар» у Навчанні
    покаже парність, відмінну від головного планнера** (який рахує від збереженого
    `CycleAnchorDate`). Це і є описаний баг-розбіжність.
  - `TwoWeekTable` взагалі не анкериться на дату: показує week0 як «Чисельник», week1 як
    «Знаменник» за патерном (`targetWeek`: denom→1, num/weekly→0). Узгоджено лише тому, що
    чисельник завжди пишеться у week0. Якщо колись порядок зміниться — розсинхрон із календарем.
- 🟠 **`WeekCalendar.parity` рахується через різницю в мілісекундах** —
  `Math.round((monday - a) / (7*86400000))`. Це локальні `Date`, тож **через межі переходу на
  літній/зимовий час** тиждень ≠ рівно 7·86400000 мс; `Math.round` маскує одиничний зсув, але на
  великих offset накопичення може дати хибну парність. Сервер рахує чесно в календарних днях
  (`DayNumber`). → ще одне потенційне джерело розбіжності клієнт/сервер саме навколо DST.
- 🟡 **Дзвінки → час пар.** `addLesson` бере `bells[pairNumber-1].startTime`, фолбек `'08:30'`.
  Якщо сітку дзвінків змінили **після** створення пари (номери зсунулись/пара видалена), час у
  вже створеному правилі **не оновлюється** (він зашитий у `TimeOfDay` правила). `pairNumber`
  записаний у запис, але час — ні. Подання таблиці/календаря беруть час із `bells` за
  `pairNumber`, а головний календар — із `TimeOfDay`. → час пари у Навчанні і в планнері можуть
  розійтися після редагування дзвінків.
- 🟡 **Розклад/консультації = правила повторення (moduleCode="study")** — ті самі ризики
  генерації/DoS, що й у Календарі (§11): немає ліміту на кількість записів, малформовані патерни
  ламають генерацію.
- 🟢 **Борги = невиконані прострочені завдання** — `DebtsTab`/`debts.js`:
  `!isDone && resolvedDeadline && resolvedDeadline < today`. Логіка консистентна. «Усі борги» =
  всі невиконані. Ок.
- 🟢 **Прогрес великих робіт — ділення на нуль захищене.** `percent = total==0 ? 0 : round(done*100/total)`. 0 етапів → 0% (не NaN). Смуга `width:${percent}%` коректна.
- 🟡 **Оцінки 0–12 / 0–100** — шкала визначається лише `isPupil` на клієнті і `profile.StudentType`
  на сервері; див. §8 про випадок «ніхто» → 0–100.
- 🟡 **Предмет без викладача.** Клієнт вимагає викладача (`canSave`), сервер — ні (`Teacher`
  nullable). Через API можна створити предмет без викладача; тоді у `BuildTitleDescription`
  опис пари просто не матиме викладача — не падіння, але інваріант «викладач обов'язковий»
  тримається лише на клієнті й суперечливий.
- 🟡 **Видалення предмета відв'язує (SetNull)** завдання/записи розкладу. Завдання лишиться з
  `SubjectId=null` → у таблиці «—». Запис розкладу з `SubjectId=null`: `BuildTitleDescription`
  дасть title=«Заняття», кабінет/посилання пари (що бралися з предмета) зникнуть із опису
  правила — **але опис правила в календарі НЕ перегенерується** при видаленні предмета (правило
  не чіпається), тож у планнері лишиться стара назва/кабінет. Розсинхрон.

## 10. Дата/час, межі, Unicode

- 🟠 **Дедлайни рахуються в часовому поясі СЕРВЕРА.** `ResolveDeadline` використовує
  `DateTime.Today` (локальний TZ процесу): `tomorrow = today+1`, `week = найближча неділя`
  (ISO-тиждень), `semester = SemesterEnd ?? StudyEnd`, `year = YearEnd` (може бути null → дедлайн
  null → ніколи не прострочено, сортується останнім), `date = DueDate`. Водночас «прострочено»
  для боргів порівнюється на **клієнті** з `todayApiDate()` (TZ браузера). → для користувача в
  іншому TZ відносні дедлайни (`tomorrow`/`week`) і класифікація «прострочено» можуть бути
  зсунуті на добу. Треба єдине джерело «сьогодні».
- 🟡 **`semester` фолбек на `StudyEnd`, `year` без фолбеку.** Якщо `YearEnd=null` — завдання «До
  кінця року» стає безстроковим (ніколи не борг). Дефолти створюються лише при першому GET
  settings (вересень-логіка); якщо користувач обнулив дати — дедлайни semester/year занулюються.
- 🟠 **Сітка дзвінків — межі лише в UI, час не валідується ніде.**
  - Кількість: `BOUNDS` (школяр 1–7, студент 1–6) керує лише `disabled` кнопок add/remove.
    **Сервер `ReplaceBellsAsync` не перевіряє ні min/max, ні тип користувача** → через API можна
    зберегти 0 пар (стерти сітку), 1 пару, 50 пар.
  - **`endTime < startTime` дозволено** (нема перевірки ні на клієнті, ні на сервері). Пара
    «кінець раніше за початок» зберігається; у поданнях покаже `14:00–08:00`, а як час події
    піде `startTime` — логічно безглуздо, але не падає.
  - **Перекриття/непослідовність пар** (пара 2 починається раніше за кінець пари 1) не
    перевіряється.
  - `Index` береться з клієнта (`i+1`); сервер зберігає як є → можливі дублі/пропуски індексів
    через прямий API.
  - `TimeOnly` із секундами: клієнт шле `"HH:MM:00"`, читає `slice(0,5)`. Якщо сервер колись
    віддасть із секундами ≠00 — обріжеться мовчки.
- 🟡 **Оцінки — межі.** Школяр select 0–12 (жорстко). Студент `type=number min=0 max=100
  step=0.01`, але **min/max/step браузером не примусові при ручному вводі/вставці** — можна
  надрукувати `999` чи `-5`; `Number()` їх прийме у стан. Рятує лише серверний клампінг (§8).
  Нечисловий ввід у number-полі блокується браузером (здебільшого).
- 🟡 **Проценти/прогрес** — `round(done*100/total)`; при 1 з 3 = 33% (округлення), сума по роботі
  завжди коректна, division-by-zero захищено.
- 🟡 **Порядок дат не перевіряється:** `studyStart > studyEnd`, `endDate < startDate` у правилах —
  сервер `GenerateBaseDates` поверне порожньо (не падає), але UI покаже «порожній розклад» без
  пояснення, чому.
- 🟢 **Unicode.** Назви предметів/викладачів/описів — довільний Unicode (укр. апострофи, емодзі) —
  зберігаються як текст, рендеряться екрановано. `localeCompare` для сортування за предметом/
  викладачем коректно працює з укр. Проблема лише з довжиною (§6), не з символами.
- 🟡 **`cycleWeeks` на сервері клампиться 1–4** (`GetWeekIndex`), ScheduleTab шле лише 1/2;
  але ExtraTab через повний `RecurrenceFields` може надіслати більше — усе клампиться, ок.

## 11. Продуктивність і надійність

- 🟠 **Гонки збереження налаштувань/дзвінків.** Три незалежні джерела пишуть `StudySettings`:
  верхній перемикач форми (`Study.handleSetForm` → весь об'єкт), `ScheduleTab.saveSettings`
  (локальний `cfg`), і дефолтне створення при GET. Без версіонування/ETag — **класичний
  last-write-wins**: редагування дат у ScheduleTab + перемикання форми зверху затирають одне
  одного (див. §1). `ScheduleTab` тримає власну копію `cfg`, синхронізовану через
  `useEffect([settings])`; зміна форми зверху оновлює `settings` → `cfg` перезатирається,
  **несхоронені правки дат зникають**.
- 🟠 **`ReplaceBells` — деструктивний повний replace** (`RemoveRange` + заново). Дві паралельні
  вкладки/повільна мережа → остання перемога стирає зміни іншої; збій усередині (після Remove,
  до Add) теоретично лишає порожню сітку (хоч і в одній транзакції SaveChanges). `BellsTab`
  тримає локальний `rows`, ініціалізований один раз — якщо сітку змінили деінде, ця вкладка
  збереже застарілий знімок.
- 🟠 **Генерація повторень / DoS (успадковано від Календаря).** Кожен запис розкладу/консультації
  = `RecurrenceRule` + шаблон-задача. `GetTasksForRangeAsync` щоразу тягне **ВСІ** правила
  користувача (`Where(UserId).ToListAsync()`) і для кожного крутить `GetEffectiveOccurrences`
  день-за-днем по діапазону. **Немає ліміту на кількість записів розкладу** → користувач (чи
  атака) створює тисячі правил study → кожен перегляд дня/періоду стає O(rules × days) у пам'яті
  застосунку. Плюс малформований `MonthDays` (§6) кидає виняток під час цієї генерації → 500 на
  головному календарі, а не лише в Навчанні.
- 🟡 **N+1-подібні перезавантаження на клієнті.** Після кожної мутації — повний `reload`
  (`getAssignments`/`getSubjects`/`getScheduleEntries`/`getProjects`). `DebtsTab` і
  `AssignmentsTab` — дві окремі вкладки, кожна робить власний `getAssignments`; `Planner`
  додатково смикає `getAssignments` через `loadDebts`. Багато дубльованих запитів за той самий
  набір.
- 🟡 **`GetScheduleEntriesAsync` відкидає записи без правила** (`Where(rules.ContainsKey(...))`).
  Якщо правило видалили, а запис лишився (частковий збій у `DeleteScheduleEntry`, де спершу
  `DeleteRecurrenceRuleAsync`, потім Remove entry, без єдиної транзакції) — **запис-сирота мовчки
  зникає з UI, але лишається в БД**. Немає транзакційної узгодженості між правилом і записом.
- 🟡 **Узгодженість парності з планувальником** — див. §9: при зміні `studyStart`/дзвінків уже
  створені правила не оновлюються, тож Навчання і головний календар можуть показувати різні
  час/парність/назву. Немає міграції існуючих правил при зміні налаштувань.
- 🟡 **Оптимістичні апдейти без інваліації** (§3) — при повільній мережі швидкі кліки
  «виконано/оцінка» можуть відправити кілька перекриваних `updateAssignment` із різним станом;
  немає черги/дебаунсу → фінальний стан сервера залежить від порядку відповідей.
- ⚪ `WeekCalendar` перераховує `monday/parity/days` на кожен offset через `useMemo` — дешево.
