## 1. Фронтенд — сторінка, картки, фільтр розділів, логіка

- [ ] 🟠 **Немає обробки помилок у жодному хендлері дій.** `handleAdd`, `handleDelete`, `handleCategoryChange`, `confirmCheck`, `handleSuggestion`, `handleReceipt`, `handlePlanTrip` викликають `apiSend`, який кидає виключення на не-2xx (`http.js`). Жодного `try/catch` → unhandled promise rejection, UI «мовчки» не оновлюється, користувач не бачить, що дія не відбулась. Стан `error` виставляється лише під час початкового `useEffect`.
- [ ] 🟠 **`reload()` після кожної дії теж без `catch`.** Якщо повторний `getShoppingList()` впаде (мережа), застаріле відображення залишиться, помилка не показується.
- [ ] 🟠 **Немає блокування повторних кліків.** Кнопки «Додати», «Куплено», «Відмітити», «Запланувати похід», «Розкласти суму» не дизейбляться на час запиту → подвійні/потрійні сабміти (див. §11 спам-задач і дублів).
- [ ] 🟡 **Форма додавання — тільки назва**, без кількості/одиниць (відповідає ОПИСу). Але після `handleAdd` немає фокусу назад в інпут → незручно додавати багато позицій поспіль.
- [ ] 🟡 **Фільтр розділу не скидається.** Якщо вибрано розділ (напр. «Аптека»), видалити останню позицію цього розділу — `presentSections` його прибере, але `sectionFilter` залишиться `'Pharmacy'`, `visibleItems` стане порожнім і покаже «порожній список», хоча інші розділи мають позиції. Активна пігулка зникне, а фільтр «залипне».
- [ ] 🟡 **`guessShoppingCategory` виконується на клієнті**, а не на сервері. Якщо бекенд колись додаватиме позиції з інших модулів (Food/Stock/Cycle) — категоризація розійдеться з клієнтською. `AddItemAsync` приймає `category` як є, без автовизначення на сервері.
- [ ] 🔵 **Картка показує `displayName`**, що для `CustomText` дорівнює і Uk, і En (сервер кладе однаковий текст). Для позиції-продукту — локалізована назва з довідника. Ок, але змішаний список виглядатиме непослідовно за мовою.
- [ ] 🟡 **Чекбокс «куплено» незворотний.** `disabled={item.isChecked}`, немає ендпоінта «зняти відмітку». Випадкова відмітка → лише видалення позиції (а запас/ціна/витрата вже записані — відкотити не можна, див. §9).

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо)

- [ ] 🟢/🟡 **Є стани `loading` і `error`** лише для первинного завантаження (`common.loading` / `common.error`). Ок, але див. §1 — для дій станів немає.
- [ ] 🟡 **Порожній стан залежить від фільтра.** `visibleItems.length === 0` → «Список покупок порожній», навіть якщо список не порожній, а просто вибрано розділ без позицій (пов'язано з §1 «залипанням» фільтра).
- [ ] 🟠 **Ціна при відмітці не валідовується по верхній межі перед відправкою.** `confirmCheck` бере `Number(checkPrice)`. `NumberStepper` клемпить до `[0, RANGES.money.max]` **лише на blur / через кнопки**; якщо користувач вводить число і одразу тисне «Відмітити», клемп на blur спрацює (бо фокус піде), але значення вже у стані — покладатися на порядок подій ненадійно.
- [ ] 🟡 **Порожнє vs нуль при відмітці.** «Відмітити» з порожнім полем → `price=undefined` (без ціни) — ок. Але якщо ввести `0` → `checkPrice='0'`, `'0' !== ''` → `price=0`: позиція отримає «відому ціну 0 ₴», запишеться витрата 0 ₴ і ціна продукту перезапишеться нулем. Навряд чи бажано.
- [ ] 🟡 **`budget` і `receiptTotal` — рядки зі `NumberStepper`.** `Number('')` не викликається завдяки гардам (`=== ''`), але варто впевнитись, що `NumberStepper` ніколи не віддасть рядок на кшталт `'.'` чи `'1.'` (при `allowDecimal` проміжний стан `'1.'` можливий → `Number('1.')=1`, ок, але `Number('.')=NaN`).
- [ ] 🟡 **Назва товару не обмежена за довжиною на клієнті.** Є лише `trim()`; дуже довгий рядок піде на сервер (див. §10).

## 4. Інтернаціоналізація (i18n) — назви категорій/розділів, невикористані застарілі ключі

- [ ] 🟡 **Багато застарілих невикористаних ключів** у `shoppingList.*` від старої реалізації: `priceLabel`, `categoryFormLabel` (використовується лише як `title`-фолбек), `autoCategory`, `groupEmpty`, `category.food/drinks/chemistry/stationery/other/uncategorized`, `ownedLabel`, `totalLabel`, `sectionFormLabel`, `section.Groceries/Pharmacy/Other`, `categoryPlaceholder`. Нова картка бере назви категорій/розділів **не з i18n**, а з `shoppingCategories.js` (`c.uk/c.en`, `sectionName`). Подвійне джерело правди + мертві ключі.
- [ ] 🟠 **Два паралельні переліки категорій розходяться.** Старі i18n-ключі `shoppingList.category.*` (food/drinks/chemistry/stationery/other/uncategorized) **не збігаються** з актуальним переліком у `shoppingCategories.js` (produce, meat_fish, dairy, bakery, grocery, drinks, frozen, sweets, condiments, medicine, hygiene, household, home, stationery, pets, other). Якщо десь ще використовуються старі ключі (QuickAdd/парсер) — буде неузгодженість назв.
- [ ] 🟡 **Назви розділів/категорій локалізуються з JS-масиву, а не з JSON** → перекладачі, які правлять лише `uk.json/en.json`, не змінять їх. Варто або перенести в i18n, або задокументувати.
- [ ] 🔵 **Перевірити EN-паритет для всіх активних ключів.** Вибірка (`priceAge`, `budgetCountNote`, `budgetFitsCount`, `receiptPerItem`, `planTripDone`) у `en.json` є. Пройтись по всьому активному набору на відсутні ключі.
- [ ] 🟡 **Плюралізація.** `budgetFitsCount` = «Влазить {count} позицій» та `receiptResult`/`priceAge` не мають форм однини/множини (укр. «1 позиція / 2 позиції / 5 позицій», «1 міс. / 2 міс.»). Завжди форма на «-ій».
- [ ] 🟡 **Валюта хардкоджена логікою.** У `receiptResult` рядок містить «грн» у тексті ключа, тоді як у картці валюта береться з `landing.moneyCurrency`. Непослідовність джерела валюти.

## 5. Доступність (a11y): чекбокс «куплено», NumberStepper, drawer

- [ ] 🟠 **Drawer не є модальним діалогом.** Немає `role="dialog"`, `aria-modal="true"`, немає переносу фокусу в панель при відкритті, немає **focus trap**, немає обробника **Escape** (закрити можна лише кліком по backdrop або хрестику — обидва мишею). Клавіатурні користувачі «провалюються» у фон.
- [ ] 🟠 **Фокус не повертається** на чекбокс/картку після закриття drawer.
- [ ] 🟡 **Чекбокс «куплено» семантично оманливий.** `onChange` не змінює чекбокс, а відкриває шторку; реальний стан ставиться лише після сабміту. Скрінрідер оголосить «checkbox, not checked», а після дії він стає `disabled checked`. Label обгортає лише `<input>`, видимого тексту немає — лише `title`.
- [ ] 🟡 **Кнопки `NumberStepper` мають `tabIndex={-1}`** — недосяжні з клавіатури; інкремент можливий лише стрілками нативного `type=number`. `aria-label="+"/"−"` є, але фокус на них не потрапляє.
- [ ] 🟡 **Селект категорії без видимого лейбла** — лише `title`. Для скрінрідера опис береться з `title`/плейсхолдера `categoryNone`.
- [ ] 🟡 **Пігулки фільтра/підказок — `<button>` без `aria-pressed`** для активного стану (візуально `pill--active`, семантично не позначено).
- [ ] 🔵 **Кнопка видалення** має `aria-label` + `data-tooltip` — ок; перевірити, що `data-tooltip` не дублюється читанням.

## 6. Бекенд — API, статус-коди, валідація

- [ ] 🔴 **`CheckItemAsync` взагалі не валідує ціну.** `CheckShoppingItemRequest(decimal? Price)` → `item.EstimatedPrice = price` без перевірок знаку та верхньої межі. Прямий виклик API з `price = -500` чи `price = 10^15` проходить (див. §8, §9, §10).
- [ ] 🟠 **`receipt-total` валідує лише `Total < 0`**, але не верхню межу (немає серверного `RANGES.money.max`). Величезна сума приймається.
- [ ] 🟠 **`SetCategoryAsync` не валідує категорію** — будь-який рядок приймається (mass assignment, див. §8).
- [ ] 🟡 **`AddItemAsync` валідує лише `Section` (whitelist) і наявність джерела назви**, але не перевіряє існування `ProductId`/`MedicineId` у довідниках. Неіснуючий `productId` → `Include(Product)==null` → `DisplayName` поверне порожні рядки → «порожня» картка.
- [ ] 🟡 **Невідповідність енумів Section.** Коментар у `Shopping.cs` каже `Groceries | Pharmacy | Other`, але whitelist в `AddItemAsync` і фронтові `SHOPPING_SECTIONS` містять 7 значень (+Household, Cosmetics, Stationery, Pets). Модель-коментар застарів.
- [ ] 🟡 **Статус-коди.** `AddItem` повертає `BadRequest{error:"invalid_item"}` або `Ok{id}`; Delete/SetCategory/Check — `NotFound`/`Ok`. `plan-trip` завжди `Ok`. Загалом розумно, але `Check`/`SetCategory` не розрізняють «не знайдено» від «чуже» (обидва 404 — це навіть добре для anti-enumeration, див. §7).
- [ ] 🔵 **`CurrentUserId` парсить `sub` через `int.Parse(... !)`** — якщо claim відсутній/некоректний → `NullReferenceException`/`FormatException` → 500 замість 401. Малоймовірно під `[Authorize]`, але краще безпечний парсинг.

## 7. Авторизація та власність (IDOR над чужими позиціями)

- [ ] 🟢 **Усі операції скоуплені по `UserId`.** `GetListAsync`, `DeleteItemAsync`, `SetCategoryAsync`, `CheckItemAsync` використовують `x.Id == id && x.UserId == userId`; `ApplyReceiptTotalAsync` і `BuildSuggestionsAsync` фільтрують `x.UserId == userId`. Чужу позицію не видалити/не змінити/не відмітити — повертається `NotFound`. **IDOR над позиціями не виявлено.** Зафіксувати як перевірено.
- [ ] 🟡 **IDOR над `taskId` з `plan-trip`.** Повертається `taskId` створеної задачі (для поточного користувача) — сам по собі безпечно. Але якщо фронт колись дозволить перехід/дію за цим `taskId` без повторної перевірки власності — ризик. Зараз `taskId` лише показується в тексті.
- [ ] 🟡 **`ReplenishStockAsync`/`UpsertPriceAsync`/`UserMedicines`** теж скоуплені по `userId` — ок. Перевірити, що `CheckItemAsync` не може поповнити чужий запас, якщо `productId` належить спільному довіднику (Product спільний — це нормально, запис `StockItem` все одно на `userId`).
- [ ] 🔵 **`PlanTripAsync` передає `sourceEntityId: 0`** — фіктивний id. Якщо десь по `sourceModule="shopping"` + `sourceEntityId` шукатимуть конкретну позицію — 0 нічому не відповідає.

## 8. Безпека (XSS у назві товару, масове призначення category/section)

- [ ] 🟢 **XSS у назві товару.** `CustomText` рендериться через `{displayName(item)}` (React екранує) — збережений XSS не спрацює в UI. Але текст зберігається **сирим** (`text.Trim()`, без санітизації) → небезпечно для будь-якого майбутнього несекранованого споживача (експорт, email, звіт). Зафіксувати припущення «React екранує».
- [ ] 🟠 **Mass assignment категорії.** `SetCategoryAsync` пише будь-який рядок у `Category`. Через картку селект пропонує лише валідні ключі, але прямий `PUT /category` з довільним/дуже довгим рядком приймається. Далі цей `Category` потрапляє у **`FinanceTransaction.Category`** при відмітці з ціною → засмічення фінансових категорій довільними значеннями.
- [ ] 🟡 **`Category` у картці** показується через `shoppingCategoryName`, яке для невідомого ключа повертає ключ **як є** (сирий рядок) у `title` селекта. React екранує — XSS немає, але видно «сміття».
- [ ] 🟢 **Section** захищений whitelist-ом в `AddItemAsync` — mass assignment розділу неможливий (повертає `null`→400). Але **через `SetCategory` розділ не оновлюється** взагалі: якщо вручну змінити категорію на таку, що належить іншому розділу (напр. `medicine`), `Section` залишиться старим (`Groceries`) → неузгодженість category↔section (клієнт `sectionForCategory` застосовується лише при створенні).
- [ ] 🟡 **`FinanceTransaction.Description = nameUk`** (сира назва товару) — знову покладання на екранування споживачем фінансів.

## 9. Бізнес-логіка та інваріанти

### Автокатегоризація (rule-based)
- [ ] 🔴 **Конфлікт ключових слів: «паста» → Гігієна, а не Бакалія.** У `KEYWORDS` правило `hygiene` (індекс 2) містить підрядок `'паст'` (для «зубна паста»), а `grocery` з `'макарон'` — значно нижче. Оскільки збіг за **підрядком** і перемагає **перше** правило, товар «**паста**» (макарони — приклад прямо з ОПИСу, «паста 110 грн») класифікується як **Гігієна/Косметика**, а не Бакалія. Явна помилка автокатегоризації на демо-даних.
- [ ] 🟡 **Інші потенційні підрядкові конфлікти:** `'олі'` (grocery, «олія») є підрядком у «**олівець**» — рятує лише те, що `stationery` з `'олівец'` стоїть вище; `'чай'` (grocery) є в «**чайник**» (мало б бути home); `'сир'` (dairy) vs `'сироп'` (medicine — medicine вище, тож ок). Порядок правил критичний і крихкий — будь-яка перестановка ламає класифікацію.
- [ ] 🟡 **Порядок правил = пріоритет**, але він не задокументований як контракт і легко порушується при додаванні слів. Специфічні категорії (medicine, hygiene, household, stationery, pets) навмисно вище за продуктові — варто покрити тестами.
- [ ] 🟢 **Невідома назва → `'other'`** (і `sectionForCategory('other')='Other'`). Порожня/пробільна → `'other'`. Ок.
- [ ] 🟡 **Регістр/діакритика.** `toLowerCase()` є, але немає нормалізації (напр. «мясо» без апострофа покрито окремим ключем `'мяс'`; а помилки типу «мʼясо» з U+02BC apostrophe — ключ `"м'яс"` використовує звичайний апостроф U+0027 → не збіжиться). Unicode-варіанти апострофа не враховані.

### Ціна при відмітці / витрата / запас
- [ ] 🔴 **Негативна / величезна ціна при відмітці** (сервер не валідує, §6): `price=-500` → `EstimatedPrice=-500`, `UpsertPrice` запише від'ємну особисту ціну, `FinanceTransaction.Amount=-500` (від'ємна витрата = фактично дохід). `price=10^15` → переповнення точності `decimal` колонки в MySQL / аномальна сума.
- [ ] 🟠 **Відмітка з ціною = один жест: запас + ціна + історія + витрата.** Але для позиції-**продукту** створюється `FinanceTransaction` і `PurchaseHistory` і `StockItem`; для **ліків** — лише `UserMedicine` (НЕ створюється `FinanceTransaction` навіть якщо ціна вказана? — ні, витрата створюється поза if-гілками, бо блок `if (price.HasValue)` окремий). Перевірити: витрата створюється для будь-якого джерела з ціною — ок. Але **історія покупок для ліків не пишеться** (лише для product/customText), тож ліки ніколи не потраплять у «часто купуєте».
- [ ] 🟡 **Відмітка без ціни** не оновлює ні особисту ціну, ні витрату, але запас/аптечку/історію — оновлює. Консистентно з ОПИСом.

### Розклад суми чека
- [ ] 🔴 **Подвійний облік витрат.** Позиції, відмічені **з ціною**, вже створили `FinanceTransaction` на свою ціну. Потім `ApplyReceiptTotalAsync` створює **ще одну** `FinanceTransaction` на **весь `Total`** (категорія «shopping», опис «Покупки за чеком»). Відомі ціни входять і в свої окремі витрати, і в суму чека → **витрати подвоюються**. Серйозна фінансова неузгодженість.
- [ ] 🔴 **Чек застосовується до ВСІХ відмічених позицій за весь час.** Вибірка `x.UserId == userId && x.IsChecked` — без вікна/сесії/прив'язки до походу. Відмічені тижнями тому позиції без ціни отримають `EstimatedPrice = perItem` від нового чека; `KnownSum` рахується по всіх історично відмічених із ціною. Один чек «розмазується» по старих покупках.
- [ ] 🟠 **Решта від'ємна → обрізається до 0.** `remainder = Math.Max(0, total - knownSum)`. Якщо `total < knownSum` (сума чека менша за вже відомі ціни), решта = 0, `perItem=0` — усі позиції без ціни стануть 0 ₴, але витрата на весь `total` все одно запишеться (і подвоїться з §вище). Користувач не попереджений, що введена сума менша за відоме.
- [ ] 🟠 **Втрата залишку при округленні.** `perItem = Round(remainder/unknown.Count, 2)`. `Σ perItem` може не дорівнювати `remainder` (напр. 10/3 → 3.33×3 = 9.99). Останню позицію не коригують на залишок. Сума цін позицій ≠ сума чека (хоча витрата = `total`).
- [ ] 🟡 **Ділення коли `unknown.Count == 0`** → `perItem=0`, `split` порожній, але витрата на `total` все одно створюється. Тобто можна «списати» довільну суму чека, навіть якщо немає жодної позиції без ціни.
- [ ] 🟡 **`ApplyReceiptTotalAsync` не оновлює запас/історію** — лише ставить ціни й пише одну витрату. Для продуктів викликає `UpsertPriceAsync` (перезапише особисту ціну значенням `perItem`, можливо 0). Перезапис реальних цін усередненим `perItem` — спотворює історію цін.

### Докупити в межах бюджету
- [ ] 🟠 **Режим «за кількістю» vs «за сумою».** `byCount = known < total/2`. Коли `total === 0` (немає невідмічених позицій): `0 < 0` = false → режим суми, бюджет>0, `toBuy` порожній → «нічого не влазить». Прийнятно, але повідомлення оманливе (справа не в бюджеті).
- [ ] 🟠 **У режимі суми позиції без ціни «безкоштовні».** `price = x.estimatedPrice ?? 0` → невідома ціна = 0, така позиція завжди «влазить» і не споживає бюджет. Користувач бачить товар як «по кишені», хоча ціна невідома.
- [ ] 🟡 **Не оптимізація, а жадібний перебір у порядку списку** (`OrderBy IsChecked, CreatedAt`), не за ціною. «Влазить» — не максимальний набір. За задумом просто, але варто зафіксувати як обмеження.
- [ ] 🟡 **0 бюджет / порожній** → `limit <= 0` → `[]`. `NumberStepper min=0` не дає від'ємного через кнопки/blur, але режим count із `budget='0'` коректно дає порожньо.
- [ ] 🟡 **У режимі count `limit` може бути дробовим** якщо хтось обійде (NumberStepper без `allowDecimal`, тож цілий) — `slice(0, 2.5)` поведеться дивно; зараз захищено відсутністю `allowDecimal`.

### «Часто купуєте» (90 днів)
- [ ] 🟢 **Приватність історії.** `BuildSuggestionsAsync` фільтрує `h.UserId == userId` — **чужа історія не витікає.** Зафіксувати як перевірено.
- [ ] 🟡 **Тільки продукти з довідника.** `h.ProductId != null` — покупки з `CustomText` ніколи не стають підказками, навіть якщо купуються щотижня.
- [ ] 🟡 **Вікно 90 днів через `DateTime.Now.AddDays(-90)`** (локальний час сервера), а `PurchasedAt` пишеться як `DateTime.Now`, тоді як `CreatedAt` моделі — `DateTime.UtcNow`. Змішування Now/UtcNow (див. нижче) може зсунути межу вікна на години.
- [ ] 🔵 **`Take(10)`** без пагінації/налаштування — захардкоджено.

### «Запланувати похід» → задача
- [ ] 🔴 **Спам задач.** Кожен клік «Запланувати похід» створює **нову** задачу «Купити за списком» (`CreateTaskAsync`), без перевірки, чи вже існує незавершена задача-похід. Клікнути 50 разів → 50 задач у «Нерозподілених».
- [ ] 🟡 **`tripTaskId` показується лише локально** й не скидається при повторному кліку — створиться друга задача, а текст покаже лише останній id.
- [ ] 🟢 **IDOR над taskId:** задача створюється для `CurrentUserId` через `TaskService`; повернений id належить користувачу. Сам показ id безпечний (див. §7).

### Вік ціни «N міс.»
- [ ] 🟡 **`MonthsSince` рахує календарні місяці** з корекцією на день (`now.Day < from.Day → months--`), `Math.Max(0,...)`. Коректно, але: ціна, оновлена `UpsertPrice` з `DateTime.Now`, порівнюється з `DateTime.Now` → якщо `UpdatedAt` у майбутньому (годинник/таймзона), `months` обрізається до 0. У картці показ лише коли `priceAgeMonths > 0` — свіжа ціна (0 міс.) не показує вік. Ок.

### Загальне
- [ ] 🟠 **Змішування `DateTime.Now` і `DateTime.UtcNow`.** Модель: `CreatedAt = UtcNow`, `PurchasedAt = UtcNow` (дефолти); сервіс скрізь використовує `DateTime.Now` (локальний) для `CheckedAt`, `UpdatedAt`, вікна 90 днів, `OccurredAt`. На сервері з ненульовим UTC-offset це дає неузгоджені дати (вік ціни, межа 90 днів, сортування). Уніфікувати на UTC.
- [ ] 🟡 **Порожня назва** відсікається і на клієнті (`text.trim()`), і на сервері (`IsNullOrWhiteSpace`) → `BadRequest`. Ок.

## 10. Дані, межі, Unicode, довгі назви

- [ ] 🔴 **Від'ємна ціна** при відмітці (прямий API) — немає серверного гарда (§6, §9). `NumberStepper` на UI не дасть мінус (`sanitize` лишає лише цифри), але бекенд довіряє клієнту.
- [ ] 🟠 **Величезна ціна/бюджет/чек.** Фронт клемпить до `RANGES.money.max = 1_000_000_000`, **але лише на blur** і лише в UI. Сервер не має еквівалента для `price` (і для `receipt-total` — лише `<0`). Значення > `decimal`-точності колонки → помилка збереження / аномалії.
- [ ] 🟡 **Дроби.** `allowDecimal` у полях ціни/чека. `EstimatedPrice`/`Amount` — `decimal`. Перевірити точність колонки MySQL (`decimal(p,s)`); `perItem` округлюється до 2, але ручна ціна — ні (напр. 3.333 збережеться як є або обріжеться схемою).
- [ ] 🟡 **Роздільник дробу.** `NumberStepper` конвертує `,`→`.`. Але локаль відображення ціни (`{item.estimatedPrice} {currency}`) без форматування — покаже `3.33` крапкою навіть в укр. UI, та «сирі» довгі дроби/експоненту для великих чисел.
- [ ] 🟡 **Дуже довга назва товару.** Немає `maxlength` на інпуті й немає обмеження довжини в `AddItemAsync`/моделі (`CustomText` nvarchar без явного ліміту?). Довжелезний рядок зламає верстку картки (`word-break: break-word` пом'якшує) і роздує БД. Перевірити max-length колонки.
- [ ] 🟡 **Unicode / емодзі / RTL у назві** — зберігається як є; React екранує при показі. RTL-назва може «поплисти» у flex-картці. Апостроф-варіанти ламають автокатегоризацію (§9).
- [ ] 🔵 **`productId`/`medicineId` за межами довідника** — приймаються без перевірки існування (§6) → порожні картки, «висячі» FK.

## 11. Продуктивність і надійність

- [ ] 🟠 **Гонка «відмітка/видалення».** Drawer відмітки тримає `checkingId`. Якщо позицію видалити (інший таб/подвійна дія) поки drawer відкритий, `confirmCheck` піде на видалений id → сервер `NotFound` → `apiSend` кине виключення без `catch` (§1) → `reload()` не виконається, стан «зависне».
- [ ] 🟠 **Спам повторного додавання / дублі.** Немає дедуплікації: «молоко» можна додати багаторазово (кожне — окремий `ShoppingItem`). Підказки «часто купуєте» виключають лише позиції-**продукти**, що вже в списку (`inList` по `ProductId`), але ручні текстові дублі не відсікаються. Швидкі кліки по одній підказці створять кілька однакових позицій (немає debounce/disable).
- [ ] 🟠 **Спам-кнопки без дизейблу:** «Запланувати похід» (§9 — множинні задачі), «Розкласти суму» (§9 — множинні витрати на весь чек!), «Додати». Кожен повторний клік = ще один серверний запис.
- [ ] 🟡 **Повне перезавантаження списку після кожної дії** (`reload()` → `GET /api/shopping-list` з `Include(Product)`, `Include(Medicine)`, словник цін, підказки за 90 днів). При великому списку/історії — важкий запит на кожен чек/видалення/зміну категорії. Немає оптимістичних оновлень.
- [ ] 🟡 **`GetListAsync` + `BuildSuggestionsAsync`** роблять кілька запитів (items, prices, history) — N+1 пом'якшено `Include`, але історія за 90 днів із `Include(Product)` може бути великою; групування/сортування в пам'яті (`ToListAsync` → LINQ-to-objects).
- [ ] 🟡 **Багато позицій** → `grid auto-fill minmax(210px)` рендерить усі картки без віртуалізації; сотні позицій = повільний рендер + важкий `reload` щоразу.
- [ ] 🔵 **Відсутність транзакції в `CheckItemAsync`/`ApplyReceiptTotalAsync`.** Кілька змін (запас + ціна + історія + витрата) зберігаються одним `SaveChangesAsync` (EF обгортає в одну транзакцію — ок), але `PlanTripAsync` делегує `TaskService` окремо. Переконатися, що часткових збоїв немає.
- [ ] 🔵 **Паралельні `UpsertPriceAsync`/`ReplenishStockAsync`** без унікального індексу/ON CONFLICT — дві одночасні відмітки того самого продукту можуть створити дубль `UserProductPrice`/`StockItem` (race між `FirstOrDefault` і `Add`). Перевірити унікальні обмеження PK `{UserId, ProductId}`.

1. 🔴 **Подвійний облік витрат** (ціна при відмітці + сума чека на весь `Total`) — `ApplyReceiptTotalAsync`.
