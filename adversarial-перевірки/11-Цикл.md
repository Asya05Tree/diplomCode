# Adversarial review — Менструальний цикл

> Обсяг перевірки: `client/src/pages/Cycle.jsx`, `client/src/pages/Cycle.css`, `client/src/api/cycle.js`, `client/src/components/planner/DayView.jsx`, `client/src/pages/Planner.jsx`, `client/src/App.jsx`, `client/src/components/Sidebar.jsx`, `client/src/i18n/{uk,en}.json`, `server/Controllers/CycleController.cs`, `server/Services/CycleService.cs`, `server/Models/Cycle.cs`, `server/Services/AccountService.cs`.
>
> **Контекст ризику:** це найчутливіший розділ застосунку — медичні/репродуктивні дані. Будь-який витік, IDOR або відсутній серверний гейтинг тут важить більше, ніж у будь-якій іншій вкладці. Нижче все згруповано за розділами; критичні пункти позначені 🔴, вагомі 🟠, косметичні 🟡.

## 1. Фронтенд — сторінка, дашборд, календар, фази, історія, логіка

- [ ] 🔴 **Відмітка «кінець» на календарі/у DayView не має обмеження «лише коли є відкритий запис».** Герой-кнопка `btn-period--end` справедливо `disabled={!openRecord}` (Cycle.jsx:355), але поповер клітинки (`handlePick('end', api)`, Cycle.jsx:301) і кнопка в `DayView` (`markPeriod('end')`, DayView.jsx:213) викликають `markCycleEnd` для будь-якого дня. Захист «кнопка disabled» суто косметичний і легко обходиться двома іншими шляхами.
- [ ] 🟠 **Герой `openRecord` визначається як перший запис без `endDate` (Cycle.jsx:171), а кнопка кінця ставить кінець на `todayApiDate()`.** Якщо відкритий запис почався в майбутньому (запис заднім числом навпаки — на завтра), кнопка активна, але кінець ставиться «сьогодні» — тобто раніше за старт. Жодної перевірки `end ≥ start` на клієнті.
- [ ] 🟠 **`computeCycleStats` і серверний `ComputeForecast` рахують різні речі й можуть розійтися.** Клієнт самостійно рахує `avgCycleLength`, `isRegular`, `cycleDay`, `avgPeriodLength` (Cycle.jsx:33–60), сервер — свій `forecast`. Герой показує серверний `forecast.isRegular`/`insufficientHistory`, а метрики — клієнтський `stats.isRegular`. При розбіжності (різні «сьогодні», різні дані у відповіді) користувачка побачить суперечливі «Регулярний/Нерегулярний» в одному екрані.
- [ ] 🟠 **День циклу без верхньої межі.** `cycleDay = Math.max(1, daysBetween(lastStart, today)+1)` (Cycle.jsx:57). Якщо остання відмітка — рік тому (користувачка перестала вести), метрика покаже «День циклу 400 / 28», смужка прогресу застрягне на 100%, а фаза «прогноз» давно в минулому. Немає стану «дані застаріли».
- [ ] 🟠 **`progressPct` базується на `avgCycleLength`, що може бути дефолтним 28.** При одному записі `avgCycleLength = 28` (дефолт), тож смужка й «з 28» виглядають як реальні дані, хоча це просто заглушка. Користувачка не відрізнить виміряне середнє від дефолту.
- [ ] 🟠 **Фаза «фолікулярна»/«лютеїнова» може мати інвертований діапазон.** `follicular.to = ovulation − 1`, `ovulation = nextStart − 14` (Cycle.jsx:71,76). Якщо `avgPeriodLength` велике (через брудний запис з `endDate` далеко після `startDate`) → `periodEnd` може перевищити `ovulation`, і діапазон фолікулярної стане «пізніша дата – ранніша дата». Жодного клампінгу `from ≤ to`.
- [ ] 🟡 **Рядок прогнозу в героєві змішує формати дат:** `fmtShort(fromR)` (d.m) для «від» і `formatDate(toR)` (локальний формат) для «до» (Cycle.jsx:227) — у межах одного діапазону два різні формати. Те саме у прогноз-рядку таблиці (Cycle.jsx:459).
- [ ] 🟡 **`historyRows` рахує `cycleLen` як відстань до наступного старту** (Cycle.jsx:246), тож останній (найсвіжіший) запис завжди має `—` в «Довжині циклу». Для користувачки з одним записом — усе `—`, що очікувано, але без пояснення.
- [ ] 🟡 Клік по клітинці-прогнозу (пунктир) теж відкриває поповер «Початок/Кінець/Прибрати» — на прогнозований день «Прибрати» нічого не робить (запису нема), але пункт показується.
- [ ] 🟡 Двомісячний календар завжди показує `new Date()` + наступний місяць; немає навігації назад — минулі цикли в календарі недоступні (лише в таблиці). Для «реєстру історії» це прийнятно, але легенда/позначки минулого невидимі.

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, друк PDF (no-print)

Прибрати разом із відповідними i18n-ключами (див. §4).

У темній темі фон клітинки лишається світло-рожевим (`--cycle-period-soft` не переозначено для dark), тож контраст тексту на темному тлі сторінки локально ок, але самі свотчі/фони циклу не мають dark-варіантів — лише `--status-*` переозначено (Cycle.css:31–34). Варто перевірити контраст `#8a2b5a` на `#fce3ee` (≈ проходить) і загальну «світлу пляму» календаря в темній темі.
- [ ] 🟠 **Друк/PDF ховає потрібне, але варто перевірити повноту.** `@media print` ховає `.sidebar`, `.app-header`, `.no-print` (Cycle.css:257–265). `no-print` стоїть на: герой-діях (Cycle.jsx:351), колонці дій таблиці (453,464,478), картці налаштувань (493). Перевірити вручну: чи не лишається порожня колонка-привид у таблиці (th.no-print прихований, але клітинки `td` теж `no-print` — ок), чи не друкується поповер `cyc-pick` якщо був відкритий у момент друку (він не `no-print` → **може потрапити в PDF**).
- [ ] 🟠 **Друк оголює ВСЮ медичну історію.** Це за задумом (експорт), але означає: будь-хто, хто натисне «Експорт у PDF» на спільному/робочому ПК, віддрукує повний реєстр місячних. Жодного попередження/підтвердження перед `window.print()` (Cycle.jsx:358). Розглянути застереження про чутливість.
- [ ] 🟡 Легенда (`cyc-legend`) не має `no-print` → друкується, що доречно. Але «Сьогодні» в PDF втрачає сенс (друк статичний) — дрібниця.
- [ ] 🟡 `.cyc-metrics` — flex із `border-right` між елементами; при переносі на вузькому екрані (`flex: 1 1 150px`) останній елемент у рядку збереже `border-right`, бо `:last-child` стосується лише останнього з п'яти. Косметичний артефакт сітки роздільників.
- [ ] 🟡 Поповер `cyc-pick` позиціонований `top:100%` від клітинки; для клітинок останнього тижня/біля краю екрана він вилазить за нижній/правий край без репозиціювання (немає collision detection).

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо)

- [ ] 🟠 **Більшість мутацій без обробки помилок.** `handleMarkStart`, `handleMarkEnd`, `handleDelete`, `handleToggleReduceLoad`, `handleSetHygiene` (Cycle.jsx:178–206) не загорнуті в `try/catch`. Падіння мережі/сервера → необроблений rejection, жодного тосту/повідомлення, UI мовчки не оновлюється. Лише `handlePick` має `catch {}` — і той **глушить помилку повністю** (Cycle.jsx:214), тож «Прибрати»/«Кінець» без запису провалюються беззвучно.
- [ ] 🟠 **Немає стану «збереження…» / блокування під час польоту запиту.** Кнопки лишаються активними, поки йде `reload()` — відкриті двері для гонок (див. §11).
- [ ] 🟡 Стани loading/error/empty є (Cycle.jsx:313–326, 441) і охайні. Але error-екран — просто текст `common.error` без кнопки «повторити»; єдиний шлях відновлення — перезавантаження сторінки.
- [ ] 🟡 Toggle/select оптимістично оновлюють `settings` локально до відповіді сервера (Cycle.jsx:195–197, 203–205); якщо `setCycleSettings` впаде, UI показуватиме несправжній стан до наступного `getCycle`.

## 6. Бекенд — API, статус-коди, валідація дат

- [ ] 🔴 **Жодної валідації логіки дат на сервері.** `AddRecordAsync`/`StartByDateAsync` приймають будь-яку `DateOnly` (CycleService.cs:88,99). `EndByDateAsync`/`EndRecordAsync` ставлять `EndDate` без перевірки `EndDate ≥ StartDate` (CycleService.cs:114,144). Наслідок: від'ємна тривалість менструації, яка потім ламає клієнтські розрахунки (`periodLen` від'ємний/`null`).
- [ ] 🔴 **Ризик `ArgumentOutOfRangeException` → 500.** `ComputeForecast` робить `last.AddDays(DefaultCycleLength)` / `last.AddDays(avg)` (CycleService.cs:74,85). Якщо старт близько до `DateOnly.MaxValue` (9999-12-31) — `AddDays` кине виняток, GET `/api/cycle` впаде 500. Немає верхньої/нижньої межі дозволених дат.
- [ ] 🟠 **`EndByDateAsync` мовчки перезаписує кінець уже завершеного запису.** Знаходить найпізніший запис зі `StartDate ≤ date` і ставить `EndDate = date` **незалежно від того, чи він уже закритий** (CycleService.cs:107–117). Відмітка кінця «заднім числом» на старому циклі зіпсує давно завершений запис. Немає інваріанта «закривати лише відкритий».
- [ ] 🟠 **Мутації повертають 200 OK навіть коли «нічого не змінилось».** `MarkStart` на існуючу дату повертає `id` існуючого (ок), але `MarkEnd`/`Clear` повертають `NotFound` лише якщо запису взагалі нема — семантика «кінець поставлено не туди» не відрізняється від успіху.
- [ ] 🟠 **Немає `ModelState`/атрибутів валідації** на `CycleSettingsRequest.HygieneProduct` — приймає будь-який рядок; сервіс потім мовчки зводить невідоме до `null` (CycleService.cs:169). Довгий/сміттєвий рядок прийметься з 200 OK (не зберігається, але й не 400).
- [ ] 🟡 `AddRecord` повертає `{ id }` 200; `MarkStart` теж `{ id }`. `MarkEnd`/`Clear`/`Delete` → 200/404. Немає 201 Created для створення запису — дрібна невідповідність REST.
- [ ] 🟡 Немає ідемпотентності/захисту від повторного POST `records` з тією ж датою через `/records` (на відміну від `/start`, який дедуплікує) — через `AddRecordAsync` можна створити дублі-старти на одну дату (клієнт не викликає, але ендпоінт відкритий).

## 7. Авторизація, власність і ПРИВАТНІСТЬ (гейтинг female; IDOR)

- [ ] 🔴 **ГЕЙТИНГ `female` — ЛИШЕ НА КЛІЄНТІ. Сервер не перевіряє стать взагалі.** `CycleController` має тільки `[Authorize]` (CycleController.cs:16), жодної перевірки `gender`. Усі обмеження — фронтові: `App.jsx:207` (`Navigate` якщо не female), `Sidebar.jsx:33` (ховає пункт), `Planner.jsx:129` (`if gender !== 'female' return`), `DayView.jsx:209` (умовний рядок). **Будь-який автентифікований користувач (стать «Чоловіча» або взагалі не задана) може з curl/DevTools робити GET/POST/PUT/DELETE на `/api/cycle/*`** — читати, створювати й видаляти власні записи циклу в обхід призначення фічі. Для найчутливіших даних це недопустимо: гейтинг має бути на сервері (перевірка `HealthProfile.Gender == "female"` у контролері/фільтрі), інакше клієнтський — лише UX, не безпека.
- [ ] 🟠 **IDOR між користувачами — наразі закрито, але тримати під наглядом.** `EndRecordAsync`/`DeleteRecordAsync` фільтрують `x.Id == id && x.UserId == userId` (CycleService.cs:142,152) → чужий `id` дає `NotFound`. `UserId` береться з JWT `sub` (CycleController.cs:26), не з тіла. Перевірити: немає жодного ендпоінта, що приймає `userId` ззовні; `records/{id}/end` і `DELETE records/{id}` — єдині з `id` в маршруті, обидва scoped. **Додати тест-кейс:** користувач A намагається `POST /api/cycle/records/{B_id}/end` → має бути 404, не 200.
- [ ] 🟠 **`CurrentUserId` робить `int.Parse(... sub ...!)` без захисту** (CycleController.cs:26). Токен без `sub` → `NullReferenceException`/`FormatException` → 500 замість 401. Не IDOR, але погана відмова.
- [ ] 🟠 **Автостворення `CycleSettings` на GET для будь-кого** (CycleService.cs:51–57). Чоловічий акаунт, смикнувши GET, створить собі рядок налаштувань циклу в БД — побічний запис через відсутній серверний гейт.
- [ ] 🟡 Експорт даних акаунта (`AccountService.cs:145`) включає сирі `CycleRecords` у JSON — медичні дати у відкритому вигляді у файлі вивантаження. «Видалити всі дані» їх чистить (AccountService.cs:54). Зберігання — без шифрування поля/аудиту доступу (очікувано для диплому, але варто згадати в розділі приватності).

## 8. Безпека (витік медичних даних, масове призначення, друк/експорт)

- [ ] 🟠 **Масове призначення (mass assignment) обмежене DTO — добре, але перевірити.** Запити — `record`-DTO з явними полями (CycleController.cs:8–11); `UserId`/`Id` з тіла не біндяться. `SetSettingsAsync` приймає лише два поля. Ризик низький; підтвердити, що немає прихованого байндингу навігаційних властивостей.
- [ ] 🟠 **Витік через спільний пристрій/експорт.** `window.print()` без підтвердження (§2) + JSON-експорт (§7) — два канали, якими повний медичний реєстр лишає застосунок. Немає ре-автентифікації перед експортом/друком найчутливішого розділу.
- [ ] 🟠 **Відсутність серверного гейта = потенційний витік самого факту наявності даних.** Навіть якщо чоловічий акаунт «не має» показувати цикл, сервер віддасть його `CycleDto` (порожній або ні) — підтверджуючи, що ендпоінт живий і не фільтрує за статтю. Enumeration/recon поверхня.
- [ ] 🟡 Назви засобів гігієни захардкоджені на сервері (CycleService.cs:29–36), ключ валідований whitelist-ом (CycleService.cs:169) — ін'єкція довільного тексту в список покупок через `hygieneProduct` неможлива. Добре.
- [ ] 🟡 `EnsureHygieneSupplyAsync` пише в чужий модуль (ShoppingItems) з `Source="Cycle"` (CycleService.cs:205) — перевірити, що `ShoppingService.AddItemAsync` теж scoped по `userId` і не допускає підміни категорії/розділу.
- [ ] 🟡 Немає rate-limiting на мутаціях циклу — скриптом можна забити БД тисячами записів-стартів (кожен створює рядок), особливо без серверного гейта.

## 9. Бізнес-логіка та інваріанти

- [ ] 🔴 **`reduceLoadOnHeavyDays` — повністю мертвий інваріант.** Зберігається (Cycle.cs:20), повертається в DTO (CycleService.cs:39,62), перемикається в UI (Cycle.jsx:495) з обіцянкою впливу на перенос задач — але **ЖОДЕН код (ні сервер, ні клієнт, ні TaskService) його не читає** (grep по всьому репо: лише запис/читання самого налаштування, жодного споживача). «Впливає на пропозиції переносу задач» — функції не існує. Або реалізувати, або прибрати чекбокс+підказку.
- [ ] 🟠 **Прогноз при 0/1/2 записах — перевірити кожну гілку:**
  - 0 записів → `HasData=false`, `InsufficientHistory=false`, `rangeDays=5` (CycleService.cs:70). Клієнт показує `forecastNoData`. Ок.
  - 1 запис → `InsufficientHistory=true`, `predicted = last+28`, `IsRegular=null` (CycleService.cs:74). Клієнт показує `forecastInsufficient`. Ок, але `AverageLength=null` → метрика «Середня довжина» бере клієнтський дефолт 28, що виглядає як реальне середнє (§1).
  - ≥2 → `avg`, `spread=max−min`, `IsRegular = spread ≤ 3` (CycleService.cs:80–82). Ок.
- [ ] 🟠 **Нерегулярність: розкид > 3 → `rangeDays = ceil(spread/2)+2`** (CycleService.cs:83). При великому `spread` (наприклад, брудний запис) діапазон прогнозу роздувається до десятків днів — «Наступний початок: 01.01 – 20.02» виглядає безглуздо, але попередження `forecastIrregular` показується. Перевірити верхню межу `rangeDays`.
- [ ] 🟠 **Овуляція = прогноз − 14 (орієнтовно)** (Cycle.jsx:71). Для коротких циклів (<18 днів) овуляція випаде на дні менструації/до старту попереднього — фаза «фолікулярна» зникне або інвертується (§1). Немає клампа на мінімальну довжину циклу.
- [ ] 🟠 **День циклу `max(1, …)`** (Cycle.jsx:57) коректно не допускає 0/від'ємного для майбутнього старту, але не має стелі (§1). Сервер власного «дня циклу» не рахує — лише клієнт; при розбіжності «сьогодні» клієнт/сервер (таймзони) день зсунеться.
- [ ] 🟠 **Дефолти 28/6:** `DEFAULT_CYCLE_LENGTH=28` (клієнт Cycle.jsx:18) і `DefaultCycleLength=28` (сервер CycleService.cs:22) — збігаються. Але `DEFAULT_PERIOD_LENGTH=6` існує **лише на клієнті** (Cycle.jsx:19); сервер період взагалі не рахує (`ComputeForecast` ігнорує `endDate`). Джерело правди для «середньої менструації» — тільки клієнт. Задокументувати/узгодити.
- [ ] 🟠 **Синхронізація з головним календарем:** відмітки йдуть через ті самі `/api/cycle/start|end|clear` і з Cycle, і з DayView (DayView.jsx:110–112); Planner перезавантажує через `cycleVersion` (Planner.jsx:57,156). Перевірити: відмітка в DayView → `onCycleChanged` інкрементить версію → Planner робить `getCycle`, але **вкладка Cycle (інша сторінка) не знає про зміну** — при поверненні треба свіжий `getCycle` (робиться в `useEffect` на монтуванні, ок). Крос-табове неузгодження можливе лише в межах однієї сесії двох відкритих вкладок браузера.
- [ ] 🟠 **Засіб гігієни → покупки (консистентність і дублі):**
  - Додається на GET, `AddRecord`, `EndRecord`, `MarkEnd`, `SetSettings` (виклики `EnsureHygieneSupplyAsync`). Умова: обрано засіб І (`ongoing` АБО `soon ≤5 дн`) (CycleService.cs:191–199).
  - Дедуп: не додає, якщо є **незакреслена** позиція `Source="Cycle"` (CycleService.cs:201–203). 🟠 Але щойно користувачка **викреслить** куплене, наступний GET/дія **знову додасть** позицію (бо `!IsChecked` вже false) — навіть у межах того самого циклу повторна поява. Немає прив'язки «один засіб на один цикл».
  - 🟠 При знятті засобу (`hygieneProduct=null`) раніше додана позиція **НЕ видаляється** (коментар прямо каже «нічого не видаляємо», CycleService.cs:176). Очікувано, але означає: обрав помилково → лишилось у покупках назавжди.
  - 🟠 `ongoing` на сервері = відкритий запис не довше `OpenPeriodMaxDays=8` (CycleService.cs:193), тоді як клієнт малює період відкритого запису аж до «сьогодні» з guard-ом 40 днів (Cycle.jsx:96–99). **Різні визначення «триває»** між доданням покупки (8 днів) і підсвіткою календаря (40 днів).
- [ ] 🟡 `ComputeForecast` на клієнті (`utils/cycle.js`, згаданий у коментарі CycleService.cs:65 як «дзеркало») — перевірити, що клієнтська версія ще існує й не розійшлася; у Cycle.jsx прогноз приходить із сервера, тож клієнтське дзеркало може бути застарілим мертвим кодом.

## 10. Дата/час (записи заднім числом, відкритий період, запобіжники 40/400, таймзони), межі, Unicode

- [ ] 🔴 **«Відкритий період рахується до сьогодні» має запобіжник лише 40, і лише на клієнті.** `buildCalendarMarks` для відкритого запису бере `last = today` і заповнює дні циклом `for (guard=0; cursor<=last && guard<40; …)` (Cycle.jsx:96–99). Guard=40 рятує від зависання, **але сервер такого захисту не має зовсім** — `ComputeForecast`/`EnsureHygiene` не ітерують по днях, тож «зависання» не там; реальна серверна небезпека — `AddDays` overflow (§6). Прошене «400 днів» як запобіжника **ніде не існує** — ні на клієнті (є лише 40), ні на сервері. Якщо старт відкритого запису давній, календар обріже на 40 днів (неточно, але безпечно), а метрика «День циклу» роздується без межі (§9).
- [ ] 🔴 **Записи заднім числом + накладені/вкладені періоди не контролюються.** `StartByDateAsync` дедуплікує лише точний збіг `StartDate` (CycleService.cs:101), але дозволяє старт **усередині** вже існуючого періоду (напр., старт 5-го при записі 1–8). Жодної перевірки перекриття. Наслідок: два «цикли» завдовжки 4 дні замість одного; `cycleLengths` отримає аномально малий інтервал → `spread` роздується → хибна «нерегулярність».
- [ ] 🟠 **Таймзони: «сьогодні» клієнта ≠ «сьогодні» сервера.** Клієнт скрізь `todayApiDate()` (локальний час браузера); сервер `DateTime.Today` (локальний час сервера, CycleService.cs:188). «Відмітити початок/кінець» шле `todayApiDate()` клієнта, а `EnsureHygieneSupply`/`soon`/`ongoing` рахуються від серверного `Today`. При розбіжності TZ (напр., користувач UTC+2, сервер UTC) засіб може додатись/не додатись на день раніше/пізніше, а «День циклу» зсунутись на 1. Жодної фіксації TZ користувача.
- [ ] 🟠 **Прогнозований період у календарі заповнюється `periodLen` ітерацій** (Cycle.jsx:108), де `periodLen = avgPeriodLength ?? 6`. Якщо `avgPeriodLength` роздутий брудним записом (endDate далеко після start), прогнозна зона розтягнеться на десятки днів без guard-а (на відміну від period-петлі з guard 40).
- [ ] 🟠 **`daysBetween` через `(fromApiDate(b) − fromApiDate(a)) / 86400000`** (Cycle.jsx:22) — ділення мілісекунд. При переході на літній/зимовий час доба може бути 23/25 год → `Math.round` рятує більшість випадків, але на межі DST можлива похибка ±1 день у довжині циклу. Сервер використовує `DayNumber` (CycleService.cs:78) — коректно й без TZ; клієнт — ні. Неузгоджений метод підрахунку.
- [ ] 🟡 Межі місяця: `renderMonth` бере `new Date()` і `addMonths(new Date(),1)` (Cycle.jsx:398–399). 31-го числа `addMonths` у місяць із 30 днями — перевірити, що утиліта не з'їжджає (класична пастка «31 січня +1 міс»). Залежить від реалізації `addMonths` в `utils/date`.
- [ ] 🟡 Unicode/ввід: вільного текстового вводу в розділі немає (дати — кліком, засіб — whitelist select), тож Unicode-ін'єкцій поверхні катма. `hygieneProduct` валідований whitelist-ом (§8).

## 11. Продуктивність і надійність (гонки, перезавантаження, недостатня історія)

- [ ] 🟠 **Гонки відмітки початок/кінець/прибрати.** Кнопки не блокуються під час `await …; await reload()` (Cycle.jsx:178–219). Швидкі кліки «Початок»→«Кінець» до завершення першого `reload` дають непередбачуваний порядок: `markCycleEnd` може виконатись, коли ще немає свіжого `openRecord`. Сервер частково рятує (дедуп старту, end шукає найпізніший), але UI показуватиме проміжні/застарілі стани.
- [ ] 🟠 **Поповер + одночасна дія.** Якщо відкрито `picker` на дні й паралельно прийшов `reload` (наприклад, після зміни засобу з reload — Cycle.jsx:205), `records` перерендеряться; `picker` (apiDate-рядок) лишиться валідним, але клітинка могла змінити стан під відкритим меню. Дрібне, але плутає.
- [ ] 🟠 **Кожен GET `/api/cycle` робить запис у БД** (створення settings + можливе додавання покупки через `EnsureHygieneSupplyAsync`, CycleService.cs:60). GET з побічними ефектами: не ідемпотентний, навантажує БД на кожне відкриття сторінки/реренд Planner (`cycleVersion`). Полінг/часті переходи = зайві INSERT.
- [ ] 🟠 **`EnsureHygieneSupplyAsync` викликається 5+ разів** (на GET і після кожної мутації) — щоразу додатковий `AnyAsync` по ShoppingItems + `ComputeForecast` + можливий `AddItemAsync`. На гарячому шляху (кожен markStart→reload→GET) це кілька зайвих запитів. Кешування/об'єднання відсутнє.
- [ ] 🟠 **Недостатня історія.** 0 записів: усе `—`, фази не рендеряться (`phases.length===0`, Cycle.jsx:411) — ок. 1 запис: прогноз є, але `cycleLengths` порожній → `avgCycleLength=28` (дефолт), `isRegular=null`, `lastCycleLength=null`. Перевірити, що жоден розрахунок не ділить на нуль: `avgPeriodLength` при `periodLengths.length===0` → `null` (Cycle.jsx:44), `avg` на сервері лише коли `starts.Count≥2` (ок).
- [ ] 🟡 **Перезавантаження/повернення на вкладку** завжди робить свіжий `getCycle` (useEffect, Cycle.jsx:148). Стан не персиститься локально, тож завжди консистентний із сервером — добре. `cancelled`-guard проти race на анмаунті є (Cycle.jsx:149,162).
- [ ] 🟡 Відсутність пагінації історії: `records` і `historyRows` рендеряться повністю. За багато років відміток таблиця/календарні `Set`-и ростуть лінійно — для диплому не критично, але `buildCalendarMarks` ітерує всі записи щоразу.
- [ ] 🟡 `useMemo` для stats/phases/marks залежить від `[records, forecast, stats]` (Cycle.jsx:172–174) — `stats` сам мемоізований, ок; але `marks`/`phases` перераховуються при кожній зміні `forecast` (приходить при кожному reload новим об'єктом) — незначні зайві перерахунки.
