# Adversarial review — Нотатки

Чек-лист критичної перевірки вкладки **«Нотатки»** планувальника «Всетута» (React/Vite + ASP.NET Core / EF Core / MySQL, JWT). Складено за фактичним кодом:

- `client/src/pages/Notes.jsx` — сторінка, вкладки, картки-нотатки.
- `client/src/components/notes/Board.jsx` — дошка для малювання (localStorage).
- `client/src/api/notes.js` — тонкі обгортки HTTP.
- `client/src/api/http.js` — спільний HTTP-шар (Bearer-токен).
- `server/Controllers/NotesController.cs` — CRUD-контролер.
- `server/Models/Note.cs` — сутність `Note`.
- `client/src/i18n/{uk,en}.json`, `client/src/i18n/index.jsx` — локалізація.
- `client/src/pages/Notes.css` — стилі.

Легенда пріоритетів: **[B]** блокер / **[H]** високий / **[M]** середній / **[L]** низький / **[I]** інфо-спостереження.

---

## 1. Фронтенд — сторінка, вкладки Нотатки/Дошка, логіка

- **[M] `handleAdd` без обробки помилок.** `const { id } = await addNote(...)` — якщо `addNote` кине (мережа/401/500), проміс відхиляється без `try/catch`. Нотатка не додається, користувач не бачить жодного повідомлення, в консолі — unhandled rejection. Порівняйте з `handleColor`/`handleRemove`, де є `.catch(() => {})`. Непослідовна обробка помилок.
- **[M] Деструктуризація `{ id }` впаде, якщо сервер поверне `null`.** `apiSend` повертає `null`, коли тіло відповіді порожнє. Контролер повертає `Ok(new { id })`, але за будь-якої зміни контракту (чи проксі, що зжирає тіло) `const { id } = null` кине `TypeError`, і знову ж таки — без фолбеку.
- **[H] Гонка подвійного додавання (див. §11).** `handleAdd` читає `notes.length` із замикання на момент кліку і лише потім `await`-ить мережевий запит. Швидкі повторні кліки (або повільна мережа) пройдуть перевірку `>= MAX_NOTES` зі «старим» значенням і створять більше нотаток, ніж дозволено.
- **[L] Стан вкладки не зберігається.** `tab` — локальний `useState('notes')`; перехід на іншу сторінку і назад скидає на «Нотатки». Для диплому прийнятно, але варто зафіксувати як свідоме рішення.
- **[L] Немає порожнього стану для нуля нотаток.** Якщо нотаток немає, показується лише кнопка «Додати нотатку» — окремого тексту-підказки («Нотаток ще немає») немає, на відміну від інших модулів. Не помилка, але неузгодженість UX.
- **[I] `getNotes().catch(() => setNotes([]))`** мовчки ковтає помилку завантаження: за збою бекенда користувач бачить порожній список, ніби нотаток немає (хоча вони є на сервері) — ризик, що користувач почне створювати дублі. Варто показувати стан помилки, а не «порожньо».
- **[I] Поле `position` на клієнті задається (`position: prev.length`), але нікуди не надсилається** — див. §10 (мертвий код).

## 2. Фронтенд — стилі, CSS, адаптивність, світла/темна тема, сітка карток, полотно

- **[M] Пастельні картки ігнорують темну тему.** `.note-card` має жорстко зашитий `color: #33312b`, а фон — один із 6 світлих пастельних HEX. У темній темі картка лишається світлою плямою з темним текстом. Коментар у CSS це визнає («пастельні картки лишаються світлими в обох темах»), тобто це свідомо, але контраст плейсхолдера `rgba(0,0,0,0.4)` і лічильника `rgba(0,0,0,0.45)` на світлому пастелі — на межі WCAG (див. §5).
- **[M] Сітка нотаток: `minmax(190px, 1fr)` + `min-height: 190px`.** На дуже вузьких екранах (< ~210px робочої області) картка впритул до країв; на широких — картки розтягуються до повної ширини колонки, виглядають непропорційно великими за короткого тексту. Прийнятно, але не ідеально.
- **[M] Полотно дошки має фіксований `max-width: 860px`, але внутрішній растр 1200×720.** Канвас масштабується по ширині (`width:100%; height:auto`), а координати перераховуються через `getBoundingClientRect` (добре). Проте на мобільному полотно стає маленьким (≈320px), лінія товщиною 3px у растрі 1200px — майже невидима; малювати пальцем по дрібному полотну незручно. Немає зуму/панорами.
- **[L] Активний колір картки визначається точним рядковим збігом `note.color === c`.** Якщо сервер поверне HEX в іншому регістрі/форматі (`#FFF3B0`, або взагалі довільний рядок — див. §6/§8), жоден свотч не підсвітиться як активний, хоча фон застосовано.
- **[L] `.note-colors` з 6 кружечків по 16px + лічильник + кошик у `.note-footer` з `gap:8px`** — на найвужчій картці футер може переноситись/тіснитись; `flex-wrap` не задано, тому елементи стискаються.
- **[I] Тема панелі інструментів дошки використовує змінні теми (`--color-surface` тощо)** — тулбар адаптивний, але сам канвас завжди білий (`#ffffff` і в CSS `.board-canvas-wrap`, і в JS `BG`). У темній темі біле полотно б'є по очах. Свідомо (JPEG без прозорості), але варто зафіксувати.

## 3. Фронтенд — валідація вводу (280 символів, 30 нотаток), стани

- **[H] Обидва ліміти (280 / 30) — суто клієнтські для UX; обмеження кількості взагалі не дублюється на сервері (див. §6, §10).** `MAX_NOTES = 30` перевіряється лише у `handleAdd` і для показу заглушки `note-add--full`. Контролер `Add` не рахує наявні нотатки — пряме звернення до API створює 31-шу і далі без обмежень.
- **[M] Ліміт 280 має подвійний клієнтський захист (`maxLength={280}` на `<textarea>` + `text.slice(0, MAX_LEN)` у `handleText`), але сервер лише мовчки обрізає (`Clamp`), не повертаючи 400.** Тобто надсилання >280 через API не є помилкою з точки зору API — текст тихо тинкається. Для інтеграцій/тестів це приховує проблему вводу.
- **[L] Лічильник `{note.text.length}/{MAX_LEN}` рахує код-юніти JS (UTF-16), а не графеми.** Емодзі/сурогатні пари рахуються як 2, а `maxLength`/`slice` також ріжуть по код-юнітах — можна «розрубати» емодзі навпіл (див. §10, Unicode).
- **[L] Немає індикації «збереження».** Текст іде на сервер лише на `blur`; користувач не бачить, збережено чи ні. За збою `saveNote` (`.catch(() => {})`) зміни мовчки губляться — у стані вони лишаються, але на сервері ні; після перезавантаження текст зникне без попередження.
- **[I] Немає стану «відправляється/відправлено» для кнопки додавання** — під час `await addNote` кнопка лишається активною (що й живить гонку з §1/§11).

## 4. Інтернаціоналізація (i18n) — ключі/інтерполяція limitReached

- **[L] `notes.limitReached` інтерполює `{max}` коректно**, але реалізація `t` робить `text.replace('{max}', val)` — **лише перше входження**. Для цього ключа одне `{max}`, тож ок; проте патерн крихкий для майбутніх ключів із повторюваним плейсхолдером.
- **[L] `t` не має фолбеку мови: `dict[key] ?? key`** — якщо ключ відсутній у вибраній мові, показується сам ключ (напр. `notes.limitReached`), а не англійський/дефолтний варіант. Для наявних ключів usk/en присутні обидва — перевірено (рядки 823–830 в обох файлах). Але нові ключі легко «світитимуть» сирим id.
- **[M] aria-label кольорів і розмірів не локалізовані й не людиночитні.** Кольори нотатки: `aria-label={c}` → `"#fff3b0"`; кольори дошки те саме; розміри пензля: `aria-label={`${s}px`}` → `"3px"`. Жоден не проходить через `t()`, і жоден не є осмисленою назвою (див. §5).
- **[I] Текст-заглушка плейсхолдера `notes.placeholder` = «Нотатка…»** локалізований коректно; delete-кнопка використовує `common.delete`, loading — `common.loading` — узгоджено зі спільними ключами.

## 5. Доступність (a11y): textarea, вибір кольору (aria=hex), полотно для малювання

- **[H] Полотно дошки повністю недоступне без миші/дотику.** `<canvas>` без `role`, без `aria-label`, без текстової альтернативи, без клавіатурної взаємодії. Малювання тільки через Pointer Events. Для незрячих/клавіатурних користувачів дошка — «чорна скринька». Хоча б `aria-label`/`role="img"` з описом і декларація, що інструмент графічний, бажані.
- **[H] Вибір кольору озвучується як HEX.** `aria-label={c}` для свотчів нотатки й дошки → скрінрідер читає «решітка f f f три b нуль». Треба осмислені назви («жовтий», «блакитний» …), бажано локалізовані через `t()`. Те саме для товщини пензля (`"3px"` замість «тонкий/середній/товстий»).
- **[M] Свотчі кольору — `<button>` без тексту й без видимого фокус-стилю поза `:hover`.** Активний стан позначається лише рамкою (`note-color--active`), що для дальтоніків/слабозорих недостатньо; немає `aria-pressed`/`aria-selected`, щоб озвучити, який колір обрано зараз.
- **[M] Кнопки інструментів дошки (гумка/очистити) — toggle без `aria-pressed`.** «Гумка» має візуальний активний клас, але семантично не повідомляє стан увімкнення.
- **[M] «Очистити» дошку і видалення нотатки — деструктивні дії без підтвердження і без `aria-live`-повідомлення про результат** (див. §9). Випадкове натискання = миттєва незворотна втрата.
- **[L] `<textarea>` без явного `<label>`/`aria-label`** — асоціюється лише плейсхолдером `notes.placeholder`, який зникає при вводі. Для скрінрідера поле безіменне.
- **[L] Контраст: лічильник `rgba(0,0,0,0.45)` і плейсхолдер `rgba(0,0,0,0.4)` на пастельному фоні** можуть не дотягувати до 4.5:1.

## 6. Бекенд — API, статус-коди, валідація тексту/кольору

- **[B] Відсутня валідація кількості нотаток у `Add`.** Контролер не перевіряє `Count()` наявних нотаток користувача перед вставкою → серверного ліміту 30 немає взагалі. Прямий `POST /api/notes` (в обхід UI) створює необмежену кількість. Обмеження 30 живе лише в `Notes.jsx`.
- **[B] Відсутня валідація формату кольору.** `Color = string.IsNullOrWhiteSpace(r.Color) ? "#fff3b0" : r.Color.Trim()` — приймається **будь-який непорожній рядок**: `"red; url(...)"`, `"javascript:"`, CSS-функції, рядок на мегабайти. Немає перевірки, що це HEX із палітри з 6 кольорів. Наслідки — §8.
- **[M] `Clamp` мовчки обрізає текст >280 замість `400 BadRequest`.** API не сигналізує про перевищення — тихе спотворення даних; погано для контрактних тестів і клієнтів-інтеграцій.
- **[M] Немає обмеження довжини кольору ні в коді, ні (ймовірно) в схемі БД.** `Note.Color` — звичайний `string` без `[MaxLength]`/`[StringLength]`; за замовчуванням EF Core для MySQL може створити `longtext`/`varchar(max-подібне)`. Можна зберегти велетенський рядок у `Color` і роздути БД/відповідь `GET`.
- **[M] `Add` не валідує модель.** Немає `[Required]`/перевірки на `null` для `NoteRequest.Text` — `Clamp(null)` рятує від NRE (`text ?? ""`), але це покладання на дефолт, а не явна валідація. `record NoteRequest(string Text, string Color)` при JSON `{}` дасть обидва `null`.
- **[L] Усі відповіді — `Ok()`/`NotFound()`; немає `201 Created` з `Location` для `POST`.** Для диплому прийнятно, але не RESTful.
- **[I] CRUD прямо на `DbContext` без репозиторіїв** — відповідає заявленому coding-guide; не зауваження, а контекст.

## 7. Авторизація та власність (IDOR над чужими нотатками)

- **[I/Позитив] IDOR коректно закритий.** `Update` і `Delete` фільтрують `n.Id == id && n.UserId == CurrentUserId` і повертають `NotFound()` для чужого `id`. `Get` фільтрує по `UserId`. Тобто читання/зміна/видалення чужої нотатки неможливі — підтверджено в коді. **Перевірити тестом**: `PUT/DELETE /api/notes/{чужий_id}` під іншим токеном має віддати 404 (а не 403/200).
- **[L] `NotFound()` для чужого id технічно розкриває лише «немає такої вашої нотатки»** — ок, не витікає факт існування чужої (бо умова комбінована). Це правильний вибір; просто зафіксувати.
- **[M] `CurrentUserId` робить `int.Parse(User.FindFirst(Sub)!.Value)` з `!`.** Якщо валідний JWT без claim `sub` (чи з нечисловим `sub`) — `NullReferenceException`/`FormatException` → 500 замість 401. Залежить від того, як налаштована видача токена; варто перевірити, що `sub` гарантовано числовий.
- **[L] `[Authorize]` на рівні контролера** — добре; переконатися, що немає `[AllowAnonymous]` деінде і що схема автентифікації застосована глобально.

## 8. Безпека (XSS у тексті нотатки; валідація кольору)

- **[I/Позитив] XSS через текст нотатки не відтворюється.** Текст рендериться як `value` у `<textarea>` і в лічильнику `{note.text.length}` (число). Ніде немає `dangerouslySetInnerHTML`/`innerHTML`. React екранує текстові вузли. Тож `<script>`/HTML у тексті зберігається дослівно й показується як текст — **безпечно**. Зафіксувати явно: сервер зберігає сирий текст, безпека тримається на тому, що клієнт його не інтерпретує як HTML. Будь-який майбутній рендер нотатки через `innerHTML`/markdown негайно відкриє збережений XSS.
- **[H] Колір = вектор CSS-ін'єкції / завантаження зовнішніх ресурсів.** Клієнт застосовує `style={{ background: note.color }}` напряму з серверного значення. React через інлайн-об'єкт не дасть «вирватися» в інший селектор чи виконати JS, **але** приймає валідні CSS-значення властивості `background`, зокрема `url(https://evil.example/beacon.gif)`, `image-set(...)`, градієнти. Оскільки сервер приймає довільний рядок (§6), зловмисник може зберегти `background: url(...)` і при кожному відкритті нотаток браузер жертви **витягуватиме зовнішній ресурс** (трекінг-маячок, деанонімізація IP, CSP-обхід якщо політики немає). Це не script-XSS, але реальна проблема приватності/безпеки. **Фікс:** валідувати колір проти whitelist із 6 HEX і на клієнті, і на сервері; відхиляти інше (400).
- **[M] Відсутність серверної перевірки палітри** означає також, що навіть легітимний клієнт довіряє серверу у зворотному напрямку: якщо в БД потрапив «брудний» колір, `GET` віддасть його, і він застосується. Валідація потрібна на вході (`Add`/`Update`).
- **[L] Дошка: `localStorage.getItem` → `new Image(); img.src = saved`.** Значення контролює лише власний браузер (не інший користувач), тож XSS-ризику немає, але див. §10 про пошкоджений dataURL.
- **[I] CSP не перевіряв — якщо її немає, п.§8-H (external `url()`) повністю експлуатований.** Рекомендація: заголовок `Content-Security-Policy` з обмеженням `img-src`.

## 9. Бізнес-логіка та інваріанти

- **[H] Ліміт 30 нотаток — не інваріант системи, а лише UI-гейт.** Інваріант «≤30 нотаток на користувача» не гарантується (§6-B). Істинний інваріант тримається лише доти, доки користувач ходить через UI.
- **[M] Текст зберігається на `blur`, колір — одразу.** Два різні моменти запису породжують вікна втрати/гонок (див. §11). Зокрема: користувач друкує, не знявши фокус із `<textarea>`, йде зі сторінки/закриває вкладку — `blur` може не спрацювати (особливо при навігації SPA без розмонтування фокуса) → останні символи не збережуться.
- **[M] Дошка зберігається ЛИШЕ в `localStorage` (вимога).** Наслідки як інваріант: (1) **втрата** при очищенні кешу/браузера/режимі інкогніто; (2) **немає крос-девайсу** — на іншому пристрої/браузері дошка порожня; (3) **не прив'язана до акаунта** — ключ `notesBoard` не містить `userId`, тож на спільному комп'ютері різні користувачі «Всетути» бачать **один і той самий малюнок** (витік приватних даних між акаунтами); (4) не очищається при «Видалити всі дані»/виході з акаунта (див. Налаштування) — залишок після розлогінення.
- **[M] Квота `localStorage` перевищена → тихо не збережеться.** `persist()` ловить виняток і ігнорує; користувач продовжує малювати, вважає, що все збережено, а між сесіями малюнок зникне без жодного попередження.
- **[L] Експорт JPEG: ім'я файлу `vsetut-board-${new Date().toISOString().slice(0,10)}.jpg`.** `toISOString` дає **UTC-дату**; для користувача в UTC+2..+10 близько опівночі дата у назві може «відставати» на день від локальної. Також за кілька експортів того ж дня файли матимуть ідентичні імена (браузер додасть `(1)` сам).
- **[L] Збереження в localStorage — PNG (`toDataURL('image/png')`), а експорт — JPEG.** Тобто persist тримає більший PNG-рядок (ближче до квоти), хоча для відображення/експорту якість JPEG достатня. Невідповідність форматів роздуває сховище без потреби (пришвидшує досягнення квоти з §9/§11).
- **[I] `clear()` стирає і полотно, і `localStorage`, але не питає підтвердження** (див. §5/§9 — деструктив без confirm).

## 10. Дані, межі

- **[H] 31-ша нотатка через прямий API.** `POST /api/notes` × N без перевірки кількості → список необмежено росте; `GET` поверне їх усі, UI покаже всі (сітка просто подовжиться), а кнопка «Додати» сховається лише коли `notes.length >= 30`, хоча нотаток уже, скажімо, 50. Підтверджено відсутністю ліміту в `Add`.
- **[M] Довгий текст / межа 280.** Через UI обрізається двічі (клієнт), через API — `Clamp` до 280 код-юнітів. Але обрізка по код-юнітах може лишити «висячий» half-сурогат, якщо 280-й символ — половина емодзі → зіпсований символ у БД/відображенні.
- **[M] Unicode / емодзі.** `text.length`, `maxLength`, `slice`, `Clamp` — усі рахують UTF-16 код-юніти, не графеми. Емодзі (2 юніти) і складені графеми (прапори, ZWJ-послідовності, сім'ї) рахуються несправедливо, лічильник «280» не відповідає сприйняттю, і межа ріже всередині графеми.
- **[M] Пошкоджений `dataURL` у `localStorage` дошки.** `new Image()` має лише `img.onload`; **немає `img.onerror`**. Якщо збережене значення пошкоджене/обрізане (напр., квота обрубала запис), зображення просто не завантажиться — полотно лишиться білим, а битий рядок **залишиться в сховищі назавжди** (нічого не чистить). Тихий збій.
- **[B/мертвий код] Поле `position` не задіяне наскрізно.** Клієнт створює `position: prev.length` у стані, але **не надсилає** його (ні `addNote`, ні `updateNote` не передають `position`; `NoteRequest` його не має). Сервер обчислює `Position = maxPos + 1` сам і сортує за ним у `GET`. Тобто клієнтський `position` — суто декоративний/мертвий; жодного перетягування чи зміни порядку в UI немає (підтверджено описом «немає перетягування»). Поле `Position` у моделі/DTO існує, передається в `NoteDto`, але клієнт його ігнорує (у `setNotes` після `GET` використовується як є, бо вже відсортовано). Висновок: напівреалізована фіча впорядкування — або прибрати, або довести до кінця.
- **[L] `Color` без обмеження довжини** (див. §6) — межа даних не визначена; теоретично мегабайтний колір.
- **[L] Порожня нотатка — валідний стан.** `addNote({ text: '', color })` створює порожню нотатку на сервері одразу при кліку «Додати». Якщо користувач передумав і пішов, лишається порожня нотатка, що «з'їдає» слот із 30.

## 11. Продуктивність і надійність

- **[H] Гонка blur-збереження vs зміни кольору.** Зміна кольору шле `PUT {text: note.text, color}` **негайно**, текст — на `blur`. Якщо користувач: друкує → клікає свотч кольору (не знявши фокус) — `handleColor` бере `note.text` з поточного рендера (ок, актуальний), але якщо після цього `blur` відправить ще один `PUT` із тим самим текстом — два конкурентні запити; порядок виконання на сервері не гарантований. За різної латентності пізніший (зі старішими даними) може перезаписати новіший. Both-full-payload пом'якшує, але не усуває інверсію порядку.
- **[H] Подвійне/швидке додавання.** Кнопка «Додати» активна під час `await addNote`; `notes.length` читається зі stale-замикання. N швидких кліків = N POST-ів, перевірка ліміту не встигає оновитись → можна перевищити 30 (на сервері ліміту теж немає, §6) і створити зайві нотатки.
- **[M] Гонка «редагування + видалення».** Користувач друкує в нотатці й одразу тисне кошик: `handleRemove` шле `DELETE`, а `blur` textarea — `PUT`. Якщо `PUT` дійде після `DELETE`, отримає `NotFound` (тихо проковтнеться `.catch`), що безпечно; але якщо `PUT` дійде **раніше** завершення видалення — зайвий запис/оновлення вже видаленої. Залежить від латентності.
- **[M] Квота `localStorage` дошки.** PNG-dataURL 1200×720 детального малюнка легко сягає сотень КБ–кількох МБ; `localStorage` ~5 МБ на origin і **ділиться з рештою застосунку** (`authToken`, `food:weeklyMenu`, тема/палітра тощо). Велика дошка може або сама не зберегтись (тихо, §9), або **витіснити/зламати запис інших ключів**, якщо десь робиться запис без `try/catch`. Варто перевірити, що інші модулі теж захищені від `QuotaExceededError`.
- **[M] `persist()` на кожному `end` (pointer up / leave).** Кожен штрих серіалізує все полотно в PNG-dataURL (base64 ~1.3× від бінарного) і пише в синхронний `localStorage` — це блокуючий main-thread запис розміром у мегабайти при кожному відпусканні пензля. На слабких пристроях — помітні фрізи під час малювання.
- **[L] `pointer-capture` + `onPointerLeave={end}`.** `end` викликається і на `leave`, і на `up`; з `setPointerCapture` leave може не спрацьовувати як очікується — у певних браузерах лінія «тягнеться» за межі канви. Треба перевірити крайові випадки (швидкий вихід за межі).
- **[L] Немає скасування незавершених запитів при розмонтуванні.** Якщо піти зі сторінки під час `await addNote`/`saveNote`, `setNotes` не викликається (ок, бо handleAdd більше не оновлює), але unhandled-помилки й «запізнілі» записи можливі. `getNotes` у `useEffect` без abort — класичний warning «set state on unmounted».

## Зведення найкритичніших пунктів

1. **[B] Сервер не обмежує кількість нотаток** — ліміт 30 обходиться прямим API (§6, §9, §10).
2. **[B/H] Сервер приймає довільний рядок як `color`** → CSS-ін'єкція `url(...)` / завантаження зовнішніх ресурсів при рендері `style={{background}}` (§6, §8). Потрібен whitelist палітри на клієнті і сервері.
3. **[B] `position` — напівреалізований/мертвий код**: задається на клієнті, не надсилається, сортування рахує сервер; впорядкування в UI відсутнє (§10).
4. **[H] Дошка лише в localStorage і не прив'язана до userId** → втрата даних, відсутність крос-девайсу, витік малюнка між акаунтами на спільному браузері, тихий збій при перевищенні квоти та при пошкодженому dataURL (немає `onerror`) (§9, §10, §11).
5. **[H] Гонки**: подвійне додавання та blur-збереження vs негайна зміна кольору (§11).
6. **[H] A11y**: канвас недоступний з клавіатури/скрінрідера; `aria-label` кольорів = сирий HEX (§5).
7. **[Позитив] IDOR закритий коректно** (фільтр `UserId` + `NotFound`) і **XSS у тексті не відтворюється** (textarea `value`, без `innerHTML`) — обидва підтверджені в коді, рекомендовано зафіксувати регрес-тестами (§7, §8).
