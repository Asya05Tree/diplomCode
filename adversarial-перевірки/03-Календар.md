# Adversarial review — Календар (Планувальник)

> Обсяг: `client/src/pages/Planner.jsx`, `client/src/components/planner/*`, `client/src/utils/{date,recurrence,debts}.js`, `client/src/i18n/*`, серверні `TasksController`, `RecurrenceRulesController`, `Services/TaskService`, сутності `TaskItem`, `RecurrenceRule`, `RecurrenceException`, `ManualRecurrenceDate`.
>
> Нижче — марковані пункти-перевірки саме для цієї вкладки. Пункти з позначкою **[знахідка]** — це вже виявлені реальні дефекти/ризики в коді; решта — контрольні перевірки для захисту диплому. Позначка **[verify]** означає «перевірити вручну/емпірично».

---

## 1. Фронтенд — сторінка, режими перегляду, логіка компонентів

- [ ] `Planner.jsx` тримає стани `activeTab` (`dayPeriod|recurring|unassigned|debts`) і окремо `mode` (`day|period`). Перевірити, що `ModeSwitch` не дає потрапити в неможливу комбінацію (напр. `activeTab='recurring'` + `mode='period'` одночасно малює ліву сітку з `recurringMarkings`, але права область — `RecurringView`; `markings = activeTab==='recurring' ? recurringMarkings : busyMarkings` — ок).
- [ ] Клік по дню в лівій сітці (`handleSelectDate`) завжди перемикає на `dayPeriod`+`day`, **крім** випадку активного ручного введення дат (`activeTab==='recurring' && manualDateHandler`). Перевірити: якщо обрано Manual-правило і користувач хотів просто «відкрити день» — він натомість додає/знімає ручну дату (неочевидна зміна семантики кліку; документувати в UI).
- [ ] **[знахідка]** `setManualDateHandler(() => async (date) => …)` — handler зберігається у стані через функцію-обгортку. Перевірити, що замикання бачить **актуальний** `selected.manualDates` (ефект перестворює handler при зміні `selected`, але не при зміні лише `version`/`manualDates` того самого правила — після додавання дати `bump()` інкрементить `version`, `getRecurrenceRules` повертає новий `selected` об'єкт → ефект перезапускається; підтвердити, що `includes(key)` не працює зі застарілим списком між `addManualDate` і перезавантаженням).
- [ ] `tasksVersion` бампається після будь-якої мутації й тягне **4 паралельні ефекти** (busy+freeDays, workDays, unassignedCount, debts). Перевірити, що немає зайвого потрійного перезавантаження і «блимання» сітки.
- [ ] **[знахідка]** `workDays`-ефект робить **повторний** `getPeriodTasks(token, from, to)` для того самого діапазону, що й busy-ефект (п.1 вище) — дубльований мережевий виклик на кожен `tasksVersion`/зміну місяця. Злити в один запит.
- [ ] `DayView`/`PeriodView`/`UnassignedView`: `reload()` викликається після кожної дії; перевірити відсутність race, коли `reload` і `onTasksChanged→setTasksVersion` паралельно тягнуть один ендпоінт.
- [ ] `itemKey = \`${task.id}-${task.startDateTime}\``. Для віртуальних інстансів усі інстанси одного правила мають однаковий `task.id`; унікальність ключа тримається лише завдяки різному `startDateTime`. Перевірити, що в межах одного дня правило дає рівно одне входження (інакше дублікат React-ключа). Дві події з **однаковим** `startDateTime` з різних правил → колізія ключа.
- [ ] `OverlapGroup key={group[0].startDateTime}` — кластер задач без часу дав би `key=null`. У Дні такого не буває (день повертає лише задачі з часом), але підтвердити інваріант.
- [ ] Віртуальний інстанс не можна позначити «Готово/Пропущено» — лише «Перенести/Видалити». Перевірити, що це свідоме обмеження (у повторюваних немає per-occurrence статусу виконання) і що воно зрозуміле користувачу.
- [ ] `RecurringView.summarizeRule` для `WeekCycle` з `cycleWeeks===1` бере `pattern[0]` — якщо патерн зберігся як `"1:..."` (не нульовий тиждень), підсумок покаже порожньо. Перевірити кодування.
- [ ] `now = new Date()` у `DayView`/`PeriodView` — знімок на рендер, «зараз»-підсвітка не тікає наживо. Задокументовано як намір; перевірити, що після опівночі відкрита сторінка не показує вчорашній день як «сьогодні» (MonthGrid бере `new Date()` щорендеру — ок; DayView `isToday` теж).

## 3. Фронтенд — валідація вводу, стани (завантаження/помилка/порожньо)

- [ ] **[знахідка]** Усі види (`DayView/PeriodView/UnassignedView/RecurringView`) на помилці запиту роблять `.catch(() => setTasks([]))` → **помилка мережі невідрізнима від «порожньо»**: показується «На цей день задач немає» замість повідомлення про збій. Немає ні стану завантаження (спінера), ні стану помилки. Додати явні loading/error стани.
- [ ] `Planner` busy/workDays/debts/unassignedCount — усі `.catch` тихо скидають у порожнє; сітка «очищається» при будь-якому збої без індикації.
- [ ] **[знахідка]** `TaskForm`: поле звичайної назви (`title`) **не має `maxLength`** і не прогнано через `limitText` (на відміну від `mediaTitle`, де `maxLength={MAX_LEN.title}`). Наддовга назва піде на сервер без обмеження (див. §8 — сервер теж не обмежує довжину).
- [ ] **[знахідка]** `RecurringView` поле тривалості: `type=number min=1 max=1440` і шле `Number(editDuration)` напряму — дозволяє ввести до **1440 хв**, тоді як `DurationFields` (створення) обмежує 0–8 год, а опис каже «макс 8 год». Сервер усе одно клампить до 480 (`ClampDuration`), тож введені 9–24 год мовчки обріжуться — неузгоджений UX і відсутня валідація на клієнті тут.
- [ ] `DurationFields`: під час набору (`onChange`) значення не клампиться, лише `onBlur`. Перевірити, що при сабміті без blur `combineDuration` все одно клампить (так — клампить). Від'ємні/нечислові → `Number||0`.
- [ ] Валідація «дата в минулому»: `TaskForm`/`EditTaskForm`/`MoveTaskForm` ставлять `min={todayApiDate()}` на `<input type=date>` і `TaskForm` додатково перевіряє `date < todayApiDate()`. Перевірити, що `min` не блокує сьогодні і що ручне введення тексту в date-поле (де браузер дозволяє) ловиться JS-перевіркою. **`EditTaskForm`/`MoveTaskForm` JS-перевірки минулого НЕ мають** — покладаються лише на `min` атрибут (легко обійти).
- [ ] Порожні стани перевірити для кожного режиму: День («На цей день задач немає»), Період («На цей період…»), Нерозподілені, Повторювані («Немає правил»), Борги. Переконатися, що вони не з'являються під час першого завантаження (миготіння порожнього до приходу даних).
- [ ] `RecurrenceFields`: `intervalDays` клампиться 1..365 в `onChange`; `cycleAnchorDate`/`endDate` коригуються при зміні `startDate` (`handleStartDateChange`). Перевірити, що зміна типу правила не лишає несумісних полів (вони фільтруються в `recurrenceValueToPayload`).
- [ ] Перевірити, що `validateRecurrenceValue` ловить: порожній тиждень (WeekCycle без днів), `endDate<startDate`, `endDate>maxEndDate`, порожні MonthDays/Specific, `intervalDays<1`.

## 4. Інтернаціоналізація (i18n) та формати дати/часу (12/24, перший день тижня)

- [ ] **[знахідка]** `weekStart`, `dateFormat`, `timeFormat`, `language` зберігаються лише в **localStorage** (`utils/settings`, `i18n/index.jsx`) — не прив'язані до акаунта на сервері. Зміна пристрою/браузера скидає на дефолти; між двома вкладками браузера стан у пам'яті не синхронізується до перезавантаження.
- [ ] **[знахідка]** Непослідовне застосування `dateFormat`: `DebtsView`/`RecurringView` використовують `formatDate` (поважає налаштування), але `DayView` заголовок і `PeriodView` заголовки груп використовують `toLocaleDateString(locale, …)` (ігнорує обраний `dateFormat`), а `UnassignedView` показує дедлайн як **сирий ISO** `task.deadline.slice(0,10)` (ні локаль, ні формат). Звести до `formatDate` всюди.
- [ ] Формат часу 12/24: `TaskItem`→`formatTimeRange`, `OverlapGroup`→`formatTime`, `ReminderBanner`→`formatTime`, `summarizeRule`→`formatClock` — усі беруть `timeFormat` з контексту. Перевірити, що **форми вводу** (`<input type=time>`) свідомо лишаються 24-годинними (нативний контрол) і це не плутає користувача з 12-год показом.
- [ ] Перший день тижня: `getMonthGridCells(y,m,weekStart)` і `orderedWeekDays(weekStart)` — перевірити, що заголовки днів (`weekdays`) і зсув сітки **узгоджені** між собою й з сервером (сервер взагалі не знає про weekStart — лише показ). Перевірити всі 7 значень weekStart (Пн…Нд), зокрема неділю (7).
- [ ] `isoDayOfWeek`: `getDay()===0 → 7`. Перевірити, що клієнт і сервер (`IsoDayOfWeek`) однаково кодують неділю як 7 (патерни `WeekDaysPattern` спільні!). Розбіжність зсунула б повторення на день.
- [ ] `MonthGrid` стрілки місяця мають **хардкод українські** `data-tooltip="Попередній/Наступний місяць"` — не перекладаються при `language='en'`.
- [ ] Місяць у `MonthGrid` через `toLocaleDateString(month:'long')` — для `en-US` дасть англійську назву, але решта UI може лишитись укр. якщо словник не перемкнено. Перевірити цілісність перемикання мови.
- [ ] `t(key, params)` робить лише **один** `replace('{name}')` на параметр — якщо плейсхолдер трапляється двічі в рядку, замінить лише перший. Перевірити ключі з повторюваними плейсхолдерами (`overlapCount`, `reminder.title`, `manualDatesCount`).

## 6. Бекенд — API, статус-коди, валідація, moduleCode allowlist

- [ ] `TasksController`: `GET period`/`free-days` повертають `400 invalid_range` при `from>to` — добре. Перевірити, що `DateOnly` біндинг відхиляє сміття (`from=abc`) з 400, а не 500.
- [ ] `Create`/`Update` відхиляють порожній `Title` (`400 missing_title`). Перевірити, що пробільний заголовок (`"   "`) теж ловиться (`IsNullOrWhiteSpace` — так).
- [ ] `Resolve` валідує `Action ∈ {Done,Skipped,Postpone}` (`400 invalid_action`). Перевірити, що `Unknown`/`Planned` ззовні встановити не можна (не можна — добре).
- [ ] **[знахідка]** `moduleCode` allowlist (`AllowedModules`) застосовується **лише** в `TasksController.Create`. У `RecurrenceRulesController.Create` передається `request.ModuleCode ?? "tasks"` **без перевірки allowlist** → у шаблон-задачу правила можна записати довільний `ModuleCode` (будь-який рядок). Додати ту саму перевірку для правил.
- [ ] `RecurrenceRulesController.IsValidRule`: перевіряє тип ∈ ValidTypes, `endDate` обов'язковий і в межах `[startDate, startDate+1рік]`, параметри кожного типу. Перевірити, що **вміст** `WeekDaysPattern`/`MonthDays` НЕ валідується (лише «не порожньо») — див. §9 про 500 при розборі.
- [ ] `AddException` валідує `ExceptionType ∈ {Cancelled,Moved}` і вимагає `NewDateTime` для `Moved`. Перевірити, що `Date` поза діапазоном правила приймається без помилки (приймається — безпечно, але смітить).
- [ ] Статус-коди власності: `Update/Delete/Resolve` неіснуючої/чужої задачі → `404 NotFound` (не 403). Прийнятно, але задокументувати (не розкриває існування).
- [ ] Відсутній ендпоінт масового створення/пагінації — перевірити, що великі вибірки не повертаються без обмежень (період — див. §11/DoS).
- [ ] `GET unassigned/count`, `reminder`, `day`, `period` — усі `[Authorize]`; перевірити, що без токена → 401 (а не 500 на `User.FindFirst(Sub)!`).

## 7. Авторизація та власність (IDOR над чужими задачами/правилами/винятками)

- [ ] `CurrentUserId => int.Parse(User.FindFirst(Sub)!.Value)` — перевірити, що `sub` завжди присутній; інакше `!`/`int.Parse` кине → 500 замість 401. **[verify]** токен без `sub`.
- [ ] Задачі: `Update/Delete/Resolve` фільтрують `t.UserId==userId`. **[знахідка/добре]** IDOR над чужою задачею неможливий — повертає 404. Підтвердити тестом із двома акаунтами.
- [ ] **[знахідка/добре]** Виняток, що посилається на **чуже правило**: `AddException`/`DeleteException`/`AddManualDate`/`DeleteManualDate`/`Preview`/`Update/DeleteRecurrenceRule` усі спершу перевіряють `RecurrenceRules.Any(r.Id==ruleId && r.UserId==userId)` → для чужого правила `NotFound`. Підтвердити, що `DeleteException` також звіряє `e.RecurrenceRuleId==ruleId` (звіряє).
- [ ] **[знахідка]** `ResolveTaskAsync` НЕ фільтрує `RecurrenceRuleId==null` (на відміну від `Update/Delete`). Власник може викликати `resolve` на **шаблон-задачі правила** за її `Id` → для `Skipped/Postpone` обнулить `StartDateTime` шаблона й поставить `Unassigned`. Не крос-акаунтна діра, але порушення інваріанта шаблона (генерація інстансів бере час з правила, тож видимо не ламається — але шаблон «протікає» в Нерозподілені? Ні — Unassigned-вибірка фільтрує `RecurrenceRuleId==null`, тож не з'явиться; все одно — брудний стан). Додати фільтр `RecurrenceRuleId==null` у `ResolveTaskAsync`.
- [ ] Перенесення/скасування **віртуального інстансу** з клієнта (`handleMove`/`handleCancelOccurrence`) створює виняток через `addException(token, task.recurrenceRuleId, …)`. Оскільки сервер перевіряє власність правила — створити виняток для чужого правила не вийде. Підтвердити, що `task.recurrenceRuleId` з відповіді завжди належить користувачу (так — вибірка правил `WHERE UserId`).

## 9. Логіка повторення та інваріанти

- [ ] **[знахідка — HIGH]** `PreviewOccurrences` і `GetEffectiveOccurrences` будують `rule.Exceptions.ToDictionary(e => e.Date, e => e)`. **Два винятки з однаковою `Date` → `ArgumentException` (duplicate key) → 500** на КОЖНОМУ запиті `day`/`period`/`preview`, доки дублікат існує. Дублікат легко створити: форма «Додати виняток» у `RecurringView` не забороняє другий виняток на ту саму дату (напр. `Cancelled` + `Moved`, або два `Moved`); жодної унікальності ні в UI, ні в `AddExceptionAsync`, ні в БД. Фактично self-DoS, що «вбиває» календар користувача. Потрібен unique-constraint/upsert на (RuleId, Date).
- [ ] **[знахідка — DoS]** Вміст патернів не валідується при створенні правила, а розбирається при розгортанні: `ParseWeekDaysPattern` робить `kv[1].Split(',').Select(int.Parse)`, `GenerateMonthDaysDates` — `MonthDays.Split(',').Select(int.Parse)`. Нечислові токени (`WeekDaysPattern="0:x"`, `MonthDays="abc"`) → `FormatException` → **500** при будь-якому читанні календаря. Валідувати формат на вході.
- [ ] Межа «рік/3 міс»: `MAX_RECURRENCE_YEARS=1` продубльовано на клієнті (`utils/recurrence.js`) і сервері (`RecurrenceRulesController`). Сервер **ензфорсить** `endDate ∈ [startDate, startDate+1рік]` і обов'язковість `endDate`. Дефолт 3 міс — лише клієнт. **[знахідка/добре]** межа рік є і на сервері. Перевірити, що `endDate=null` → 400 (так).
- [ ] Розгортання не «вибухає»: `GenerateBaseDates` клампить `rangeStart=max(StartDate,from)`, `rangeEnd=min(EndDate,to)` → цикл по днях обмежений **власним** діапазоном правила (≤1 рік). Підтвердити, що жоден генератор не ітерує `from..to` до клампа (усі — після).
- [ ] **[знахідка — DoS, див. §10/11]** Проте `preview` і `period` отримують `from/to` **довільними** з клієнта (перевірка лише `from>to`). Для `preview` цикл обмежений правилом; але `GetFreeDaysAsync` і сама `GetTasksForRangeAsync` ітерують `from..to` без клампа діапазону (free-days — явний `for d=from..to`). Запит `period?from=1900-01-01&to=2100-01-01` → ~73 000 ітерацій × правила. Обмежити розмір діапазону на сервері.
- [ ] Винятки `Cancelled`/`Moved`: `GetEffectiveOccurrences` пропускає базову дату з будь-яким винятком, потім додає `Moved` за `NewDateTime`. Перевірити подвійний облік: якщо `NewDateTime` потрапляє на **іншу** базову дату того ж правила — буде і «moved-in», і базова (якщо та інша дата не має власного винятку) → дві події того дня (дубль ключа React, бо однаковий `id`, але різний час — ключ виживе; візуально дубль). Перевірити сценарій.
- [ ] **[знахідка]** `Moved.NewDateTime` на сервері не обмежений (у минуле / за межі `EndDate` / за межу року). UI (`RecurringView`) ставить `min=todayApiDate()` на нову дату, але API приймає будь-що. Можна «перенести» входження в минуле або за горизонт правила.
- [ ] Повторний рух віртуального інстансу: `handleMove` бере `occurrenceDate = toApiDate(нового startDateTime)`. Після першого перенесення інстанс показується на новій даті; другий рух створить виняток із ключем **нової** дати (не оригінальної) → лишиться старий `Moved` на оригінальну дату + новий. Перевірити, що це не породжує дубль-дату (§9 HIGH) і логічно коректний ланцюг.
- [ ] `GetWeekIndex`: `anchor = cycleWeeks>1 ? CycleAnchorDate : StartDate`; тиждень рахується від понеділка тижня-якоря; модуль нормалізований для від'ємних. Перевірити стики на межі тижня при `weekStart≠Пн` (кодування днів лишається ISO незалежно від показу — підтвердити, що зсув показу не протікає в генерацію).

## 10. Дата/час/таймзони, межі діапазону періоду, дедлайни (T23:59)

- [ ] **[знахідка — HIGH, таймзони]** Клієнт збирає ISO як **локальний wall-clock** без зсуву: `toApiDateTime` → `"YYYY-MM-DDTHH:MM:00"`, `fromApiDate`/`fromApiDateTime` парсять вручну саме щоб уникнути UTC-зсуву JS. Сервер трактує `DateTime` теж як «голий» wall-clock (коментар у `TaskService`). Але сервер для «сьогодні» бере `DateTime.Now.Date` (**локальний час СЕРВЕРА**), а `TaskItem.CreatedAt = DateTime.UtcNow` (**UTC**). Якщо часовий пояс сервера ≠ поясу користувача:
  - `SweepStaleTasksAsync` (`StartDateTime.Value.Date < DateTime.Now.Date`) і `GetReminderAsync` (`== yesterday`) рахують «день» за поясом сервера → задача користувача може передчасно/із запізненням стати `Unknown` або не потрапити в нагадування.
  - змішування `DateTime.Now` (sweep/today) і `DateTime.UtcNow` (`CreatedAt`) — внутрішня неузгодженість.
  Задокументувати припущення «сервер і користувач в одному поясі» або зберігати пояс користувача.
- [ ] **[знахідка]** Межа періоду «≤ місяць» ензфорситься **лише на клієнті** (`clampToWindow` в `PeriodView`, `to ∈ [from-1міс, from+1міс]`). Сервер `GET period` перевіряє тільки `from>to`. Прямий запит з довільним діапазоном не обмежений (див. §9 DoS). Додати серверний ліміт розміру діапазону.
- [ ] Дедлайн `"${deadline}T23:59:00"` формується як локальний рядок; за розбіжності поясів «кінець дня» може з'їхати на сусідній день на сервері. Також `23:59:00` (не `23:59:59`) — вікно 59 с наприкінці дня формально «після дедлайну».
- [ ] **[знахідка]** Дедлайн у минулому: ні `TaskForm`/`EditTaskForm` (JS), ні сервер не забороняють `Deadline < today` поза `min`-атрибутом. Через API можна створити задачу з простроченим дедлайном. Вирішити, чи це дозволено (Нерозподілені підсвітять як `--urgent`).
- [ ] Дата старту задачі в минулому: `CreateTaskAsync` не відхиляє `StartDateTime` у минулому (клієнт перевіряє, API — ні). Така задача одразу `Planned`, при наступному sweep → `Unknown`. Перевірити намір.
- [ ] `periodRange` початковий — `[сьогодні, +6 днів]`; перевірити, що зміна `from` коригує `to` (clampToWindow) і навпаки без можливості `to<from` (clamp min=from-1міс дозволяє `to<from` → `reload` дає порожньо; перевірити UX).
- [ ] `fromApiDateTime` з відсутнім time-частиною → `00:00:00`; `fromApiDate(str)` із бекенд-DateOnly. Перевірити, що `DateOnly`/`TimeOnly` серіалізуються у форматі, який клієнт очікує (`timeOfDay.slice(0,5)` припускає `"HH:mm:ss"`).
- [ ] `todayApiDate()` навмисно не кешується — перевірити, що відкрита через північ сторінка не фіксує вчорашнє «сьогодні» у `min`-атрибутах форм (вони обчислюються на рендер — ок).

## 11. Продуктивність і надійність (багато правил/входжень, гонки, sweep, нагадування)

- [ ] **[знахідка — гонка нагадувань]** `SweepStaleTasksAsync` викликається на початку `day`/`period`/`unassigned`/`count`, і він переводить **усі** вчорашні `Planned` у `Unknown`. `GetReminderAsync` шукає `Planned` саме за **вчора**. У `DayView` два окремі `useEffect` паралельно смикають `getDayTasks` (→ sweep) і `getReminder`. Якщо sweep із day-запиту встигне зберегтися першим, `reminder` поверне **порожньо** → банер нагадувань не з'явиться недетерміновано. Коментар у коді визнає потрібний порядок, але код його не гарантує (паралельні HTTP). Зробити sweep і reminder узгодженими (напр. reminder сам фіксує «показане» до sweep, або sweep виключає вчора доки reminder не оброблено).
- [ ] **[знахідка]** «Нічний sweep» фактично **lazy/on-read**, не нічний: немає `BackgroundService` для задач (є лише `InactiveAccountCleanupService`). Якщо користувач не відкриває календар, статуси не оновлюються; «Важливі борги»/лічильники застарівають до наступного читання. Опис «nightly sweep» не відповідає реалізації.
- [ ] **[знахідка]** `SweepStaleTasksAsync` виконує `SELECT`+можливий `SaveChanges` на **кожному** `day`/`period`/`unassigned`/`count`-запиті. На головному екрані один `tasksVersion`-бамп породжує 4 запити (busy, workDays, count, debts) + day/period — кілька sweep-перевірок поспіль. Перевірити навантаження/зайві записи.
- [ ] Багато правил/входжень: `GetTasksForRangeAsync` щоразу вантажить **усі** правила + усі шаблони користувача (`Include` Exceptions/ManualDates) і розгортає кожне. Немає кешу/ліміту кількості правил. Перевірити поведінку на десятках правил × місячний грід (42 дні) × повторні ефекти.
- [ ] Гонки «готово/пропущено/перенести»: дії роблять `await resolve/update/delete` потім `reload()`+`onTasksChanged`. Подвійний швидкий клік «Готово» → другий resolve на вже `Done` (ідемпотентно ставить `Done` знову — ок) або на `Skipped`→`Unassigned` із обнуленням дати (другий клік «Перенести» після «Пропущено» вже не знайде в дні). Перевірити оптимістичність/дизейбл кнопок під час запиту (зараз **не** дизейбляться — можливий подвійний сабміт).
- [ ] `addException` двічі поспіль (подвійний клік «Видалити» на віртуальному інстансі) → два `Cancelled` з однаковою `Date` → **дубль-дата → 500** (той самий корінь, що §9 HIGH). Дизейблити кнопку / робити upsert.
- [ ] `getFreeDays(minHours)` — `minHours` не обмежений згори на сервері; великі значення нешкідливі, але перевірити, що `minFreeHours` з клієнта (1..24) не йде за межі.
- [ ] Порядок у «Нерозподілених»: `OrderBy(Deadline==null).ThenBy(Deadline).ThenBy(StartDateTime)` — задачі без дедлайну в кінці. Перевірити стабільність сортування й що `StartDateTime==null` (типово для Unassigned) не ламає порядок.
- [ ] Надійність скасувань запитів: ефекти в `Planner`/`DayView`/`RecurringView` використовують прапорець `cancelled`/`AbortController`? У `Planner` — `cancelled` є; у `DayView.reload` (then без guard) при швидкій зміні дати можлива гонка «пізніша відповідь перезаписує новішу». Перевірити stale-response для `DayView`/`PeriodView` (там немає `cancelled`-guard).
- [ ] `recurringMarkings` прев'ю: ефект у `RecurringView` залежить від `onPreviewChange` (нова функція щорендеру Planner?) — `setRecurringMarkings` стабільна (з useState), тож ок; підтвердити, що ефект не циклиться.
