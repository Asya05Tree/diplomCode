## 2. Головне правило коду: максимальна простота

Це навчальний проєкт, і код мають розуміти навіть без глибокого досвіду. Тому:

- **Без зайвих патернів.** Не використовувати DI-контейнери понад вбудований в ASP.NET, не City Generic-репозиторії "на виріст", не абстрактні фабрики заради абстракції. Якщо задачу можна вирішити прямим методом на 10 рядків — не робити з неї інтерфейс + реалізацію + мок.
- **Один файл — одна відповідальність**, але без дроблення на 20 крихітних файлів там, де вистачить одного.
- **Коментарі обов'язкові** там, де відбувається щось не зовсім очевидне: чому саме так, а не "що робить рядок" (це видно й так). Приклад:
  ```csharp
  // Тег "молочне" ловить і сир, і кефір — перевіряємо предків тега, а не тільки сам тег
  var forbiddenIds = GetTagWithAncestors(userForbiddenTagId);
  ```
- **Мова коментарів і назв змінних:** назви змінних/методів/класів — англійською (це стандарт для C#/React, і так буде легше знайти приклади в інтернеті), а **коментарі-пояснення — українською**, щоб було зрозуміліше при захисті диплома.
- **Довгі методи розбивати**, якщо метод не влазить в один екран — це ознака, що варто виділити крок в окремий метод з назвою-поясненням.
- **Обробка помилок проста і явна**: try/catch там, де реально може щось піти не так (запит до БД, зовнішній виклик), без глобальних "ковтати всі помилки" конструкцій.
- Перед кожним контролером/сервісом — короткий коментар-шапка: що робить цей клас, якою мовою б це не пояснювалося другові.

## 3. Локалізація — тільки дві мови

- Мови інтерфейсу: **українська** та **англійська**. Більше жодних мов не додавати навіть як заготовку.
- Технічно: словники `uk.json` / `en.json` на фронті (ключ → текст), перемикання мови зберігається в `UserProfile.Language`.
- Українська — мова за замовчуванням.
- Тексти в БД (назви системних продуктів, рецептів, тегів) варто одразу зберігати з полем мови або хоча б `NameUk` / `NameEn`, якщо потрібно показувати системний довідник двома мовами. Якщо це занадто ускладнює — на перший етап можна залишити довідники тільки українською, а переклад інтерфейсу (кнопки, підписи) зробити повним.

## 4. Реєстрація та вхід

Тут в описі є нестиковка: сказано і "через Google", і "код на пошту". Це різні речі технічно. Пропоную **простий варіант, який реально встигнути зробити**, і позначаю альтернативу.

### Обраний варіант (за замовчуванням): email + код підтвердження
1. Користувач вводить email, пароль, стать, вік.
2. Сервер генерує 6-значний код, зберігає його (з часом дії ~10 хв) і надсилає на пошту (через SMTP, наприклад безкоштовний Mailtrap/Gmail SMTP для навчального проєкту).
3. Користувач вводить код → акаунт підтверджено → видається JWT.
4. Пароль в БД — тільки хеш (`BCrypt.Net`).

Це просто зробити, не вимагає реєстрації додатку в Google Cloud Console і схвалення OAuth-екрану, і при цьому дає той самий ефект "підтвердження через пошту", який описаний в задачі.

### Альтернатива: вхід через Google (OAuth)
Якщо саме "увійти одним кліком через Google-акаунт" — принципово важливо для захисту диплома, тоді:
- Google Sign-In на фронті видає `id_token`.
- Бекенд перевіряє токен через `Google.Apis.Auth`, дістає email, створює/знаходить користувача.
- Email при цьому підтверджувати кодом уже не треба — Google це вже гарантує.

**Це відкрите питання — потрібно обрати один з двох варіантів** (див. розділ 15).

### Таблиці (доповнення до `User` з planner-spec.md)
```
EmailVerificationCode(UserId, Code, ExpiresAt, IsUsed)
```

## 5. Кольорова система

### Ідея
Кожна **категорія/модуль** має свій закріплений пастельний колір, який використовується для всіх її елементів (картки задач, іконка в меню, підсвітка в календарі). Це не довільний акцент, а стала прив'язка "модуль → колір".

### Пропонована прив'язка (можна змінювати назви кольорів, суть — закріпленість)

| Модуль | Пастельний колір |
|---|---|
| Задачі / загальне | пастельно-синій |
| Їжа | пастельно-жовтий |
| Здоров'я / аптечка | пастельно-зелений |
| Фінанси | пастельно-помаранчевий |
| Навчання / робота | пастельно-фіолетовий |
| Цикл | пастельно-рожевий |
| Нотатки | пастельно-коричневий (бежевий) |

### Технічна реалізація
- CSS-змінні на модуль, а не хардкод кольору в кожному компоненті:
  ```css
  :root {
    --color-food: #FFE8B8;
    --color-health: #C9EAD3;
    --color-finance: #FFD9B3;
    /* ... */
  }
  ```
- Світла/темна тема — це **набір змінних**, що перемикається класом на `<body>` (`theme-light` / `theme-dark`), а не окремі версії кожного компонента. Пастельний колір модуля в темній темі стає темнішим/приглушенішим варіантом того самого відтінку (той самий тон, менша яскравість), а не іншим кольором — інакше "закріпленість кольору за модулем" зламається.
- У `UserProfile` вже є поле `AccentColor` (з planner-spec.md) — це загальний акцент інтерфейсу (кнопки, активні елементи), окремо від кольорів модулів вище.

## 6. Компоновка головного екрана — уточнити

З опису в задачі виходить така схема (відрізняється від `planner-spec.md` розділу 4.2):

```
┌─────────────────────────────┬──────────────────┐

│  частина): плани на сьогодні│  календар         │

│  які можна перенести        │  день зайнятий)   │
│  або видалити (=Нерозподі-  │                    │

Раджу підтвердити один варіант перед версткою, щоб не переробляти. Логіка та дані (Task, RecurrenceRule) не залежать від того, з якого боку календар — це суто питання CSS grid (`grid-template-columns`), змінити його потім не проблема.

## 7. Автозбереження

- Будь-яка форма (створення задачі, рецепта, запис у нотатки) зберігає чернетку локально, поки користувач не натиснув "Зберегти":
  - зберігати у `localStorage` під ключем на кшталт `draft:task:new`;
  - зберігати з невеликою затримкою (debounce ~500 мс), а не на кожне натискання клавіші;
  - при відкритті форми — перевіряти, чи є чернетка, і якщо так, пропонувати відновити.
- Це **суто фронтенд-механізм на випадок перезавантаження сторінки**, не плутати з "автоматичним збереженням на сервер" — на сервер дані йдуть тільки по явному "Зберегти", як і описано в `planner-spec.md`.
- Чернетка видаляється з `localStorage` одразу після успішного збереження на сервері.

## 8. Планування періодів (UI до вже готової моделі)

Модель (`RecurrenceRule`, `RecurrenceException`) вже описана в `planner-spec.md` (3.3). Тут — тільки як це виглядає при створенні задачі:

```
Назва задачі: [___________]
Коли:  ( ) Один раз, дата: [___]
       ( ) Повторюється: щодня / щотижня (дні: Пн Вт Ср...) / щомісяця
           з [дата початку]  по [дата закінчення / без кінця]
```

"Без кінця" технічно — `EndDate = null`, і календар при показі місяця сам генерує задачі на видимий діапазон (не на роки вперед).

## 10. Їжа — дані на першому етапі

Поки немає повноцінної БД рецептів — зберігати масив прямо у фронтовому/бекенд-коді як заготовку, у форматі, що один в один лягає на майбутні таблиці `Recipe` / `RecipeIngredient` з planner-spec.md, щоб потім просто перенести в БД без переробки структури:

```json
[
  {
    "name": "Пюре з рибою",
    "photoUrl": "/images/mash-fish.png",
    "cookTimeMinutes": 30,
    "ingredients": [
      { "name": "Картопля", "amountText": "4 шт", "tags": ["starch", "vegetable"] },
      { "name": "Молоко", "amountText": "100 мл", "tags": ["dairy"] },
      { "name": "Консервована сардина", "amountText": "1 банка", "tags": ["fish", "canned"] },
      { "name": "Яйце", "amountText": "1 шт", "tags": ["egg"] }
    ],
    "steps": ["Зварити картоплю", "Розім'яти з молоком", "Додати рибу", "Подавати з яйцем"]
  }
]
```

Такий файл (`recipes-seed.json`) можна одразу класти в БД як `Recipe`/`RecipeIngredient`/`ProductTag` через простий скрипт-сідер при старті проєкту — тоді структура коду не міняється, коли масив заміниться на 25-30 повноцінних рецептів.

## 11. Здоров'я — естетичні поля

Поля `Height`, `Weight` вже є в `UserProfile` (planner-spec.md). Додатково для "хронічних захворювань" — окрема таблиця, бо це список, а не одне поле:

```
ChronicCondition(Id, UserId, Name, AffectsFood, RelatedTagId)
```

- `AffectsFood = false` — просто інформація для естетики/самого користувача, ні на що не впливає.
- `AffectsFood = true` — тоді `RelatedTagId` створює **звичайне System/User-правило** (`Rule`) через той самий механізм, що й алергії — окремої логіки для "хвороб" не пишемо, вони заходять в той самий RuleEngine як ще один запис у таблиці Rule. Наприклад, діабет → м'яке чи жорстке правило на тег "цукор" (обирає сам користувач при додаванні).

## 12. Аптечка — джерело даних

Безкоштовне джерело: **Державний реєстр лікарських засобів України** (МОЗ / Державний експертний центр) і відкриті набори даних на **data.gov.ua** (Національний каталог цін на ліки — там є діюча речовина, торгова назва, форма випуску). ## 13. Теги блюд — приклад розбору (уточнення до 3.2/3.4 planner-spec.md)

Кожен інгредієнт рецепта отримує один або кілька тегів через `ProductTag`, а не сам рецепт — так запрет на алерген ловить рецепт автоматично через будь-який зі своїх інгредієнтів:

```
Пюре з рибою:
  Картопля       → tag: starch, vegetable
  Молоко         → tag: dairy, lactose
  Яєчний жовток  → tag: egg
  Яєчний білок   → tag: egg
  Сіль           → (без тегу алергену)
  Консервована сардина → tag: fish, canned
```

Якщо у користувача `Forbidden: dairy` — рецепт "Пюре з рибою" не покажеться, бо один з інгредієнтів (молоко) має тег `dairy`. Окремий "тег на рецепт" не потрібен — досить тегів на продукти, це вже описано в моделі, тут лише приклад для реалізації сідера.

## 14. Дошка для малювання

- Окрема вкладка, ні на що не впливає (як і зазначено).
- `<canvas>` на фронті, без бекенду взагалі — малювання, стирання (гумка = малювання білим/кольором фону), кнопка "Зберегти як PNG" (`canvas.toDataURL('image/png')` → завантаження файлу).
- Просте перо: колір + товщина, без шарів і складних інструментів — відповідає принципу "просто".
- Дані малюнка **не зберігаються на сервері** (немає такої вимоги) — тільки локальне завантаження файлу користувачем.

## 15. Відкриті питання (треба вирішити до кодування)

1. **Вхід:** email+код чи Google OAuth (розділ 4)?
2. **Розташування календаря** на головному екрані: ліворуч чи праворуч (розділ 6)?
3. Мова коментарів у коді підходить (укр. коментарі / англ. назви) чи потрібна інша конвенція?
4. Довідник продуктів і рецептів двомовний (uk/en) чи тільки українською на перший етап?
5. Модуль "навчання/робота" — як і в planner-spec.md, поки не спроєктовано; коли зʼявиться бачення, додати окремим розділом.
