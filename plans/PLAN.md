# План роботи

Робочий документ (не частина тексту диплома). Розширює план з `planner-spec.md` §7 до конкретних кроків
і прив'язує його до того, що вже зроблено в репозиторії. Мова — довільна, для власної зручності.

---

## Що вже зроблено (каркас проєкту)

- `server/` — ASP.NET Core Web API, порожній, але робочий: `Program.cs`, `AppDbContext`,
  моделі `User`/`UserProfile`/`UserModule` (planner-spec.md §3.1), контролер `/api/health`.
  Папки `Controllers/Services/RuleEngine/Repositories` відповідають шарам з planner-spec.md §2.2,
  у порожніх поки лежить `README.md` з поясненням, що туди піде.
- `client/` — React + Vite (без TS), запускається (`npm run dev`, порт 5173 фіксований).
  Є: сайдбар з усіма пунктами навігації й кольорами модулів (coding-guide.md §5),
  CSS-змінні для light/dark теми, i18n на uk/en (coding-guide.md §3), головний екран-заглушка
  з перевіркою з'єднання з backend.
- `docker-compose.yml` — MySQL 8 для розробки, без ручного встановлення MySQL на систему.
- `README.md` — як усе це запускати.

**Чого немає навіть в заготовці:** JWT-авторизації, реальних міграцій (жодної ще не створено),
RuleEngine, будь-яких модулів окрім порожнього ядра User/UserProfile/UserModule.

**.NET 8 SDK встановлено й перевірено** (`dotnet build` у `server/` проходить без помилок) —
якщо в терміналі команда `dotnet` не знаходиться, це стара сесія термінала, відкрита до встановлення:
достатньо відкрити новий термінал, PATH прописаний на рівні системи.

### Головний екран — вирішено

Календар ліворуч, права колонка — два блоки (замінено варіант з "Їжею" в правій колонці):
- зверху, більше місця: **задачі вибраного періоду** (перемикач День/Тиждень/Місяць, дефолт — сьогодні);
- знизу: **задачі, що потребують рішення** — не влізли / не зроблені вчасно / відкладені вручну,
  для кожної вибір "перенести" або "видалити" (той самий зміст, що й "Нерозподілені" з planner-spec.md §4.5,
  тут — компактний виджет, а не повний список).

Реалізовано в `client/src/pages/Dashboard.jsx`.

### Статистика — вирішено

Без окремого пункту меню й окремого екрана. Кожен модуль показує свою статистику всередині власної вкладки
(Їжа — свою, Фінанси — свою тощо), а не єдиний зведений розділ "Статистика". Пункт прибрано з сайдбара
(`client/src/components/Sidebar.jsx`). Практично це означає: задача "статистика модуля" з'являється разом
із самим модулем у відповідному місяці нижче, а не окремим пунктом у місяці 6.

## Перед тим, як писати код далі

1. **Закрити рештки відкритих питань з `coding-guide.md` §15**, бо вони впливають на структуру коду:
   - вхід: email+код чи Google OAuth (за замовчуванням у документі — email+код, це і закладено
     в план нижче; якщо потрібен Google — місяць 1 зміниться);
   - модуль "навчання/робота" поки не спроєктований на рівні даних — розписати перед місяцем 5.
   (Розташування календаря вже не в списку — вирішено вище.)

## Місяць 1 — Модель даних, схема БД, авторизація

Ціль: `dotnet run` + `npm run dev` дають робочий логін і порожній дашборд, дані реально лежать у MySQL.

- [ ] Переконатись що `dotnet run` у `server/` піднімається і `/api/health`
      повертає `database: "connected"` (MySQL з `docker compose up -d`)
- [ ] Перша міграція (`dotnet ef migrations add InitialCreate`) — зафіксувати User/UserProfile/UserModule
- [ ] Таблиця `EmailVerificationCode` (coding-guide.md §4) + сервіс відправки коду (SMTP, Mailtrap на розробку)
- [ ] Реєстрація: email, пароль (хеш через `BCrypt.Net`), стать, вік → код на пошту → підтвердження → JWT
- [ ] Вхід: email+пароль → JWT (access-токен, `Jwt:Key` з `appsettings.json` — замінити на реальний секрет
      перед будь-яким публічним деплоєм, зараз там заглушка)
- [ ] Фронтенд: форма реєстрації/входу, збереження токена, захищений запит до `/api/health` з токеном
- [ ] Таблиці `Tag`, `UserTagPreference`, `Rule` (planner-spec.md §3.2) — тільки схема, без логіки поки

## Місяць 3 — RuleEngine, теги, довідник продуктів — контрольна точка

- [ ] `RuleEngine/TagMatcher.cs` — перетин тегів об'єкта з `UserTagPreference` (з урахуванням `ParentId`-ієрархії)
- [ ] `RuleEngine/RuleEvaluator.cs` — Hard/Soft правила, конфлікт двох Hard як валідний результат
- [ ] Наповнити довідник продуктів тегами (200-300 штук, planner-spec.md §6) — це вузьке місце,
      від повноти розмітки залежить коректність фільтрації алергенів
- [ ] Екран "Мої обмеження" (planner-spec.md §4.10)
- [ ] **До кінця місяця має бути що показати науковому керівнику**: логін, календар з повтореннями,
      робочий RuleEngine хоч на одному прикладі (наприклад фільтр задач чи тестовий довідник)

## Правило контрольної точки

Якщо до кінця місяця 3 немає робочого логіну + календаря + хоч одного прикладу RuleEngine —
це сигнал зупинитись і спростити план, а не тягнути відставання в місяці 4-6 (planner-spec.md §7).
