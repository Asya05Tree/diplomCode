# Планувальник завдань — спецификация проекта

Документ фиксирует результат проектирования. Все решения ниже приняты осознанно, у каждого есть обоснование. Спорные места помечены отдельно.

---

## 1. Суть проекта

**Тема:** розробка планувальника завдань.

**Идея:** задачи из разных сфер жизни не изолированы, а связаны через общие ограничения и ресурсы. Система хранит данные пользователя один раз, проверяет их согласованность и снимает с человека менеджерскую работу — расчёты, проверки, составление списков. Решения остаются за человеком.

**Что система делает автоматически:**
- фильтрует блюда по аллергиям
- собирает список покупок из нехватки продуктов
- разворачивает повторяющиеся события в календарь
- показывает конфликты лекарств по запросу
- ранжирует ленту блюд по приоритету
- прогнозирует цикл и проверяет запасы к дате

**Что решает только человек:**
- приоритеты задач
- время выполнения и длительность
- что готовить и когда
- что переносить при перегрузке
- что важнее при конфликте

**Принцип, на котором всё держится:** один жест — несколько эффектов. Отметка покупки одновременно закрывает задачу, пополняет запасы и списывает деньги. Отдельного ввода данных система не требует.

## 2. Архитектура

### 2.1 Стек

| Слой | Технология |
|---|---|
| Backend | ASP.NET Core Web API (C#) |
| ORM | Entity Framework Core |
| БД | PostgreSQL (или MSSQL по требованию кафедры) |
| Frontend | React |
| Аутентификация | JWT |

### 2.2 Слои backend

```
Controllers        — HTTP API, валидация запросов
    ↓
Services           — бизнес-логика по доменам
    ↓
RuleEngine         — движок правил (фильтрация и ранжирование)
    ↓
Repositories       — доступ к данным через EF Core
    ↓
PostgreSQL
```

**RuleEngine — ключевой компонент.** Он вынесен отдельно, потому что используется всеми модулями: фильтрация блюд, проверка лекарств, проверка задач. Один механизм, разное наполнение.

### 2.3 Главное архитектурное решение: правила как данные

Ограничения не пишутся в коде условиями `if`, а хранятся в базе как строки. Проверка одна на всю систему: пересечение тегов объекта с запретами пользователя.

**Что это даёт:**
- новая аллергия = строка в БД, а не правка кода
- пользователь добавляет свои ограничения без программирования
- одна точка проверки — невозможно забыть проверку в новом месте
- объяснение бесплатно: система знает, какое правило сработало

**Цена решения:** качество зависит от полноты разметки справочников. Если у продукта не проставлен тег аллергена — правило его не поймает. Ошибка переезжает из кода в данные.

**Обработка неполноты:** для аллергенов «неизвестно» = «опасно» (продукт помечается предупреждением). Для остального «неизвестно» = «нет».

### 2.4 Модули

Ядро универсально, области жизни подключаются модулями. При регистрации пользователь отмечает, что ему нужно.

| Модуль | Статус | Справочник |
|---|---|---|
| Задачи и календарь | ядро, всегда | нет |
| Еда | реализуется | продукты, рецепты — дорого |
| Здоровье / аптечка | реализуется | вещества, конфликты — средне |
| Учёба / работа | реализуется | нет, только расписание |
| Цикл | реализуется | нет |
| Финансы | реализуется | нет, всё вручную |

Выключённый модуль не появляется нигде: ни в навигации, ни в фильтрах, ни в анкете.

**Расширяемость** (защищается как результат работы): пользователь может добавлять свои объекты в справочники, свои теги и свои правила. Новый модуль со своим генератором — только на уровне разработки. Это честная граница, её нужно указать в тексте.

## 3. Модель данных

### 3.1 Пользователь и настройки

```
User(Id, Email, PasswordHash, CreatedAt)

UserProfile(UserId, Height, Weight, BirthYear, Gender,
            DayStart, DayEnd, Language, Theme, AccentColor)

UserModule(UserId, ModuleCode, IsEnabled)
```

`Height` и `Weight` — необязательные, приблизительные. Спрашиваются один раз, доступны для правки всегда.

### 3.2 Теги и правила

```
Tag(Id, Namespace, Key, ParentId, DisplayName)
```

`Namespace` — группа: `allergen`, `nutrient`, `storage`, `substance`, `area`.
`ParentId` — иерархия. Запрет на родителя действует на всех потомков: запрет `dairy` ловит `cheese`, `kefir`, `butter`.

```
UserTagPreference(UserId, TagId, Relation, Weight)
```

`Relation`: `Forbidden` | `Avoid` | `Prefer`
`Weight`: 1–10, только для `Avoid` и `Prefer`

Это и есть все пользовательские правила. Аллергия — `Forbidden`. «Не люблю рыбу» — `Avoid` с весом. Один механизм, разная сила.

```
Rule(Id, UserId, Name, Strength, Weight, TagId, Action,
     Source, IsEnabled)
```

`Strength`: `Hard` (нарушать нельзя) | `Soft` (штраф при нарушении)
`Source`: `System` (поставляется) | `User` (создано вручную) | `Onboarding` (из анкеты)

**Жёсткие правила** сокращают множество вариантов до допустимых.
**Мягкие правила** упорядочивают допустимые и выбирают лучший. Они не запрещают — они голосуют весами. Конфликт двух мягких невозможен по определению.

**Конфликт двух жёстких** — валидный результат: система сообщает «вариантов нет, конфликтуют правила X и Y» и предлагает ослабить одно.

### 3.3 Задачи и календарь

```
Task(Id, UserId, Title, Description, ModuleCode,
     StartDateTime, DurationMinutes, Deadline,
     Status, IsPinned, RecurrenceRuleId, CreatedAt)
```

`Status`: `Planned` | `Done` | `Skipped` | `Unknown` | `Unassigned`

`Unknown` — полноценное третье состояние. Система не приравнивает молчание к выполнению: записать невыполненное как выполненное хуже, чем не знать.

`IsPinned` — закреплена пользователем, система не предлагает её двигать.

```
RecurrenceRule(Id, UserId, Pattern, DaysOfWeek, TimeOfDay,
               StartDate, EndDate)

RecurrenceException(Id, RecurrenceRuleId, Date,
                    ExceptionType, NewDateTime)
```

`ExceptionType`: `Cancelled` | `Moved`

**Повторяющиеся события не разворачиваются в базу.** Хранится одно правило + исключения. Задачи генерируются при показе интервала. Иначе семестровое расписание — это 60 строк, а изменение времени пары — правка 60 записей.

**Окно хранения:**
- назад: 90 дней, дальше автоматическая чистка
- вперёд: до одного года, дальше ввод не разрешён
- что дальше года — уходит в Заметки

```
Note(Id, UserId, Title, Content, CreatedAt)
```

### 3.4 Еда

```
Product(Id, Name, StorageGroupTagId, IsSystem, CreatedByUserId)
ProductTag(ProductId, TagId, Value)
```

`Value`: `Yes` | `No` | `Unknown` — для аллергенов третье состояние обязательно.

```
Recipe(Id, Name, PhotoUrl, CookTimeMinutes, LastCookedAt,
       IsSystem, CreatedByUserId)

RecipeIngredient(RecipeId, ProductId, AmountText)
RecipeStep(RecipeId, StepNumber, Text)
```

`AmountText` — строка вида «2 шт», «300 г». **Хранится справочно для человека, системой не проверяется.** Проверку наличия делает сам пользователь чекбоксами перед готовкой.

`LastCookedAt` — одно поле вместо отдельной таблицы истории. Обновляется в момент списания продуктов. Обеспечивает функцию «не показывать недавние».

`PhotoUrl` — для системных рецептов заглушки в стиле интерфейса, для пользовательских необязательно.

```
StockItem(UserId, ProductId, State, ExpiresAt, UpdatedAt)
```

`State`: `Available` | `RunningLow` | `OutOfStock`

**Количества не хранятся.** Штучное — это «есть, просто сколько». Скоропортящееся — «есть, просто до когда». Точный учёт требует ежедневного ручного ввода, от которого проект осознанно отказывается.

`ExpiresAt` заполняется автоматически по группе хранения продукта (молочка ~5 дней, консервы ~365) и помечается как оценка. Пользователь может исправить. Если группы нет — срок не ставится.

```
SelectedDish(Id, UserId, RecipeId, AddedAt, IsCooked)
```

Выбранные блюда **не привязаны к датам**. Человек готовит когда хочет. В календарь из еды попадает только поход в магазин — у него есть время и длительность.

### 3.5 Аптечка

```
Substance(Id, Name)
SubstanceConflict(SubstanceAId, SubstanceBId, Description, Severity)

Medicine(Id, Name, SubstanceId, IsSystem)
UserMedicine(UserId, MedicineId, State, ExpiresAt)
```

Конфликты хранятся **на веществах, а не на торговых названиях**: нурофен и ибупрофен — одно вещество, дублировать данные для каждого бренда нельзя.

**Учёта приёмов нет.** Ни задач, ни напоминаний, ни счётчиков остатка. Причина: приём лекарств редко идёт по расписанию — обезболивающее по потребности, витамины забываются, при болезни человеку не до планировщика. Модель, построенная на дисциплине отметок, не работает.

**Предупреждения не проактивные.** Показываются только при открытии карточки лекарства: «конфликтует с: алкоголь, варфарин». Система не всплывает с сообщениями при планировании еды — это перегружает без пользы.

### 3.6 Финансы

```
FinanceAccount(UserId, Balance, UpdatedAt)
FinanceLimit(UserId, PeriodType, Amount)
FinanceTransaction(Id, UserId, Amount, Type, Category,
                   Description, OccurredAt, TaskId)
```

Всё вводится вручную. Даты зарплаты в календарь не выносятся: их задерживают, есть кредиты и нюансы — человек ведёт это сам.

**Единственная автоматическая связь:** сумма покупки продуктов попадает в траты, и лента блюд может фильтроваться по «докупить не больше чем на N грн».

### 3.7 Цикл

```
CycleRecord(Id, UserId, StartDate, EndDate)
CycleSettings(UserId, ReduceLoadOnHeavyDays)
```

**Прогноз** считается по последним записям. Разброс:
- нет данных — ±5 дней
- есть записи, фактический разброс ≤3 дня — показываем узко
- разброс больше — показываем шире, одной строкой поясняем «цикл нерегулярный»

Никаких диагнозов и рекомендаций обратиться к врачу — только честная точность прогноза.

**Пропущенная отметка не додумывается.** Если пользователь не отметил начало — прогноз считается с чистого листа, пропуск в расчёт не берётся.

**Проверка запасов к дате:** перед прогнозируемым началом система смотрит аптечку и запасы (прокладки, обезболивающее, сладкое) — чего нет, попадает в список покупок. Отдельной логики не требует, используется тот же расчёт нехватки, что и с продуктами.

**В еду модуль не вмешивается.** Аппетит при ПМС индивидуален до противоположности, любая рекомендация будет неверной для половины пользователей.

### 3.8 Список покупок

```
ShoppingItem(Id, UserId, Section, ProductId, MedicineId,
             CustomText, IsChecked, EstimatedPrice)
```

`Section`: `Groceries` | `Pharmacy` | `Other`

Источники позиций: нехватка для выбранных блюд, статус `OutOfStock` в запасах, прогноз цикла, ручное добавление.

## 4. Интерфейс

### 4.1 Навигация

Боковое меню, пункты появляются по включённым модулям:

```
📅  Календарь
📋  Нераспределённые   (N)
🍲  Еда
💊  Аптечка
💰  Финансы
🎓  Учёба / работа
🌸  Цикл
📝  Заметки
📊  Статистика
⚙️  Настройки
```

4.2 Планувальник — головний екран

Розділи «Календар» і «Планувальник» об'єднані в один екран, поділений на дві частини. Ліва частина (≈35% ширини) — місячна сітка, яка виконує роль контексту: вона не є самостійним розділом, а показує те, що стосується поточного режиму роботи. Права частина (≈65%) — робоча область, де користувач створює та редагує записи. Такий поділ обрано тому, що планування вимагає постійного порівняння з іншими днями: коли огляд місяця залишається перед очима, користувач бачить вільні проміжки без переходів між сторінками.

Робоча область має два незалежні перемикачі. Перший — «День / Період» — визначає одиницю роботи: конкретна дата або довільний діапазон. Другий — «Повторювані» — вмикає режим роботи з правилами повторення; при його активації перший перемикач стає неактивним, оскільки правило повторення не належить ані окремому дню, ані діапазону.

4.3 Режими роботи

День. Права частина показує розклад обраної дати з часом, назвами завдань і позначкою повторюваності. Ліва сітка позначає поточний та обраний день. Це основний режим виконання.

Період. Користувач задає довільний діапазон дат. Права частина показує перелік завдань цього діапазону; ліва сітка заливкою позначає межі діапазону. Додатковий перемикач «показати вільні дні» підсвічує дні без завдань — з можливістю задати мінімальний вільний проміжок у годинах, оскільки за наявності щоденних занять повністю порожніх днів може не бути взагалі. Режим відповідає на питання «коли я можу виділити час», яке неможливо вирішити переглядом окремих днів.

Повторювані. Права частина містить перелік правил повторення та форму редагування обраного: дні тижня, час, період дії (з дати до дати) та перелік винятків. Ліва сітка в цьому режимі змінює призначення — вона стає передпереглядом обраного правила: підсвічує всі дні, у які воно спрацює, і закресленням позначає винятки. Це дозволяє користувачеві побачити результат налаштування одразу, без переходу до календаря та без розгортання правила у базі даних.

4.4 Позначення в сітці

Заливка дня в лівій сітці завжди належить поточному режиму й не поєднується з іншими позначеннями: у режимі «Період» вона позначає діапазон і вільні дні, у режимі «Повторювані» — дні дії правила. Показник «перевантажений день» не використовується, оскільки тривалість завдання є необов'язковим полем і сумарне навантаження дня не може бути обчислене достовірно. Натомість позначається накладання — дві задачі на один час, що визначається однозначно незалежно від заповненості полів.

### 4.5 Нераспределённые

Один список для трёх случаев: не влезло, не сделано вовремя, отложено вручную.

- **никакого автоудаления** — задачи висят бессрочно
- **счётчик на главном экране** — иначе список станет местом, где всё теряется
- **дедлайны подсвечиваются** — «оплатить счёт до 15-го», а сегодня 14-е

Утреннее напоминание о вчерашнем — один экран, три кнопки на задачу, нейтральный тон без оценок:

```
Вчера осталось 3 задачи:
  Зарядка          [Сделал] [Пропустил] [Отложить]
  Купить продукты  [Сделал] [Пропустил] [Отложить]
```

Не ответил — уходит в `Unknown` и в Нераспределённые.

### 4.6 Еда

**Экран раздела:**

```
Выбранные блюда (3)          [+ Планирую готовку]
  Борщ           [Приготовил]
  Омлет          [Приготовил]

Запасы                       [Изменить]
  Заканчивается: молоко, хлеб
  Испортится завтра: молоко
```

**Лента блюд** — отдельный экран, открывается по «Планирую готовку»:

```
[Из наличного] [С покупками до ___ грн] [Всё]

Повторы: ( ) скрыть недавние  ( ) показывать  (•) сначала новые

Борщ              ✓ всё есть
Паста карбонара   ○ докупить 2 (~85 грн)
Плов              ○ докупить 5 (~230 грн)
```

Режим **«Из наличного»** — самый частый реальный сценарий: что приготовить сейчас из того, что дома.

Если денег нет или выбран режим «из наличного» — блюда с нехваткой **не показываются вообще**, а не показываются с пометкой.

**Приоритет ранжирования:**
1. наличие продуктов
2. скоро испортится (поднимает блюда с этими продуктами)
3. не готовилось недавно
4. предпочтения пользователя (мягкие правила)

**Готовка:**

```
Борщ — приготовить?

Хватает ли ингредиентов?
  ☑ Свёкла    ☑ Картошка   ☐ Капуста
  ☑ Морковь   ☑ Лук

[Приготовил]
```

Проверку делает человек — система не знает граммовок и не притворяется, что знает.

После подтверждения:

```
Что осталось?
  Свёкла    [есть] [заканчивается] [нет]
  Картошка  [есть] [заканчивается] [нет]

[Всё осталось как было]
```

Кнопка «всё как было» закрывает большинство случаев одним нажатием. Что стало «нет» — уходит в список покупок. Тогда же обновляется `LastCookedAt`.

**Первый вход — шаблон, а не пустота.** Экран запасов показывает пример полупрозрачным, как placeholder в поле ввода:

```
Запасы  (пример — отметьте, что есть у вас)
  ☐ Мука     ☐ Соль      ☐ Масло
  ☐ Яйца     ☐ Молоко    ☐ Хлеб
  [+ добавить своё]
```

Лента работает сразу, с пустыми запасами — все блюда с пометкой «нужно докупить». Не «сначала заполни», а «вот результат, уточни — станет точнее».

**Запасы наполняются по ходу:** человек выбрал блюда → получил список покупок → отметил чекбоксами «это у меня уже есть» → отмеченное попало в запасы. Обязательного первичного заполнения нет.

**Если аллергии не указаны** — лента работает, но сверху честная строка: «Аллергии не указаны, блюда не фильтруются. [Указать]». Не блокируем, но и не притворяемся, что проверили.

### 4.7 Аптечка

Список лекарств с состоянием и сроком годности. Клик по препарату:

```
Ибупрофен
Вещество: ибупрофен
Состояние: есть          Годен до: 03.2027

Не сочетать с:
  • алкоголь
  • другие препараты с ибупрофеном (передозировка)
  • варфарин — усиливает действие
```

Никаких напоминаний, задач и учёта приёмов.

### 4.8 Список покупок

```
ПРОДУКТЫ                     ☐ Уже есть дома
  ☐ Молоко        ~45 грн
  ☐ Свёкла        ~20 грн

АПТЕКА
  ☐ Ибупрофен     ~80 грн

ДРУГОЕ
  ☐ (вручную)

Итого: ~350 грн
```

Разделы соответствуют модулям и разным магазинам. Отметка позиции: закрывает её, пополняет запасы, попадает в траты.

### 4.9 Статистика

Отдельный раздел. Считается по имеющимся 90 дням, **честно помечает нехватку данных**.

```
Задачи за месяц
  Выполнено 34 · Пропущено 8 · Нет данных 12
  ⓘ У трети задач нет отметок — цифры приблизительные

Еда
  Чаще всего готовили: борщ (6), омлет (4)
  Чаще покупали: молоко, хлеб, яйца

Финансы
  Траты по категориям, по неделям

Цикл
  Средняя длина 28 дней · Разброс 2 дня
```

Правило: если данных мало — так и пишем, а не рисуем красивый график из пустоты.

### 4.10 Настройки

```
Язык:        [Українська] [English]
Тема:        [Светлая] [Тёмная]
Акцент:      ● ● ● ● ●   (пастельная палитра)

Календарь:   первый день недели, границы дня,
             формат времени

Модули:      ☑ Еда  ☑ Аптечка  ☑ Финансы
             ☑ Учёба  ☑ Цикл

Мои ограничения:  список всех правил
             откуда взялось · вкл/выкл · сила
```

**Экран «Мои ограничения» доступен всегда**, а не только когда правило помешало: аллергия может пройти, вкусы поменяться. Быстрая правка из объяснения («Печенье исключено правилом X. [Изменить]») — дополнительный ярлык на тот же экран, а не единственный вход.

### 4.11 Визуальный стиль

- пастельная палитра, светлая и тёмная темы
- выбор акцентного цвета
- рисованные заглушки для рецептов в едином стиле с календарём
- нейтральный тон текстов: «осталось 3 задачи», не «вы проспали зарядку»

## 5. Границы работы

**Входит:**
задачи и календарь, повторения с исключениями, нераспределённые, движок правил на тегах, еда (лента, запасы, покупки, рецепты), аптечка с конфликтами, финансы вручную, учёба/работа, цикл, заметки, статистика, авторизация.

**Не входит** (указать разделом в тексте — защищает от вопросов «а почему нет»):
семейный доступ и несколько пользователей, мобильное приложение, распознавание еды по фото, интеграция с носимыми устройствами, ввод текстом через LLM, обнаружение закономерностей статистикой, модуль одежды и погоды, спорт, питомцы, садоводство, медицинские рекомендации, курсы лекарств с расписанием приёма, учёт продуктов в граммах.

## 6. Наполнение справочников

| Что | Объём | Как |
|---|---|---|
| Продукты с тегами | 200–300 | основа, от неё зависят аллергии |
| Рецепты | 25–30 | фото-заглушка + ингредиенты + шаги |
| Теги | 100–150 | по одному на правило, не больше |
| Вещества | 30–40 | только для демонстрации |
| Конфликты веществ | 30–50 пар | самые известные |
| Системные правила | 30–50 | лежат в БД как данные |

**Принцип отбора тегов:** тег заводится, если на него есть правило. «Содержит глютен» — есть правило, берём. «Страна производства» — правила нет, не берём.

**Шаги рецепта пишутся короткими строками**, не кулинарным текстом:
```
1. Взбить яйца с молоком
2. Разогреть сковороду
3. Вылить, жарить 5 минут
```

## 7. План работ

| Период | Содержание |
|---|---|
| Месяц 1 | Модель данных, схема БД, миграции, авторизация |
| Месяц 2 | Задачи, календарь, повторения, нераспределённые |
| Месяц 3 | Движок правил, теги, справочник продуктов. **Контрольная точка: система уже работает** |
| Месяц 4 | Еда: рецепты, запасы, лента, список покупок |
| Месяц 5 | Аптечка, финансы, цикл, учёба |
| Месяц 6 | Статистика, настройки, темы, тесты, текст диплома |

**К концу третьего месяца должно быть что защищать.** Всё после — улучшения, а не фундамент.

## 8. Открытые вопросы

1. Требования кафедры к алгоритмической части и научной новизне — не выяснены. От этого зависит, нужно ли усложнять планировщик.
2. Источник данных для справочника продуктов — решает автор.
3. Точная навигация внутри разделов и мобильная адаптация — прорабатывается при вёрстке.

---

## 9. Что защищается как результат

1. **Расширяемая архитектура на декларативных правилах.** Ограничения хранятся как данные, а не как условия в коде. Новое ограничение не требует изменения программы.
2. **Модульность областей жизни.** Ядро универсально, области подключаются. Реализовано четыре, архитектура допускает больше.
3. **Межмодульные связи через общие механизмы.** Еда ↔ здоровье (аллергии, конфликты веществ), еда ↔ финансы (стоимость докупки), цикл ↔ запасы (проверка к дате). Связи не прописаны попарно, а возникают из общего словаря тегов.
4. **Работа при неполных данных.** Третье состояние «неизвестно» в аллергенах и статусах задач; система не додумывает то, чего не знает.
5. **Минимизация ручного ввода.** Один жест — несколько эффектов. Измеримый критерий: среднее число обязательных действий пользователя в день.
