## 2026-11-07 (сесія 4) — Ремедіація безпеки, фаза P2 (продовження): P2-7

**Контекст:** той самий цикл по `adversarial-review/ПЛАН-ВИПРАВЛЕНЬ.md`; кожен фікс має перевести відповідний PoC з CONFIRMED у REFUTED (наживо, `http://localhost:5080`).

**Зроблено цієї сесії — P2-7 (TOCTOU лічильника Quick Add):** `server/Services/BillingService.cs`, метод `ConsumeAsync`.
- **Корінь:** було read-check-increment трьома кроками (прочитали `QuickAddUsedCount`, перевірили `< FreeLimit`, окремо інкрементували + `SaveChanges`). Паралельні `consume` усі читали `used=0`, усі проходили перевірку й інкрементували → ліміт обходився (12 паралельних → 8 проходжень при ліміті 3).
- **Фікс:** інкремент тепер **атомарний одним UPDATE** — `_db.Users.Where(x => x.Id == userId && !x.QuickAddUnlocked && x.QuickAddUsedCount < FreeLimit).ExecuteUpdateAsync(... used = used + 1)`; гейт за кількістю змінених рядків: `consumed == 1` → витратили спробу (200); `0` рядків і `QuickAddUnlocked` → куплено, ліміт не діє (200); інакше → ліміт вичерпано (402). Рядковий лок MySQL (InnoDB) серіалізує конкурентні UPDATE, тож проходить рівно `FreeLimit`. Без транзакцій/локів у коді, без concurrency-токена — одна атомарна умова в БД (coding-guide §2).

**Перевірка (наживо, збірка 0/0):**
- `02-quick-add/consume_race` (12 паралельних, ліміт 3) → **REFUTED** стабільно у 3 прогонах поспіль: рівно **3×200**, **9×402**, збережений `QuickAddUsedCount=3`. Ні limit-skip, ні lost-updates. PoC оновлено на явний REFUTED-вердикт (було: «not reproduced»).

(CONFIRMED-рядки там — відома/задокументована поведінка mock-режиму та «paywall гейтить лише NLP, не створення сутностей» з P0-рев'ю білінгу, не P2-7 і не регресія.)
- Бекенд зупинено в кінці (0 слухачів на :5080).

## 2026-11-07 (сесія 3) — Ремедіація безпеки, фаза P2 (продовження): P2-6

**Контекст:** той самий цикл по `adversarial-review/ПЛАН-ВИПРАВЛЕНЬ.md`; кожен фікс має перевести відповідний PoC з CONFIRMED у REFUTED (наживо, `http://localhost:5080`).

**Зроблено цієї сесії — P2-6 (Реєстрація/вхід):** усе в `server/Controllers/AuthController.cs` (+ модель `EmailVerificationCode` і міграція `AddEmailCodeAttempts`).
- **Брутфорс коду.** Додано `Attempts` і `CreatedAt` до `EmailVerificationCode`. `register`: беремо єдиний чинний код; невірна спроба → `Attempts++`, після **5** код «спалюється» (`IsUsed=true`) — lockout. `send-code`: новий код **гасить попередні** (один чинний на email) + **60-с кулдаун** на email (повторний запит коду раніше — тихо нічого не робить). Разом: ≤5 спроб на код → перебір 10^6 нереальний.
- **Енумерація.** `send-code` тепер **завжди 200** незалежно від існування email (було 400 `email_taken` vs 200). Код реально створюється/шлеться лише коли email вільний і немає кулдауну. `login` і раніше був нейтральний.
- **Gmail-аліаси.** `NormalizeEmail()` — для gmail прибирає крапки та `+suffix`; застосовано в `send-code/register/login`. Одна скринька = один акаунт (аліаси ловить `email_taken`, квота не множиться).
- **bcrypt 72 байти.** Перевірка довжини пароля тепер у **байтах** (`Encoding.UTF8.GetByteCount ≤ 72`), а не символах (36 кирилічних = 72 байти; char-ліміт колізію не закривав).
- **Супутньо (закрито дірки з `server-validation`, належать P2-2 для auth):** `[StringLength]` на DTO auth → завеликий email дає **400, а не 500** (varchar(255) overflow); відхилено email із порожньою локальною частиною (`@gmail.com`); **стать** звужено до `female|male|other` (було — сирий рядок у БД); нік вимагає ≥1 літери (regex lookahead) — `--`/пробіли відхилено.

**Перевірка (наживо, збірка 0/0):**
- `01-auth/code-bruteforce` → **REFUTED** (код спалено після 5 спроб; 1 чинний код).
- `01-auth/enumeration` → **REFUTED** (обидва `send-code` → 200 без `email_taken`; `login` нейтральний).
- `01-auth/gmail-alias` → **REFUTED** (3 аліаси → 1 акаунт; 2-й/3-й → `email_taken`).
- `01-auth/bcrypt-truncation` → **REFUTED** (80-байтний пароль → 400).
- `01-auth/server-validation` → усі дірки закрито (порожня локальна частина, oversized→400, стать, нік).
- `01-auth/token-lifetime-revocation` → і далі **REFUTED** (P2-1 тримається).
- Валідні потоки: register 200, **вхід через аліас із крапками** → 200 (резолвиться в канонічний акаунт), невірний пароль → 400, короткий пароль → 400. Регресій provision по інших вкладках немає (перевірено finance/food/notes).

**Інфраструктура PoC:** `_lib/provision.mjs` отримав `normalizeEmail()` і читає/чистить коди за **канонічним** email (сервер зберігає саме його) — інакше весь набір PoC падав би на провіженгу. PoC `code-bruteforce`, `gmail-alias`, `server-validation` переписано під виправлену поведінку й реальну перевірку БД.

**Рішення/компроміс:** замість вбудованого `AddRateLimiter` за IP (ламав би локальні тести й суперечить coding-guide §2 — зайва складність) обрано простий **per-email кулдаун + lockout + один чинний код**. Цього достатньо, щоб зробити брутфорс непрактичним; за потреби IP-rate-limit — окремий follow-up.

**Відмічено в DoD:** P2-6.

**Де зупинився / далі:** лишилось у P2 — **P2-7** (TOCTOU лічильника Quick Add → атомарний `UPDATE … WHERE used < limit`, `server/Services/BillingService.cs:63`), **P2-8** (watchlist: сирота `ReturnTaskId` + гонка `/schedule` + минулі дедлайни), **P2-9** (ідемпотентність списку покупок: дедуп Food→покупки видно в `06-food/03`, spam plan-trip, автокатегоризація), **P2-10** (інваріанти роботи/навчання: стелі розкладу/доходу/оцінок; leave `end<start` своп — `10-work/07`).
